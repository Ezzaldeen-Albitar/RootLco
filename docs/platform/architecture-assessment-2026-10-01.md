## Summary

- **One product.** One modular monolith (`docs/adr/ADR-001-modular-monolith-architecture.md`), one server foundation and one PostgreSQL database with row-level security. `apps/api/src/modules` holds 21 directories with an `index.ts`: the 20 in section 2 plus `meta`, whose surface is a ping service (`meta/index.ts:20-25`). Nothing found argues for a rewrite, a customer fork or extracting a service.
- **Module entitlements are not enforced on the server today.**
  - The tables, the resolver, the request-pipeline hook and the plan form exist.
  - No API operation declares a feature flag, and no migration or seed registers one. `INSERT INTO org.feature_flags` and `featureFlag:` occur only in four files under `tests/`.
  - What exists is navigation filtered by permission, plus plan capacity limits. That is not a modular commercial system.
- **Workshop without inventory (code reading, not demonstrated).** The code does not block a reception-to-delivery run with no inventory rows: zero open commitments do not block closure or readiness, item references are nullable, and a work-order invoice posts no stock. The code does block charging for parts: quotation drafting writes service lines only, and work-order invoices copy quotation lines (C-08). Scenario S-1 has not been run.
- **Inventory without workshop (code reading, not demonstrated).** Items, locations, receipts, transfers, counts, adjustments and reservations carry no required vehicle, appointment or work-order reference in the schema read, so the code does not block them without workshop records. Stock leaves without a work order only through a counter sale, which needs billing and a customer (C-10). Scenario S-2 has not been run.
- **Settings.** No module reads an `org.company_settings` or `org.branch_settings` row, so no such row can currently switch off audit, document integrity or tenant isolation. Configuration that does change behaviour lives in other columns, for example the branch time zone (section 5).
- **Tax.**
  - A priced line whose price names no tax class is charged a literal zero rate.
  - A tax class with no effective rate is refused, never defaulted.
  - No tax-rate literal was found in `apps/api/src` (pattern in section 6).
  - Tax classes and rates are written only by six test files. A structural write path that sets no rate is designed in section 6.1 and is held, with the rates, until the questionnaire is answered.
- **Couplings.** The couplings that stop separate packages are concrete and few (C-01 to C-17). Each one has a focused, additive change (FC-01 to FC-20). None needs a rewrite.
- **Continuous delivery.**
  - These exist: immutable forward-only migrations, a frozen schema baseline, backups, and a restored-copy rehearsal documented as a required manual step.
  - These do not exist: per-tenant release control of capabilities, a module lifecycle, an automated upgrade test over a populated database, and production monitoring.

### Tenant, legal entity, branch and warehouse

- **Tenant** is `org.tenants`. Every tenant-owned table carries the tenant under row-level security (ADR-004). The resolver reads the current tenant itself (`20260717105000_org_settings_tax_features.sql:322-326`).
- **Legal entity** is `org.legal_companies`. Tax classes and rates belong to it (`20260717105000_org_settings_tax_features.sql:168,207`). Approval limits are company-scoped (ADR-023 `:154-155`).
- **Branch** is `org.branches`, always inside one legal company. Number sequences and stock locations are per branch (`sequence-registry.ts:81-162`; `20260723093000_inv_reference.sql:312-341`).
- **Warehouse has two registers.** `org.warehouses` and `org.storage_locations` have no consumer. Their table comment says inventory consumes them (`20260717104000_org_operational_structure.sql:189`), but `inv.stock_locations` has no foreign key to them (`20260723093000_inv_reference.sql:312-341`). The open decision is already recorded at `docs/product/owner-requirements-2026-09-06.md:317`. See C-13.

### Module lifecycle: what exists today

The definitions of activation, upgrade, downgrade, expiry and reactivation are **proposed in ADR-024 only**. This section states the measured state they start from.

- **Activation.** Tenant feature overrides can be inserted only while the tenant is provisioning (`20260831093000_iam_platform_privilege_graph.sql:217-222`).
- **Upgrade and downgrade.** Plan-level assign, renew, upgrade, downgrade and cancel, each with a reason (`capability-status.md:92`; event kinds at `20260916091000_org_subscription_commerce.sql:104-108`), with an over-capacity check and explicit override (`capability-status.md:93`). No effect on modules.
- **Expiry.** Plans carry `term_months` (`20260916091000_org_subscription_commerce.sql:47,72-73`); subscriptions admit status `expired` (`20260717102000_org_subscriptions.sql:225-226`). Whether anything writes `expired` was not verified. No module effect.
- **Reactivation.** Tenant-level suspend and reactivate exist (`capability-status.md:94`, proof owed).

**Default-enabled matters for upgrade safety.** `org.feature_flags.default_enabled` defaults to false (`20260717102000_org_subscriptions.sql:73`). A module flag registered with that default and then declared on the module's operations would switch the module off for every tenant whose plan does not name it: a silent behaviour change on upgrade, which directive section 2 forbids. FC-01 therefore registers module flags default-on; the decision is ADR-024's.

### 6.1 Proposed tax write path: structure only, held until the questionnaire is answered

**Status: proposed design (FC-20), held until the accounting questionnaire is answered.** It sets no rate, names no jurisdiction and assumes no tax model. The controls in items 2 to 5 are candidate shapes for review with the questionnaire answers, not decided tax-control policy. Whether the structural part may go ahead earlier is an Owner question (`docs/product/owner-directive-2026-09-16/README.md`, open decision 10).

1. **Scope.** Classes and rates stay owned by a legal company (existing foreign keys). A branch resolves the rate of its company; no branch-level rate.
2. **Permission.** Operations declare the seeded `org.tax.manage`. No provisioned administrator holds it today: the provisioning bundle excludes it and delegation is held-only (`tests/backend/p1-31-provisioning-bundle.test.ts:1106-1121`). Who receives it is a transition decision (CC-OD-50), not a default.
3. **Maker-checker (candidate).** A rate would be scheduled by one holder and approved by a different holder before resolution could return it, reusing the dual-control pattern the database already applies to credit notes and adjustments (ADR-023 `:49-50`; `capability-status.md:141`). Today `status` admits only active or inactive (`20260717105000:231`), so a pending state needs an additive forward migration.
4. **Effective-dated insert only.** A new rate is a new row whose `effective_from` is not earlier than its approval date. A rate already in force is never updated in its rate or start date; a superseding rate closes the previous row's `effective_to` at its own start, and that forward close is the only permitted update. Because the runtime role holds UPDATE today, this needs a guard trigger plus a restrictive write policy requiring the permission.
5. **Audit.** Catalogued audit actions for class create and retire and for rate schedule, approve, refuse and close, written through `iam.audit_append`, classified financial.
6. **Documents untouched.** Issued and drafted documents keep their captured rates (existing snapshots). Nothing is recalculated.

**Blocked on the questionnaire:** this whole design, including the candidate controls in items 2 to 5; every rate value; whether selling prices include tax; whether a missing class may mean untaxed (CC-OD-48); transaction or customer classifications; legal tax-invoice fields (D10).

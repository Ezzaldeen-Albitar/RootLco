**What this is:** the factual foundation under `canonical-plan.md` §5. Before
one screen is designed, this records — with file and line — which Backend
contracts the 35 canonical tasks can bind, which are missing, and which are
decision-gated. The governing facts:

- The entire appointment + reception public surface is **12 POST commands and
  zero reads** (`docs/product/workshop/frontend-implementation-program.md:334-336`).
- The reception read remediation plan existed as **PLANNED, NOT EXECUTED** at
  the source head (`docs/phase-1/phase-1-27/reception-read-surface-plan.md:4`);
  it was EXECUTED 2026-08-12 (PR #220) and its status line now records that.
- No canonical P1-28 task register existed anywhere in the repository before
  this phase's `canonical-plan.md`
  (`docs/product/workshop/reception-media-checklist.md:476-479`).

Conventions used below: RV = `recordVersion`. IK = `Idempotency-Key` mandatory
(8-200 chars; missing answers 400 `ERR-INT-002`; key reuse with a different
payload answers 409 `ERR-INT-001`; replay returns the stored body at **200
with no ETag** — `route-handler.ts:369-401`). All operations return
`x-correlation-id` on every response, `Cache-Control: no-store, private`, and
problem+json `{type, title, status, code, correlationId, violations[{path,rule}]}`
(`apps/api/src/server/errors/problem.ts:25-44`). Pagination where it exists:
`{items, nextCursor, hasMore}`, opaque cursor up to 512 chars, limit 1-100
default 50 (`apps/api/src/server/db/pagination.ts:21-66`).

## 5. The five riskiest contract facts a UI developer would guess wrong

1. **"Confirm" does not exist.** Confirmation is a side effect of
   `apt.appointment-reschedule`; `pending_confirmation` is reachable by NO
   operation; and any window violation on reschedule reports path
   `body.confirmedFrom` even when `confirmedTo` is the bad field
   (`appointment-service.ts:184-207`). Every screen must label the control as
   what it truthfully calls (WFP-04 exit criterion).

2. **There is no GET anywhere in apt/rec**, so the only source of the
   `recordVersion` that five version-guarded writes demand is a previous
   write's response in the same session. Create's `ETag:"1"` is load-bearing;
   close the browser and the vehicle is in custody with no path forward
   (`owner-workflow-requirements.md:182-197`). Cache RVs from every command
   response; never assume a re-read exists.

3. **Three different replay shapes.** Idempotent replay of ANY command returns
   **200** (even create, whose first answer was 201) with **no ETag**, body
   only (`route-handler.ts:369-401`); re-running approve on an authorized
   visit with a NEW key answers 409 `ERR-TRN-001` — and re-reading does NOT
   fix `ERR-TRN-001`; re-running convert on a converted visit answers **200
   with `alreadyConverted:true`, which is success**. Approve also returns
   RV = sent+2 when it walks two edges; convert returns NO ETag at all.

4. **WF-27: complaint and contents writes pass the application's permission
   check with `rec.reception.evidence.manage` and are then refused by the
   DATABASE without `iam.sensitive.view`** — a 403 at write time on a form the
   operator was allowed to open. The adapter must map this honestly, and
   SEC-001's role mapping must grant the pair together.

5. **Check-in couples the two domains invisibly:** `POST /receptions` with
   appointment origin marks the appointment `checked_in` in the same
   transaction with no version predicate; body
   `companyId`/`branchId`/`vehicleId` must EQUAL the appointment's own or the
   request answers 422 `incoherent_reference`; only a `confirmed` appointment
   can check in (409 `ERR-TRN-001`); and one-open-visit-per-vehicle and
   one-consumption-per-origin both surface as the SAME 409 `ERR-RES-002`
   message.

Honourable mentions: odometer `value` is a JSON number in and a decimal string
out (INS-19); the `condition_item` and `damage_mark` vocabularies differ by
three tokens and must not be conflated; 400 and 422 both map to the web
client's `validation` kind; `ERR-RES-001` 404 deliberately hides cross-tenant
existence; scope keys in query strings throw client-side
(`read-operation.ts:89-133`).

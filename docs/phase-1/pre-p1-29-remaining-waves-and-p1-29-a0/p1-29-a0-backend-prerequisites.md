## 1. The reconciliation nobody had done

`docs/phase-1/pre-p1-29-multi-tenant-admin-rbac-workflow/dependencies.md` §4 already carries a
canonical register titled _"Genuine P1-29 dependencies — record, do not simulate"_, with seven
entries it numbers `B1`…`B7`. **The frozen P1-29 gate was written without reference to it**, and
the two overlap without being identical.

Both are canonical. Neither is wrong. Reconciling them is the single most valuable output of this
pass, because it reveals **two prerequisites the P1-29 gate does not have**.

To avoid the three-way `B1` collision recorded as `AMB-03` and `AMB-13`, the `dependencies.md` ids
are written here as `DEP-B1`…`DEP-B7`.

| `dependencies.md` | subject                                 | P1-29 gate                                                 |
| ----------------- | --------------------------------------- | ---------------------------------------------------------- |
| `DEP-B1`          | Departments as an operational dimension | **`BE-7`**                                                 |
| `DEP-B2`          | **Technician roster writes**            | **absent — see `BE-9`**                                    |
| `DEP-B3`          | Work-order-to-customer linkage          | **`BE-3`**                                                 |
| `DEP-B4`          | **Branch-wide job queue read**          | **absent — see `BE-10`**                                   |
| `DEP-B5`          | Branch-wide QC queue read               | `INS-13`, recorded as a gap, **not** as a prerequisite     |
| `DEP-B6`          | Assignment notifications                | **`BE-6`**                                                 |
| `DEP-B7`          | Unified work-order history              | `INS-30`, recorded as a blocker, **not** as a prerequisite |

And in the other direction, four gate items have no `dependencies.md` counterpart, because that
register is about _operational data capabilities_ while the gate also covers _contract and CI_:

| gate   | subject                       | why `dependencies.md` does not list it |
| ------ | ----------------------------- | -------------------------------------- |
| `BE-1` | publish the state catalogues  | a contract gap, not a data gap         |
| `BE-2` | caller → technician profile   | identity exposure, not roster data     |
| `BE-4` | diagnostic template lifecycle | not in that register's field of view   |
| `BE-5` | permission parity gate        | a CI control                           |

### 1.1 `BE-9` — technician roster writes (new, from `DEP-B2`)

> _"A production tenant has zero technicians and no supported means of acquiring any."_

**No operation creates or edits a technician profile.** Six `tech` operations ship — four
labour-session operations plus availability and queue — and all six are reads or labour-session
state changes. There is no `POST` or `PATCH` anywhere under
`apps/api/src/app/api/v1/technicians/`. The only code that inserts a technician profile is test
scaffolding.

**This changes `BE-2`.** `BE-2` resolves a caller to _their_ technician profile. If no profile can
be created, there is nothing to resolve, and `BE-2` alone leaves the technician persona exactly as
blocked as before. **`BE-9` is a hard prerequisite of `BE-2`, and the gate does not say so.**

`BE-9` is also the prerequisite of the _supervisor_ path: the availability picker returns
candidates from a roster that a production tenant cannot populate.

### 1.2 `BE-10` — branch-scoped job and QC queue reads (new, from `DEP-B4` and `DEP-B5`)

**No operation lists jobs at branch scope, and no QC read spans a branch.** A supervisor's job board
and a QC supervisor's queue are therefore both unbuildable, and — as `dependencies.md` says
explicitly — cannot be faked by iterating the work-order list, which is registered
`expensive-read` and would be wrong under paging besides.

### 1.3 A correction owed to `dependencies.md` §4

`DEP-B4` concludes: _"a job can be created, updated, transitioned, assigned and historically
audited. It cannot be read."_

**The last sentence is wrong.** `WorkOrderDetail` is
`{workOrder, jobs: readonly JobView[], nextStates}`
(`apps/api/src/modules/work-order/application/work-order-service.ts:166-170`), and the route's own
summary is _"Read one work order with its jobs and reachable states."_ `JobView` carries
`{id, workOrderId, title, jobType, state, requiresDiagnostic, recordVersion}` (`:112-120`).

The precise statement is: **a job is readable as an element of the work-order detail projection;
there is no job list at branch scope and no single-job read.** Everything `DEP-B4` concludes about
a _board_ still holds. The flat claim does not.

This planning slice does not edit another initiative's canonical document. The correction is
recorded here and belongs to the PRE-P1-29 initiative to apply.

## 2. The specification format

Every prerequisite below carries the fields §17 requires:

finding ids · business requirement · current source evidence · missing capability · exact likely
code locations · database impact · API impact · permissions · contract-mirror impact · tests ·
security threats · rollback · acceptance criteria · PRE-P1-29 dependency · estimated complexity.

**Complexity** is S / M / L, and it is a statement about _surface_, not about difficulty:
S = one route or one script; M = a service plus routes plus seeds; L = new schema modelling.

**It must parse, not grep.** Permission codes and **audit action** codes share the identical
three-segment dotted shape — `wo.work_order.transition` and `wo.work_order.state_changed` are
indistinguishable to a regex — and a naive scan produces a list dominated by audit actions. That is
the defect class that has produced a false gate result in this repository repeatedly, and it is why
the P1-28 gates were rebuilt on the TypeScript AST. The gate must read the `permissions` array of a
**parsed** `defineOperation` call and nothing else.

**The reverse direction should report, not fail.** Thirteen seeded codes are declared by no operation: `iam.login.view_all`, `inv.cost.view`, `inv.item.manage`, `org.branch.manage`, `org.company.manage`, `org.department.manage`, `org.subscription.manage`, `org.tax.manage`, `rec.reception.receiving_employee.assign_any`, `rpt.report.configure`, `sal.reversal.approve`, `wo.work_order.create`, `wty.policy.manage`. Three of them are enforced in the database and are permanent, not pending: `inv.cost.view`, checked twelve times across nine RLS policies on the three restricted cost tables (`inv.item_cost_details`, `inv.stock_adjustment_details`, `inv.external_purchase_part_details`); `iam.login.view_all`, in one RLS policy (`supabase/migrations/20260718098000_iam_rls_grants_hardening.sql:73`); and `rec.reception.receiving_employee.assign_any`, consumed by `iam.has_permission_in_scope` inside the `rec.stamp_receiving_employee_identity()` BEFORE INSERT trigger (`supabase/migrations/20260815093000_rec_receiving_employee_identity.sql:184`) — which is why `apps/web/src/features/receptions/people/receiving-employee-directory.ts:89` records that it is declared by no operation deliberately. Five carry the `org.` prefix and are exactly the five orphans of G-4 (`scope.md:49`) that Wave C is scoped to close (`scope.md:176`); they are _expected_ to be orphans until then, and failing on them would block unrelated work.

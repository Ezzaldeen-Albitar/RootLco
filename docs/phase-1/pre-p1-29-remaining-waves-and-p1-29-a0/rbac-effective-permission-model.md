# RBAC effective-permission model, and the navigation capability contract

**What the IAM authorization semantics actually are today**, established from the functions and
policies that decide them — not from any document's description of them.

## The rule that outranks every other

**Authorization is by permission, never by role name** (P-5). A search of the whole tree for an
authorization decision that reads a role code or display name is part of the evidence below. No
future contract, screen or gate may reintroduce one.

## What a consumer of effective capability must understand

The nine semantics below are what a role editor, a permission viewer and a navigation contract all
have to render correctly. Getting any of them wrong produces a UI that lies about authority:

multiple roles · allow/deny precedence · scopes · grant validity · revocation · delegation ·
overrides · Company Owner constraints · platform authority separation.

## The navigation capability contract — and its one non-negotiable caveat

A future authenticated endpoint may return the caller's resolved capabilities so the frontend can
decide what to display.

> **Every API operation independently authorizes. A navigation capability response is UX support,
> never security.** (P-4.)

Two properties the shipped client already has and must keep: it **fails closed** — an unknown
capability set yields an empty menu — and membership is **exact**, with no wildcard and no
prefix match.

The decisive open question for such a contract is whether the session's `permissions[]` is
scope-aware or scope-blind, because a scope-blind list rendered as capability will show a user
actions they hold in one branch while they are looking at another. The evidence is below.

## The semantics, as the code decides them

### 1. Multiple roles — one user, several grants, combined as a UNION of allows

**EXISTS AND LOAD-BEARING.**

Nothing constrains a user to one grant: `iam.role_grants` has no unique index on (tenant_id, user_id) — only `pk_role_grants` on id and `uq_role_grants_tenant_id` on (tenant_id, id) (20260718092000_iam_role_grants_and_scopes.sql:82-83), plus a non-unique `ix_role_grants_user` (:103). Combination is a set-level aggregate over the whole grant×mapping join, so the effective allow-set is the UNION of every active grant's allow mappings. Scope combines the same way: `iam.has_permission_in_scope` :178-198 uses `EXISTS`, so any ONE active granting grant whose scope matches satisfies the request. Approval ceilings combine differently and deliberately — a direct user limit beats a role limit, and among role limits the LARGEST wins (`ORDER BY (al.user_id IS NOT NULL) DESC, al.amount DESC LIMIT 1`, apps/api/src/server/auth/authorization.ts:304-305), documented at :238-239 as 'holding two roles grants the union of their authority rather than the intersection'.

_Evidence:_ supabase/migrations/20260718097000_iam_context_and_permission_functions.sql:104-114 — `SELECT bool_or(rp.effect = 'allow'), bool_or(rp.effect = 'deny') INTO v_allow, v_deny FROM iam.role_grants g JOIN iam.role_permissions rp ON rp.tenant_id = g.tenant_id AND rp.role_id = g.role_id WHERE g.tenant_id = v_tenant AND g.user_id = v_user AND g.status = 'active' ... AND rp.permission_id = v_perm;` then `RETURN COALESCE(v_allow, false) AND NOT COALESCE(v_deny, false);`

### 2. Allow / deny precedence — a real persisted deny, and in the scoped function the deny sweep is scope-blind

**EXISTS AND LOAD-BEARING.**

B1's finding is CONFIRMED against develop: deny wins in `iam.has_permission`. Two properties the effective-permission document must state, both verified in the SQL above. (a) The deny query in `has_permission_in_scope` has NO join to `iam.grant_scopes` and no company/branch/department predicate — so a deny mapping reached through a grant scoped to one branch denies that permission in EVERY scope, tenant-wide. Deny is not scopeable today. (b) Deny is evaluated BEFORE the allow/scope query and short-circuits (`RETURN false`), so scope never gets a chance to rescue it. Deny is also the one delegation exemption: `ins_role_permissions_delegable` (20260726090000:310-315) and `DelegationPolicy.assertDelegable` (delegation-policy.ts:131 `if (effect === 'deny') return;`) both let an administrator write a deny for a permission they do not themselves hold, on the stated ground that de-escalation is never an escalation. NOTE: no deny row ships — `supabase/seeds/04_iam_permission_catalog.sql` seeds only `iam.permissions`; there is no seeded role or mapping at all, so deny exists as mechanism with zero production instances. Writing one is exposed at POST/PATCH `/iam/roles/{roleId}/permissions` (`effect: z.enum(['allow','deny'])`, apps/api/src/app/api/v1/iam/roles/[roleId]/permissions/route.ts:27).

_Evidence:_ Column and CHECK: supabase/migrations/20260718091000_iam_roles_and_permissions.sql:126 `effect text NOT NULL DEFAULT 'allow'` and :139 `CONSTRAINT ck_role_permissions_effect CHECK (effect IN ('allow', 'deny'))`. Tenant-wide resolution: 20260718097000:114 `RETURN COALESCE(v_allow, false) AND NOT COALESCE(v_deny, false);`. Scoped resolution: 20260718097000:164-174 — `-- Deny is global: any deny mapping in an active granted role denies outright.` / `SELECT bool_or(rp.effect = 'deny') INTO v_deny FROM iam.role_grants g JOIN iam.role_permissions rp ON rp.tenant_id = g.tenant_id AND rp.role_id = g.role_id WHERE g.tenant_id = v_tenant AND g.user_id = v_user AND g.status = 'active' AND g.valid_from <= now() AND (g.valid_to IS NULL OR g.valid_to > now()) AND rp.permission_id = v_perm; IF COALESCE(v_deny, false) THEN RETURN false; END IF;`

### 3. Scopes — the grant_scopes vocabulary and how has_permission_in_scope resolves each

**EXISTS AND LOAD-BEARING.**

Four resolution facts. (i) `unrestricted` satisfies ANY target including an all-NULL one — that is exactly how `callerHoldsPermissionTenantWide` works (apps/api/src/server/auth/authorization.ts:215-224, calling `iam.has_permission_in_scope($1, NULL, NULL, NULL)`). (ii) The three arms are DISJUNCTIVE and each compares ONE column: a `branch` row matches on `s.branch_id = p_branch` alone and never re-checks the company; a `company` row matches on `s.company_id = p_company` alone. (iii) Because the comparison is `= p_company`, a company-scoped holder asked about a target that names only a branch (companyId undefined ⇒ NULL) resolves to NULL, not true, and is DENIED. Callers therefore must pass both ids; the module call sites do (`authorizeScope({ companyId: invoice.companyId, branchId: invoice.branchId })`, e.g. apps/api/src/modules/billing/application/invoice-service.ts:470). (iv) A scoped grant with no matching scope row simply does not apply — the `EXISTS` fails and the grant contributes nothing. A scoped ACTIVE grant is forced to own at least one scope row by a DEFERRABLE INITIALLY DEFERRED constraint trigger (20260718092000:165-213), and scope_mode is immutable so a grant can never be widened from scoped to unrestricted after creation (:100, :112).

_Evidence:_ Vocabulary: supabase/migrations/20260718092000_iam_role_grants_and_scopes.sql:141 `CONSTRAINT ck_grant_scopes_type CHECK (scope_type IN ('company', 'branch', 'department'))` and :142-146 `ck_grant_scopes_shape` (company ⇒ company_id only; branch ⇒ company_id+branch_id; department ⇒ all three — company_id is NOT NULL for all three). Grant-level switch: :68 `scope_mode text NOT NULL DEFAULT 'unrestricted'`, :88 `CHECK (scope_mode IN ('unrestricted','scoped'))`, immutable via :109-113. Resolution: 20260718097000:186-197 — `g.scope_mode = 'unrestricted' OR EXISTS (SELECT 1 FROM iam.grant_scopes s WHERE s.tenant_id = g.tenant_id AND s.grant_id = g.id AND ((s.scope_type = 'company' AND s.company_id = p_company) OR (s.scope_type = 'branch' AND s.branch_id = p_branch) OR (s.scope_type = 'department' AND s.department_id = p_department)))`

### 4. Grant validity — what makes a grant ACTIVE

**EXISTS AND LOAD-BEARING.**

A grant counts for a permission only when FIVE things hold simultaneously, all re-read on every call: the transaction context carries both `app.tenant_id` and `app.user_id` (unset ⇒ deny, and an unparsable UUID is caught by the `EXCEPTION WHEN invalid_text_representation` handler at :115-118 and denied, never raised); the user account is `status='active'` AND `deleted_at IS NULL` in that tenant; the grant row is `status='active'`; `valid_from <= now()`; and `valid_to` is NULL or strictly in the future. The window is half-open `[valid_from, valid_to)` — a grant whose `valid_to` equals `now()` is already dead. The same five-part predicate is repeated verbatim in `resolveScopeFor` (apps/api/src/server/context/resolve-context.ts:86-89), `heldScopesOfCaller` (apps/api/src/modules/iam/data/authorization-repository.ts:178-181), `countOtherHoldersOf` (:592-596), `callerApprovalCeiling` (apps/api/src/server/auth/authorization.ts:293-295) and the DB delegation backstop (20260727090000:144-147, :169-172) — six independent restatements of one rule, which is a drift surface worth naming in the RBAC document.

_Evidence:_ supabase/migrations/20260718097000_iam_context_and_permission_functions.sql:110-111 `WHERE g.tenant_id = v_tenant AND g.user_id = v_user AND g.status = 'active' AND g.valid_from <= now() AND (g.valid_to IS NULL OR g.valid_to > now())`; the account precondition at :91-97 `IF NOT EXISTS (SELECT 1 FROM iam.user_accounts WHERE id = v_user AND tenant_id = v_tenant AND status = 'active' AND deleted_at IS NULL) THEN RETURN false; END IF;`; the context precondition at :85-89 (`v_user`/`v_tenant` NULL ⇒ `RETURN false`); columns and CHECKs at 20260718092000:69-70, :89 `ck_role_grants_status CHECK (status IN ('active','revoked'))`, :90 `ck_role_grants_interval CHECK (valid_to IS NULL OR valid_to > valid_from)`

### 5. Revocation — how a grant ends, and whether ending is immediate

**EXISTS AND LOAD-BEARING.**

Three ways a grant stops conferring, in order of exposure. (a) REVOCATION — `DELETE /api/v1/iam/grants/{grantId}`, operation `iam.grant-revoke`, permission `iam.grant.manage`, version-guarded (apps/api/src/app/api/v1/iam/grants/[grantId]/route.ts:32-37). It is immediate: `iam.has_permission` is evaluated inside the request transaction on every call (apps/api/src/server/auth/authorization.ts:110-119) and nothing memoises the answer. (b) EXPIRY by `valid_to` — the column IS in the runtime UPDATE grant (20260726090000:156 `GRANT UPDATE (status, valid_to, revoked_at, revoke_reason)`), but NO service or HTTP operation ever writes it: `grep -n valid_to apps/api/src/modules/iam/data/authorization-repository.ts` shows only SELECT projections and the INSERT at :476. An end-date can be set at issue time (`issueGrant(... validTo ...)`, access-administration-service.ts:356) and never afterwards. (c) INDIRECT — suspending or soft-deleting the user account kills every permission at once via the account precondition (20260718097000:91-97). Physical deletion is impossible from the request path: no DELETE privilege and no DELETE policy exists on `iam.role_grants` (20260718092000:231-233 grants SELECT only; 20260726090000 adds only INSERT and column-scoped UPDATE). Two constraints on the revoke path itself: `assertNotSelf` refuses revoking your own access (delegation-policy.ts:110-116) and `assertNotLastHolder` refuses a revoke that would leave the tenant with nobody holding `iam.user.manage`, `iam.grant.manage` or `iam.role.manage` (access-administration-service.ts:479-483).

_Evidence:_ apps/api/src/modules/iam/data/authorization-repository.ts:498-514 — `UPDATE iam.role_grants SET status = 'revoked', revoked_at = now(), revoke_reason = $4 WHERE tenant_id = $1 AND id = $2 AND record_version = $3 AND status = 'active'`. Coherence CHECKs: supabase/migrations/20260718092000:91-94 `ck_role_grants_revoke_consistency CHECK ((status = 'revoked') = (revoked_at IS NOT NULL))` and `ck_role_grants_revoke_reason CHECK (revoked_at IS NULL OR btrim(COALESCE(revoke_reason,'')) <> '')`. Immediacy claim and its basis: apps/api/src/modules/iam/application/access-administration-service.ts:458-461 ('Effective immediately: `resolveScopeFor()` and `iam.has_permission` both read `status = 'active'` on every request, so nothing cached keeps it alive'), and `GET /auth/session` declares `cacheCategory: 'never'` (apps/api/src/app/api/v1/auth/session/route.ts:35).

### 6. Delegation — who may grant what, in the service and in two database backstops

**EXISTS AND LOAD-BEARING.**

The rule is 'you cannot delegate authority you do not possess', enforced at three layers. Permission delegability: an `allow` mapping, and a grant of a role conferring allows, both require the actor to hold every code CURRENTLY — the WITH CHECK re-evaluates `iam.has_permission` at write time, so self-escalation through a role you administer is refused by the database. Scope containment is hierarchical and asymmetric: company covers its branches and departments, branch covers its departments but NOT its company, department covers only itself (delegation-policy.ts:78-98 and the identical SQL at 20260727090000:160-190). A scoped actor may not issue an `unrestricted` grant at all (delegation-policy.ts:159-167; SQL :152-155). Three limits the document must record. (i) The RLS delegability policy calls the SCOPE-BLIND `iam.has_permission`, which is stated in the migration's own header at 20260727090000:22-27 — it proves the actor holds the codes SOMEWHERE in the tenant, never that they may delegate them here; that gap is exactly why the deferred backstop exists. (ii) The backstop is VACUOUS for a caller with no acting principal: 20260727090000:124-126 `IF v_actor IS NULL THEN RETURN true;` — deliberate, to preserve the `org.provision_organization` bootstrap path, and it also returns true for any superuser/BYPASSRLS role and any role that is not a member of `app_runtime` (:108-116). (iii) `actorUnrestricted` at the application layer is NOT 'holds an unrestricted grant' — access-administration-service.ts:789 computes it as `context.companyIds.length === 0 && context.branchIds.length === 0`, i.e. 'the request context carries no narrowing'. That coincides with the DB definition today only because `resolveScopeFor` returns empty arrays when `bool_or(g.scope_mode='unrestricted')` is true (resolve-context.ts:94-102) AND because no route ever supplies `requestedScope` (grep across apps/api/src/app and apps/api/src/modules returns zero call sites). A caller with ZERO active grants also gets empty arrays and would be classed unrestricted here — unreachable in practice only because such a caller holds no permission and fails the operation gate first.

_Evidence:_ Application: apps/api/src/modules/iam/domain/delegation-policy.ts:126-141 (assertDelegable), :159-167 (assertUnrestrictedDelegationAllowed), :78-98 + :189-200 (scopeCovers / assertScopeWithinAuthority), :110-116 (assertNotSelf), :234-240 (assertNotSystemRole), :255-263 (assertNotLastHolder); orchestrated at apps/api/src/modules/iam/application/access-administration-service.ts:368-407. RLS: supabase/migrations/20260726090000_iam_org_runtime_administration_capabilities.sql:370-384 `ins_role_grants_delegable` — `... AND iam.has_permission('iam.grant.manage') AND NOT EXISTS (SELECT 1 FROM iam.role_permissions rp JOIN iam.permissions p ON p.id = rp.permission_id WHERE rp.tenant_id = role_grants.tenant_id AND rp.role_id = role_grants.role_id AND rp.effect = 'allow' AND NOT iam.has_permission(p.permission_code))`; and :299-316 `ins_role_permissions_delegable`. Deferred backstop: supabase/migrations/20260727090000_iam_grant_delegation_scope_backstop.sql:86-192 (`iam.grant_delegation_within_authority`) attached at :248-256.

### 7. Overrides — there is no per-user permission override; role grants are the only path

**MISSING.**

There is no user→permission table, no user-level allow, and no user-level deny anywhere in the 17 iam tables. Every capability a principal has reaches them through `iam.role_grants` → `iam.roles` → `iam.role_permissions`. The single per-user override that exists is MONETARY, not capability-based: an `iam.approval_limits` row addressed to a `user_id` sets that person's approval ceiling for one `limit_type` in one company, and it beats any role-derived ceiling (`ORDER BY (al.user_id IS NOT NULL) DESC`, apps/api/src/server/auth/authorization.ts:304). `callerApprovalCeiling` returns null for 'no ceiling', and its docblock at :273-274 warns callers must treat null as no authority and never as unlimited. Consequence for the RBAC document: any requirement of the form 'this one person may additionally do X' has no representation today other than minting a role for them — and `uq_roles_tenant_code_active` (20260718091000:107-108) makes that a first-class tenant role visible in every role list.

_Evidence:_ `iam.role_permissions` is keyed on (tenant_id, role_id, permission_id) with no user column: supabase/migrations/20260718091000_iam_roles_and_permissions.sql:121-140. `iam.sensitive_data_permissions` is likewise role-keyed: 20260718093000_iam_approval_and_sensitive_data.sql:109-113 (`role_id uuid NOT NULL`, no user_id) with `:139-141` stating 'Access is by permission, never by role name.' The ONLY user-addressed authority row in the schema is 20260718093000:49-50 + :72 — `role_id uuid NULL, user_id uuid NULL` under `CONSTRAINT ck_approval_limits_one_subject CHECK (num_nonnulls(role_id, user_id) = 1)`.

### 8. Company Owner constraints — what limits a tenant administrator today

**EXISTS AND LOAD-BEARING.**

A tenant administrator today is limited by: they cannot invent a permission code (catalogue is platform reference data, readable by all, writable by none); cannot modify or grant-map an `is_system` role; cannot grant or revoke their own access; cannot delegate a permission they do not currently hold, nor a scope they do not cover; cannot leave the tenant with zero holders of `iam.user.manage` / `iam.grant.manage` / `iam.role.manage`; cannot create or delete a tenant, and can edit only three columns of their own tenant row; cannot bootstrap the FIRST administrator of a tenant (with no accounts nobody holds `iam.user.manage`, so `ins_user_accounts_admin` matches nothing). What does NOT limit them today, and matters for wave C: `org.company.manage` and `org.branch.manage` exist in the catalogue but have ZERO consumers in apps/api/src (measured: `grep -rl "'org.company.manage'" apps/api/src | wc -l` = 0, same for org.branch.manage), so there is no HTTP operation to create a company or a branch at all; and the RLS that would gate such a write is PERMISSION-BLIND — `ins_legal_companies_tenant` (20260717103000_org_companies_branches.sql:369-371) is `WITH CHECK (tenant_id = iam.current_tenant_id())` with no `iam.has_permission` at all, and `ins_branches_scope` (:389-395) checks only tenant + `allowed_company_ids()`.

### 11. Effective permissions for a caller — GET /auth/session, and it is SCOPE-BLIND

**AVAILABLE BUT NEEDS ADAPTER.**

This is the ONLY operation on develop that returns a caller's effective capabilities. What populates `permissions[]` is a full scan of the platform catalogue — 112 codes across 17 domains (`supabase/seeds/04_iam_permission_catalog.sql`, counted: org 9, iam 10, shared 6, crm 10, veh 7, apt 4, rec 12, wo 9, dia 4, tech 4, qms 5, svc 5, quo 3, inv 9, sal 10, wty 2, rpt 3) — with `iam.has_permission` evaluated once per code. `iam.permissions` is readable by every runtime session (`sel_permissions_all ... USING (true)`, 20260718091000:168-169), so the loop always sees all 112. It is SCOPE-BLIND by construction: `iam.has_permission` reads no scope, so the answer is 'the caller holds this code SOMEWHERE in the tenant'. For a branch-scoped operator the list is therefore strictly WIDER than what any scoped operation will actually allow, and it carries no information about WHERE. `companyIds`/`branchIds` ship alongside but are a flattened union that cannot express whether the caller holds a whole company or only a branch inside it — the granularity-preserving read exists (`heldScopesOfCaller`, authorization-repository.ts:159-186, returning scope_type + company/branch/department) but is used ONLY by `delegationFacts` (access-administration-service.ts:786-796) and is not published by any operation. The web consumes exactly this: apps/web/src/app/[locale]/(dashboard)/layout.tsx:43-50 passes `capabilities={{ permissions: session.permissions }}` into `AppShell`, and `hasPermission` (apps/web/src/lib/permissions.ts:41-50) is a plain `.includes()` with unknown ⇒ denied. There is no other effective-permissions endpoint: `GET /iam/users/{userId}` returns another user's GRANT ROWS (id, roleId, scopeMode, status, validFrom, validTo — apps/api/src/modules/iam/application/user-administration-service.ts:110-124), never their resolved permissions.

_Evidence:_ Operation: apps/api/src/app/api/v1/auth/session/route.ts:25-36 (`id: 'iam.auth-session'`, `GET /auth/session`, `permissions: ['iam.user.read']`, `scope: 'tenant'`, `cacheCategory: 'never'`). ### An ARCHIVED role still confers every permission it maps

**MISSING CONTRACT.**

So archiving a role blocks future grants and hides it from the active-code unique index (`uq_roles_tenant_code_active`, 20260718091000:107-108) but withdraws nothing from anyone who already holds it. An administrator who 'deletes' a role reasonably expects its holders to lose it; today they must revoke each outstanding grant individually. This is a semantic the RBAC effective-permission document has to state explicitly, because both plausible readings are defensible and the code implements only one.

_Evidence:_ `iam.has_permission` and `iam.has_permission_in_scope` join `iam.role_grants` directly to `iam.role_permissions` on `role_id` and NEVER touch `iam.roles` (supabase/migrations/20260718097000_iam_context_and_permission_functions.sql:106-112 and :180-183), so `iam.roles.deleted_at` (20260718091000:90) is not in the predicate. Archiving is a plain column write with no cascade: apps/api/src/modules/iam/application/access-administration-service.ts:155-199 calls `this.authorization.updateRole(..., { archive })`, appends the `iam.role.archived` audit record, and touches no grant. Issuing a NEW grant of an archived role IS refused (:176-181, 'An archived role cannot be granted').

### `countOtherHoldersOf` — the docblock claims FOR UPDATE; the SQL has none, and it ignores deny

**MISSING CONTRACT.**

Two defects in the last-administrator protection. (a) The concurrency claim is unimplemented: two simultaneous revocations can each see one remaining holder and both commit, locking the tenant out of `iam.user.manage`/`iam.grant.manage`/`iam.role.manage`. (b) The count filters `rp.effect = 'allow'` but never subtracts a DENY — a 'remaining holder' whose other active role carries a deny mapping for that code does not actually hold it (`iam.has_permission` would return false for them), so the protection can be satisfied by a holder who holds nothing. This is the repository's recorded dominant defect class: a docblock stating a rule the code does not implement.

_Evidence:_ Claim: apps/api/src/modules/iam/domain/delegation-policy.ts:246-251 — 'the count is read `FOR UPDATE` inside the same transaction as the revoke so two concurrent revocations cannot both see two remaining administrators and both proceed'; restated at apps/api/src/modules/iam/application/access-administration-service.ts:477-478 ('Counted `FOR UPDATE`'). Implementation: apps/api/src/modules/iam/data/authorization-repository.ts:581-598 — `SELECT count(DISTINCT g.user_id)::int AS holders FROM iam.role_grants g JOIN iam.role_permissions rp ON ... WHERE g.tenant_id = $1 AND p.permission_code = $2 AND g.user_id <> $3 AND g.status = 'active' AND g.valid_from <= now() AND (g.valid_to IS NULL OR g.valid_to > now()) AND u.status = 'active' AND u.deleted_at IS NULL` — no `FOR UPDATE`, and an aggregate `count()` could not carry one in PostgreSQL anyway.

### Runtime write capability on the IAM tables — the double block, and what was opened

**EXISTS AND LOAD-BEARING.**

DELETE is granted on exactly two tables — `iam.role_permissions` and `iam.grant_scopes` (:149, :161) — because withdrawing a mapping and withdrawing a scope are genuine removals with no soft-delete column. Everything else in iam ends by `deleted_at` / `status` / `revoked_at` / `effective_to`. UPDATE is column-scoped everywhere it is granted, so an issued grant can be revoked or time-bounded but never re-pointed at another user or role (:152-156), and a user account can never be re-pointed at another external identity (:112-118). Session revocation is terminal by construction: both UPDATE policies carry `revoked_at IS NULL` in USING and deliberately omit it from WITH CHECK (:210-216, :222-232), so a revoked session cannot be resurrected by clearing the column — not by an administrator and not by its owner. The login-audit administrative arm is narrowed to `event_type = 'lockout'` (:254-262) so `iam.user.manage` cannot fabricate another principal's authentication history.

_Evidence:_ Baseline: supabase/migrations/20260718091000:181-184 and 20260718092000:231-233 grant SELECT only and state 'Deliberately ABSENT: INSERT/UPDATE/DELETE'. The opening: supabase/migrations/20260726090000_iam_org_runtime_administration_capabilities.sql:116-174 (privileges) and :184-426 (nineteen policies). Header at :12-20 explains the double block (FORCE RLS on all seventeen iam tables means a privilege alone still denies and a policy alone still denies) and records the measurement: 'DBCR-P1-14-001 measured the gap by executing every write P1-14 requires as `rootlco_test_runtime`: 22 of 24 probes failed with SQLSTATE 42501.'

implementation _slices_ (`wave-b-control-plane-design-v2.md:955-957`); they are the three surviving

dimension". Nothing in the canonical set disambiguates them. **This document always means the Wave B
slice**, and writes `dependencies.md` ids as `DEP-B1`..`DEP-B7` when it must refer to them.
Recorded as `AMB-03` and `AMB-13`.

**"Wave" also means two things.** `scope.md` §5 counts nine _delivery_ waves A..I;
`gap-register.md` §3 counts four _ownership lanes_ and calls them waves. Recorded as `AMB-38`.

### Wave B slice B2 — Company status history and its transition function

**Status: MISSING.** Evidence: wave-b-control-plane-design-v2.md:956 (slice row); §12.3 at :722-742; M3 at :840; §7.2 grant row at :480

**Canonical Name.** "B2 | Company status history and its transition function (§12.3) | Reviewable alone: Yes" (:956).

**Goal.** Close a real, symmetrical gap: tenant has a transition function and an append-only history, branch has both, and company has "a status column ... and **neither** — verified by enumerating every `org.` table and every `org.` function in the migration series" (:729-731). Independently corroborated at wave-a-discovery.md:330 ("no `org.change_company_status` function anywhere in the 124 migrations, no `org.company_status_history` table"; a company can only change status through a direct UPDATE under `upd_legal_companies_tenant`, unrecorded).

**Dependencies.** Not specified. §19 states an ordering constraint only for B4-before-B5 (:958). Its CONSUMER is stated: "The tenant-side operation that calls this function is wave C's" (:742), and §7.2 lists `org.change_company_status(...)` as needed "§12.3, for the wave C operation that calls it" (:480).

**Database Changes Expected.** Migration M3 (§15:840), additive only, numbered above 124. Two objects (:733-739): `org.company_status_history` — append-only, recording previous state, new state, actor, reason, moment, tenant and company, "modelled column-for-column on the branch history table"; and `org.change_company_status(...)` — row lock, transition-graph validation, status update and history append in one transaction, SECURITY INVOKER, **no actor parameter**. EXECUTE "created and revoked from public by M3" and granted to `app_platform` (:480).

**API Changes Expected.** NONE in wave B: "No route in wave B updates a company's status directly, and no operation exposes an arbitrary status write" (:741-742).

**Frontend Changes Expected.** None. "No web tier." (:965).

**Permission Changes Expected.** None for this slice. The catalogue movement in wave B is the three `platform.` codes of §4.2 (:192-196), which belong to B1/B4/B5/B6/B7, not to B2.

**Security Invariants.** No actor parameter, following `org.change_branch_status` rather than `org.change_tenant_status`, because "of the two existing shapes, only the branch one cannot be handed a forged actor" (§8 rule 3, :530-534; finding N-8, refutation register :345-357). SECURITY INVOKER — the design introduces no definer-rights function (§6.6:418-419). Transition-graph validation lives inside the function.

**Tests.** P-22 (§16:889): "A legal company transition, then an illegal one → Accepted, then refused; history appended in the first case only." P-21 is NOT this slice's — §17:918 moves it to wave C.

**Exit Gate.** Not specified per slice beyond "Reviewable alone: Yes" (:956). The governing gate is §21 (:986-1001).

### Wave B slice B3 — The platform request context and its two shapes

**Status: MISSING.** Evidence: wave-b-control-plane-design-v2.md:957 (slice row); §3 at :95-163; finding N-3 at wave-b-control-plane-refutation-register.md:263-276

**Canonical Name.** "B3 | The platform request context and its two shapes (§3) | Reviewable alone: Yes" (:957).

**Goal.** Give the request path a way to express a control-plane request. Today it cannot: `buildRequestContext` requires and validates BOTH a principal user and a principal tenant (apps/api/src/server/context/request-context.ts:88-93) and `applyContext` sets both database settings on every transaction (apps/api/src/server/db/transaction.ts:91-105) — finding N-3 (:140, register :263-276).

**Dependencies.** B1's `app_platform` role and `iam.has_platform_authority` resolver — both shapes "run as `app_platform`" (:155). Not otherwise ordered in §19.

**Database Changes Expected.** None attributable to this slice; the role, the relation and the resolver are B1 (§19:955) and the privilege graph is M2 (§15:839).

**API Changes Expected.** Two context shapes (:150-153). **Platform-origin** — provisioning only, tenant absent, acting principal set, narrowing lists absent. **Platform-on-target** — every other platform operation, tenant set to "the target tenant, positively, after §4 authorized that exact target", acting principal set, narrowing lists absent. Plus one addition to the request-context type: "a context whose tenant is legitimately absent. It is a distinct type, not an optional field on the existing one, so no tenant-path caller can be handed one by mistake" (:160-163). The request path is §3.2 (:117-127): authenticate → resolve platform authority from `iam.platform_grants` → establish the platform context → authorize exactly one platform operation → validate every target identifier → install the narrow database execution context → execute → audit.

**Frontend Changes Expected.** None.

**Permission Changes Expected.** None.

**Security Invariants.** (1) A platform principal is "**positively established** or it does not exist" — never inferred from an absent tenant, an absent narrowing list, an address, a stored browser value or anything the client can set (:99-102). (2) The two context readers are ASYMMETRIC and this is the whole reason the slice exists: an absent `iam.current_tenant_id()` DENIES, while an absent `iam.allowed_company_ids()`/`allowed_branch_ids()` means NO NARROWING, i.e. widens (:106-113, from 0002_base_schemas.sql:108-115, :128-141, :143-153). (3) The absent narrowing lists are safe "**only** because `app_platform` holds no grant on any tenant business table" (:157-158, §6.1:329-331). (4) Neither shape is `app_runtime`, "so no tenant policy admits either by accident" (:155). (5) Audit constrains the shapes: an audit event cannot be written outside a tenant context (N-6; writer refuses an absent tenant at 20260725090000:181-183; all three insert policies compare the row's tenant against the current one at :264-272).

**Tests.** P-8 (§16:875), two halves and the second is the load-bearing one: "Set both narrowing lists empty on a platform request, **then remove the positive tenant assignment** → First: no widened row set, and nothing in a tenant's business tables becomes readable. Second: the request **fails** rather than succeeding broadly — revision 1 dropped this half, and it is the only half that can fail."

**Exit Gate.** Not specified per slice beyond "Reviewable alone: Yes". Governing gate is §21.

### Wave B slice B4 — Organisation read contract (platform.organization-read)

**Status: MISSING.** Evidence: wave-b-control-plane-design-v2.md:958 (slice row); §6.5 at :399-414; §12.2 row at :709; §4.2 at :189

**Canonical Name.** "B4 | Organisation read contract (§12.2). **Creates the `app_platform` SELECT privilege and policy on `org.tenants`** that §6.4 depends on too, so it must land before B5 | Reviewable alone: Yes" (:958).

**Goal.** Publish the control-plane read: "Listing and reading tenants from the control plane" (:189). Justified as a distinct authority because "A read-only operator is a real need. Folding it into provisioning would force full creation authority on anyone who may look" (:189). §12.2:709 records why the existing read cannot be reused: `iam.tenant-settings-read` "returns the caller's own tenant. A control-plane read crosses the boundary the existing one is defined by." permission-reuse-register.md:253-258 states the same prohibition from the permission side — `org.tenant.read` "must not be reused for it".

**Dependencies.** B1 (role, relation, resolver) and B3 (context shapes — "Platform-origin for a list, platform-on-target for one tenant", :406). **B4 must land before B5** (:958).

**Database Changes Expected.** Part of M2 (§15:839). `GRANT SELECT ON org.tenants TO app_platform` plus a policy. §6.5 gives the read-only form: `FOR SELECT TO app_platform USING (iam.has_platform_authority('platform.organization.read'))` (:408). §6.4:386 gives the wider form B5 also needs, written out deliberately "because 'satisfiable by any platform authority' is not a predicate an implementer can copy": `USING (iam.has_platform_authority('platform.organization.read') OR ...lifecycle') OR ...provision'))`. No writes (:409).

**API Changes Expected.** One new operation, `platform.organization-read`, in a NEW `platform` module prefix (§12.2:709, :719 — "Three new operations, one new module prefix, and the prefix carries meaning: these are the only operations in the product that are not inside a tenant"). Declares `auth-adjacent` as its rate-limit policy (§10:637). Every address parameter and target identifier validated by the shared identifier rule before any context is installed (§11:668-674), using a validator matching request-context.ts:63 exactly (:676-680).

**Frontend Changes Expected.** None.

**Permission Changes Expected.** Seed `platform.organization.read` in the seeds bucket, `platform` domain (§4.2:192). The catalogue holds 112 codes across 17 prefixes today; "this change moves both, and the baseline pin at `.github/ci-baselines/schema-baseline.json:14` moves in the same commit" (:193-196). Post-change figures deliberately not stated (C11).

**Security Invariants.** Reads `org.tenants` and nothing beneath it: "A control-plane operator can see that a tenant exists and what state it is in; they cannot see its customers, its vehicles or its work" (:413-414). "A read is not audited; the rate limit and the denial path are its controls" (:410). A well-formed identifier naming something the operator may not reach produces the same non-disclosing refusal as a target that does not exist, "so the control plane does not become an oracle for which tenants exist" (:682-684). An operation may not mix `platform.` codes with tenant codes; an unrecognised authority kind is refused at registration (:216-218). The registry guard is untouched — an empty permission list never means platform authority (§4.1:168-178).

**Tests.** §16: P-1 (revoke the grant → refused), P-2/P-3/P-4/P-5 (each with a positive control), P-9/P-10 (rate limit), P-11 (malformed identifier → standard validation refusal, no database error), P-6/P-7/P-24 (privilege and policy mutations, asserted on message text not error class), P-29 (revoke EXECUTE on `iam.has_platform_authority` → every platform policy fails loudly rather than answering false).

**Exit Gate.** "Reviewable alone: Yes", plus the hard ordering constraint that it lands before B5. Governing gate is §21.

### Wave B slice B5 — Lifecycle contract (platform.organization.lifecycle)

**Status: MISSING.** Evidence: wave-b-control-plane-design-v2.md:959 (slice row); §6.4 at :379-397; M4 at :841; P-26/P-26b/P-26c/P-31/P-32 at :894-902

**Canonical Name.** "B5 | Lifecycle contract (§6.4) | Reviewable alone: Yes" (:959).

**Goal.** Suspend, reactivate and close a tenant (§4.2:190), kept separate from provisioning because it is "Destructive to a **live** tenant. Provisioning authority must not imply the power to suspend an existing customer" (:190). The transition function exists and is granted to no application role (§12.2:711).

**Dependencies.** B4 must land first, for the `org.tenants` SELECT privilege and policy (:958). M4 must be ordered BEFORE M2 (§15:841), "because M2 grants the privilege this trigger exists to bound and shipping the grant first leaves a window where the graph is unenforced."

**Database Changes Expected.** (a) EXECUTE on `org.change_tenant_status(...)`, granted to no application role today (:387, 20260717101000:232-235). (b) A MANDATORY read of `org.tenants` — the function is SECURITY INVOKER and its first statement is `SELECT status INTO v_from ... FOR UPDATE`, so the row lock runs with this role's privileges; this was "the third instance of the same class" (:385). (c) `GRANT UPDATE (status)` column-scoped (:389), noting the existing runtime grant "deliberately withholds `status`, so this is a new privilege and not a precedent for itself". (d) `GRANT INSERT ON org.tenant_status_history` — the SECOND write, which §6.2's policy cannot serve: plpgsql advances the command counter between the parent UPDATE (:219) and the child INSERT (:221-224), so the child policy reads the ALREADY-UPDATED parent, making §6.2's "parent tenant is in the provisioning state" false for every lifecycle transition; "Left as revision 3 had it, every transition fails `42501` and rolls the status change back with it" (:391). (e) TWO policies on two tables: on `org.tenants`, `USING (iam.has_platform_authority('platform.organization.lifecycle'))` plus a `WITH CHECK` restricting the destination to ('active','suspended','closed') — `provisioning` refused outright (:390); on `org.tenant_status_history`, its own `FOR INSERT ... WITH CHECK (iam.has_platform_authority('platform.organization.lifecycle') AND to_state IN ('active','suspended','closed'))` (:392). (f) Migration M4: a `BEFORE UPDATE` transition backstop on `org.tenants`, its own migration ordered before M2, firing only when `OLD.status IS DISTINCT FROM NEW.status` so the runtime's existing three-column settings update is untouched, validating against the same graph as `org.change_tenant_status` rather than a destination list (§15:841). (g) EXECUTE on `iam.current_user_id()` for `tg_tenants_touch_metadata` → `shared.touch_row_metadata` (:394, §7.2:475).

**API Changes Expected.** One operation, `platform.organization-lifecycle`, `platform` module (§12.2:711), platform-on-target context (:384), `auth-adjacent` rate limit. A TWO-STEP refusal shape: "§11 validates the identifier's **form**; the route must then **resolve** the target — confirm the tenant exists and the operator may reach it — and answer §11's non-disclosing refusal when it does not, so the function's `no_data_found` is never the response a caller sees. Revision 3 attributed both steps to §11" (:396). The function's actor parameter is NOT bound from the request (:395, §8).

**Frontend Changes Expected.** None.

**Permission Changes Expected.** Seed `platform.organization.lifecycle` (§4.2:190, :192).

**Security Invariants.** The `WITH CHECK` is a DESTINATION WHITELIST, not the graph — `closed → active` and `provisioning → suspended` both pass it, and "Only M4's trigger enforces the graph" (:1036-1038). A `FOR UPDATE` policy with only a `USING` clause reuses it as the check, which is how revision 1 admitted `status = 'provisioning'` (:390) — blocker B3. The bootstrap window "only closes if nothing can reopen it" (:377). A history row can never record a transition the parent's own check would have refused (:392).

**Tests.** §16: P-26 (control first — a legal transition succeeds; then set a live tenant back to `provisioning` → refused by the WITH CHECK, refused again by M4's trigger with the policy removed and the grant present, and a bootstrap write against that tenant still refused); P-26b (a transition the destination list admits but the graph forbids → refused BY M4's trigger, "which is the only thing that catches it"); P-26c (a settings-only update as `app_runtime` → succeeds; M4 must not fire when the status is unchanged); P-30 (call holding only the lifecycle code); P-31 (full transition end to end → BOTH writes commit; "Revision 3 would have failed this on the second write with `42501`"); P-32 (remove the history insert policy → the transition fails and the status change rolls back with it); plus P-6/P-7/P-24.

**Exit Gate.** "Reviewable alone: Yes". Governing gate is §21.

### Wave B slice B6 — The sanctioned path to the provisioning function

**Status: MISSING.** Evidence: wave-b-control-plane-design-v2.md:960 (slice row); §6.2 at :332-354; §9.1 at :542-563; P-27 at :897

**Canonical Name.** "B6 | The sanctioned path to the provisioning function (§6.2) | Reviewable alone: Yes" (:960).

**Goal.** Build the legitimate path to `org.provision_organization` — the first half of `platform.organization.provision`. "`org.provision_organization` is **not rebuilt, not copied, and not modified.** It already provides tenant, history, subscription, company, branch, settings, overrides, number sequences and replay protection in one transaction, rolling all of it back on any failure, and it is `SECURITY INVOKER`. Wave B builds the legitimate path to it and nothing more" (:351-354).

**Dependencies.** B1 (role, resolver), B3 (platform-origin context — tenant absent, acting principal set, :338), and the §7 audit privilege graph. Not otherwise ordered in §19.

**Database Changes Expected.** Part of M2. EXECUTE on `org.provision_organization(jsonb, text)`, currently revoked from public and granted to no application role (:339). Grants and policies for the TEN writes the function performs: `org.tenants`, `org.tenant_status_history`, `org.tenant_subscriptions`, `org.legal_companies`, `org.branches`, `org.company_settings`, `org.branch_settings`, `org.tenant_feature_overrides`, `shared.number_sequences`, `shared.idempotency_keys` (:340). Reads, stated explicitly rather than left to inference (:341, :345): `shared.idempotency_keys` for the replay check; `org.subscription_plans` for the plan lookup (a plain read — platform reference data with no tenant column); and all four `RETURNING` targets, "because `RETURNING` is evaluated against the SELECT policy" — `org.tenants`, `org.legal_companies`, `org.branches`, `org.tenant_subscriptions`, each under a FOR SELECT policy mirroring its insert predicate. "Revision 1 named two of the six." On `org.tenants` the insert check is `status = 'provisioning'` — "the platform role may only ever create a tenant in the provisioning state, never a live one" — and on every child table the check is that the parent tenant is in that state: this is the BOOTSTRAP WINDOW (:342). Activation is a separate, later act — §9.1. Revision 1 missed this entirely" (:344, :555-563). The provisioning audit event is written AFTER the function returns, inside the same transaction, with the new tenant installed as context — the platform-on-target shape entered mid-transaction, because no audit row can exist before the tenant does (:348).

**Permission Changes Expected.** Seed `platform.organization.provision` (§4.2:188) — shared with B7, because "These are one act. Splitting the authority would allow creating tenants nobody can use, or placing an Owner into a tenant the actor did not create."

Actor always server-derived; no control-plane route binds an actor from the request; "A request document carries **targets** ... and never authority" (§8:526-529). Activation is not part of provisioning (§9.1:555-563). Neither existing function is modified (§8 rule 4).

**Tests.** §16: P-13 (same key, same request → replayed, nothing created); P-14 (same key, different request → refused); P-15 (fail midway — control: the unmutated run commits all of it → no tenant, no Owner, no replay record); P-27 (pass `tenant.activate` through the adapter → the adapter refuses to forward it and the tenant stays in `provisioning`); P-12 (forged actor in the request document → the recorded actor is the authenticated operator and the forged value appears nowhere); P-20 (append an audit event as `app_platform`, then attempt to amend and delete → append succeeds and reads back, both amendments refused); P-6/P-7/P-24.

### Wave B slice B7 — First-Owner bootstrap (highest-risk slice)

**Status: MISSING.** Evidence: wave-b-control-plane-design-v2.md:961 (slice row); §6.3 at :356-377; §9 at :540-618; P-16/P-17/P-18/P-19 at :883-886

**Canonical Name.** "B7 | First-Owner bootstrap (§6.3, §9) | Reviewable alone: Yes — and it should be, it is the highest-risk slice" (:961).

**Goal.** Establish a new tenant's first Owner — the one thing no path in the product can do today. The codebase states the boundary in its own words: "No policy here can create the FIRST administrator of a tenant: with no user accounts, nobody holds `iam.user.manage`, so `ins_user_accounts_admin` matches nothing" (20260726090000:80-85, quoted at dependencies.md:397-399). It is the second half of `platform.organization.provision`.

**Dependencies.** B6 — the two halves commit together or not at all (§9.1:542-550). B1's resolver, because every policy calls `iam.has_platform_authority`. EXECUTE on `iam.grant_delegation_within_authority` (§9.3).

**Database Changes Expected.** Part of M2. Writes to SIX tables: `iam.user_accounts`, `iam.user_status_history`, `iam.roles`, `iam.role_permissions`, `iam.role_grants`, `iam.grant_scopes` — "Revision 3 argued in prose that the status-history table is a write of this slice and then left it out of this list" (:362). Policies predicated on BOTH the bootstrap window (target tenant in the provisioning state) AND `iam.has_platform_authority('platform.organization.provision')` (:363). READS that are "not optional" (:364): `iam.role_grants` and `iam.grant_scopes`, because `tg_role_grants_require_scope` reads `iam.role_grants` unconditionally as the writing role, "so a write-only grant aborts the bootstrap at commit"; and `iam.permissions`, because `role_permissions.permission_id` is a surrogate key, so mapping the Owner role to permission CODES means resolving each code to its row first — a plain read with no tenant term. TWO deferred constraint triggers fire on the grant write, not one: `tg_role_grants_require_scope` and the delegation backstop; "Revision 1 named only the second" (:365). The account is inserted `active` rather than taking the `invited` default, because an invited account resolves zero permissions "and would hand the Owner a tenant they cannot enter" (:366). EXECUTE on `iam.grant_delegation_within_authority(uuid)`, currently `app_runtime` only (§7.2:481).

**API Changes Expected.** The bootstrap adapter, running inside the provisioning transaction. The Owner's provider identity is established out of band before the transaction opens, "the pattern `scripts/dev/owner-acceptance/create-owner-account.mjs` already uses" (:366).

**Frontend Changes Expected.** None.

**Permission Changes Expected.** None beyond `platform.organization.provision` (§4.2:188).

**Security Invariants.** The containment is §9.2's FOUR conditions and explicitly NOT the delegation backstop: because `app_platform` is not an `app_runtime` member, the backstop's second early exit fires and it "**returns true unconditionally for it**. That is the function's own design ... But it means the backstop is **not** the platform path's containment ... Saying so is the difference between this pass and the last one" (:596-603). The four conditions (:574-583): reachable only by `app_platform`, which the request path never uses for a tenant session — and this holds "because the bootstrap policies are written `TO app_platform` and no ordinary session runs as that role — **not** because any policy refuses `app_runtime`. Policies are permissive and refuse nothing"; the policies require the platform authority; the policies require the provisioning state, a window that closes itself on the tenant's first legal transition; and a tenant actor, a Company Owner and `app_runtime` are all outside it. Normal tenant delegation is UNTOUCHED — `ins_role_permissions_delegable` and `ins_role_grants_delegable` keep their current text (:567-570). The window "closes on the tenant's first legal transition" with two exits, to `active` and to `closed` (:369-372).

**Tests.** §16 and §9.3, which requires a POSITIVE CONTROL FIRST — "Without it a red result proves only that something is broken" (:607-608). P-17 (remove the bootstrap-window predicate → bootstrap succeeds against a live tenant, "proving the window, not the backstop, is the containment"); P-18 (remove the backstop execute grant → fails with `insufficient_privilege` NAMING THE FUNCTION, asserted on message text, never on error class, because `42501` is raised by this trigger, by every row-level denial and by every missing grant alike); P-16 (bootstrap a second Owner into the same tenant → never a second conflicting Owner); P-19 (after bootstrap, delegate as a tenant administrator → unchanged behaviour, existing delegation tests still pass untouched); and a database-level proof of §9.2 condition 2, "because §4.3 refuses a missing platform authority in middleware before any statement runs — so a request-level test can never exercise it. Call the bootstrap writes directly as `app_platform` with no `iam.platform_grants` row and be refused" (:615-618).

**Exit Gate.** "Reviewable alone: Yes — and it should be, it is the highest-risk slice" (:961). Governing gate is §21.

### Wave B slice B9 — Published contract and security proofs

**Status: MISSING.** Evidence: wave-b-control-plane-design-v2.md:963 (slice row); §16 at :855-902; §10 at :644-654

**Canonical Name.** "B9 | Published contract and security proofs (§16) | Last" (:963). Note there is no B8: it is struck through in the table and "**moved to wave C** (§17): wave B introduces no operation a Company Owner can reach, so the slice and its proof would pass vacuously here" (:962).

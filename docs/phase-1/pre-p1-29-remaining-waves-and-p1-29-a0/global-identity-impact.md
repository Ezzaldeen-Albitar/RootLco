# Wave D — global identity and membership: impact analysis

**CURRENT:** `iam.user_accounts` is tenant-bound.
**TARGET:** GLOBAL IDENTITY → MEMBERSHIP(S) → TENANT / COMPANY → BRANCHES → ROLES / GRANTS.

**This document does not implement the migration and does not choose a remedy.** It measures the
blast radius, so that whoever does choose knows what they are choosing.

## The one sentence that frames it

One live external identity resolves to **exactly one tenant, platform-wide**, because
`uq_user_accounts_provider_identity_active` is unique on `(identity_provider, provider_subject)`
with **no tenant in the key** — and the login service depends on that shape by construction. The
initiative's own scope document records the remedy as explicitly unsettled and names three
candidates: change the key; introduce a separate identity record above the tenant-scoped account;
or add a membership table that spans them. **This document does not pick one.**

## Why "it is one index" understates it

The index is the _mechanism_. The _dependency surface_ is everything below. Each class was counted
rather than estimated, and where a count is disputed the measurement method is given.

### CURRENT STATE — identity is tenant-bound at the provider, not at the database

**EXISTS AND LOAD-BEARING.**

iam.user_accounts is one row per human PER TENANT: `tenant_id uuid NOT NULL` (:68), `uq_user_accounts_tenant_id UNIQUE (tenant_id, id)` (:83), `fk_user_accounts_tenant → org.tenants(id)` (:84-85). tenant_id is frozen by tg_user_accounts_immutable (:115-118), so an account can never be moved between tenants. The ACTIVE tenant of a request is decided outside the database: the provider JWT carries `app_metadata.tenant_id` (token-verifier.ts:186-191), written service-role-only at invite (supabase-provider.ts:357-361 — a second admin call, deliberately not `data`, because GoTrue routes `data` to user-editable user_metadata); bearer-authenticator.ts:82-90 REFUSES a token with no tenant binding (`if (!verified.tenantId) … return null`); resolveRequestContext then builds a bootstrap context carrying only that tenant (resolve-context.ts:259-264), blanks app.user_id (:273), and looks the account up by (identity_provider, provider_subject) with NO tenant predicate in the SQL (:61-70) — the tenant filter is RLS, not the query. The tenant then reaches SQL through set_config('app.tenant_id', …, true) (transaction.ts:93, :102-104). Exactly 6 operations are public (grep -rn "public: true" apps/api/src/app/api/v1 --include=route.ts → 6: auth/login, auth/logout, auth/password-reset, auth/password-reset/completion, health/live, health/ready); every other one of the 305 registered operations goes through resolveRequestContext and answers ERR-IAM-002 without an active account in the claimed tenant (route-handler.ts:300-312).

### TARGET STATE — GLOBAL IDENTITY → MEMBERSHIP(S) → TENANT/COMPANY → BRANCHES → ROLES/GRANTS

**MISSING.**

The authorized direction is recorded in three canonical places and is consistent across them: global identity → membership(s) → tenant/company → branches → roles and grants; ONE ACTIVE TENANT PER REQUEST IS RETAINED (P-3, scope.md:104-118); the difference is a CHOICE among memberships the server already established, made after authentication, never a tenant identifier the client names. ### GAP — what actually has to change, and where the 'single index' framing understates it

**MISSING.**

architecture-decisions.md:120-122 says the one-account-per-identity rule 'is a single index. That is the whole reason this remediation is tractable.' Measured, the index is necessary but nowhere near sufficient. Four blockers sit behind it, each measurable: (1) TOKEN SHAPE. The active tenant arrives as a single scalar JWT claim and a token without one is refused (bearer-authenticator.ts:82-90). A multi-membership identity either loses the claim (breaking every authenticated request) or keeps a stale one (which is then the membership choice, made by the provider). Nothing in the canonical documents addresses where the chosen membership is carried. (2) SESSION UNIQUENESS. `uq_user_sessions_session_ref UNIQUE (session_ref)` (20260718094000:117) plus `ON CONFLICT (session_ref) DO NOTHING` in insertSession (identity-repository.ts:398) means one provider session yields at most one iam.user_sessions row, in one tenant. A second membership under the same login would be silently dropped, not created — and `sel_user_sessions_own` requires `tenant_id = iam.current_tenant_id() AND user_id = iam.current_user_id()` (20260718094000:154-156), so the session row becomes unreadable the moment the active tenant changes, which resolveRequestContext:302-304 converts into 'Session is not active'. (3) FK SHAPE. All 14 inbound FKs are composite on tenant (see the FOREIGN KEYS item). (4) NO PLACE TO ASK. `iam.has_permission` and `iam.has_permission_in_scope` both begin by requiring an ACTIVE, non-deleted account in the CURRENT tenant (20260718097000:92-96 and :151-156). A pre-tenant membership list therefore cannot be permission-guarded by the existing model, and it cannot be answered from the database either, because sel_user_accounts_tenant needs a tenant and CI forbids SECURITY DEFINER (migration-replay-checks.mjs:221-225). This is the identical shape that forced a fourth database role in wave B.

### DEPENDENCY CLASS 2 — provider identity uniqueness, quoted exactly

**EXISTS AND LOAD-BEARING.**

The asymmetry is deliberate: the email index carries tenant_id, the identity index does not. THE AUTHENTICATION CODE THAT DEPENDS ON ITS SHAPE. (1) authentication-service.ts:326-337 — the resolveTenant docblock names the index and concludes "a verified subject resolves to exactly one account and therefore one tenant. The resolution is unambiguous by construction, not by convention." (2) resolveTenant itself, :338-356: `const bound = session ? session.tenantId : await this.directoryTenant(input.email)` (:342); a caller-supplied tenant that disagrees is refused (:348); where the identity carries NO provider binding the caller-asserted value is the fallback (:355) — that fallback is the only place a client-supplied tenant decides anything, and dependencies.md:355-359 records it as D7. (3) resolve-context.ts:61-72 — `SELECT id, tenant_id FROM iam.user_accounts WHERE identity_provider = $1 AND provider_subject = $2 AND status='active' AND deleted_at IS NULL LIMIT 1`, then returns `row.tenant_id` as the request's tenant. Under RLS the row is already narrowed to the claimed tenant, so today `LIMIT 1` is deterministic BECAUSE of the index; relax the index and `LIMIT 1` becomes an unordered pick within the claimed tenant only — which is safe by RLS but silently makes the resolver's authority the JWT claim alone. (4) The login flow re-checks the binding: `if (session.tenantId !== null && session.tenantId !== account.tenantId) … 'tenant-binding-mismatch'` (authentication-service.ts:248-251). (5) identity-provider.ts:165-179 documents the whole reason findByEmail exists on the port: iam.user_accounts cannot be a tenant-agnostic directory. NOTE: docs/phase-1/pre-p1-29-.../gap-register.md:82 cites the dependency as authentication-service.ts:326-331; the docblock actually spans :316-337 and the executing code :338-356.

### DEPENDENCY CLASS 4 — role grants and grant scopes: tenant-bound, and exactly how

**EXISTS AND LOAD-BEARING.**

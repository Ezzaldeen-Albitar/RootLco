Every gap found during preparation, classified, with the evidence that
establishes it. **Read this before planning any slice.**

Nothing here is a prediction. Each row was verified against the tree at
`c081a019` or the live database, and where a lane's claim disagreed with the

## The three CRITICAL findings

### `INS-09` — diagnostics is unreachable: no templates, and no way to author one

**CRITICAL.** Blocks Owner requirements 9, 10 and 11.

`dia.inspection_templates`, `dia.template_versions` and `dia.template_items`
hold **zero rows**, and so does `dia.diagnostic_types`, which a template
requires NOT NULL. **No `INSERT` or `UPDATE` against any of the three template
tables exists anywhere in `apps/api/src`.** `POST /jobs/{jobId}/inspections`
requires a `templateVersionId` and accepts nothing else.

So **no diagnostic report can be created at all**. Diagnostics is not thin or
unpolished — it cannot be entered.

Be precise about what is absent: the **authoring** surface, not all HTTP
reachability. The read path ships — `dia.template_versions JOIN
`dia.inspection_templates`is read at`diagnostics-repository.ts:264-265`behind`dia.diagnostic-create`, and `dia.template_items`is read at six further
repository sites. And the **database layer is complete and guarded**:`draft → published → retired` (`dia.guard_template_version_publish`), items
frozen once a version leaves `draft` (`dia.guard_template_item_frozen`), and
`GRANT SELECT, INSERT, UPDATE … TO app_runtime`on all three tables.`BE-4` is
therefore routes, a service and permission codes — **no schema work**.

Compounding it: the permission catalogue has **no template-management code**
among its 112 shipping rows (the shared container shows 115 — three of those are
the unmerged PRE-P1-29 B1 branch’s, see `INS-42`), so even the Backend work
needs new permissions, not just new
routes.

**Options, and the recommendation, are in
[technician-and-diagnostics-design.md](technician-and-diagnostics-design.md)
B2.1.** Recommendation: **defer diagnostics out of the first P1-29 slice** and
scope template authoring as the Backend prerequisite (`BE-4`). Seeding a
"standard inspection" from the platform is not merely forbidden by the standing
no-fake-data policy — it is **not representable**:
`dia.inspection_templates.tenant_id` is `NOT NULL` with no `scope` column, so
every template belongs to exactly one tenant by design. (`dia.diagnostic_types`
**is** dual-scope, so a platform _type_ vocabulary is a legitimate seed and is
the first link in the chain.)

**Diagnostics stays in P1-29 and the phase is therefore not Frontend-only.**
[execution-decision.md](execution-decision.md) §1.1 settles it: the
recommendation above defers diagnostics out of the _first slice_, not out of
the phase, and P1-29 cannot be declared complete without the diagnostics
experience.

### `INS-04` — the user → technician mapping exists and no contract exposes it

**CRITICAL.** Blocks the technician persona; degrades Owner requirement 7.

**This entry previously read "nothing maps a signed-in user to their technician
profile". That was wrong at the data layer and is corrected here** — the
correction makes the fix smaller, not the finding weaker.

`tech.technician_profiles` **already carries the mapping**:
`user_id uuid NOT NULL`
(`supabase/migrations/20260722094000_tech_profiles_skills_certs.sql:42`) with
`fk_technician_profiles_user FOREIGN KEY (tenant_id, user_id) REFERENCES
iam.user_accounts (tenant_id, id)` (`:59-60`), a partial unique index
`uq_technician_profiles_active_user ON (tenant_id, user_id) WHERE deleted_at IS
NULL` (`:67-68`) guaranteeing **at most one live profile per user per tenant**,
and a covering index `ix_technician_profiles_user`. The repository already
selects it (`technician-catalog-repository.ts:177`, `:221`, mapped to `userId`
at `:186`, `:231`).

**Nothing consumes it.** A grep for `userId`/`user_id` across
`modules/technician/application/` is empty, and neither technician route file
mentions it. `GET /auth/session` returns
`{userId, tenantId, email, displayName, companyIds, branchIds, permissions[]}`
and **no `technicianProfileId`**. Exactly two published technician operations
exist, both `GET`, and `tech.technician-queue` takes the profile id as a **path
parameter** — i.e. from the client.

So `GET /technicians/{technicianProfileId}/queue` exists and **a technician
cannot reach their own queue** without being handed an id they have no
legitimate way to learn.

**No client-side workaround is legitimate.** Matching on `displayName` or an
email local-part is a correctness defect (names collide) and a privacy defect
(it enables profile enumeration — see
[security-threat-model.md](security-threat-model.md) T-11).

**Fix (`BE-2`):** add the profile reference to the session payload, or — better
— add `GET /technicians/me/queue`, which resolves the profile server-side from
`iam.current_user_id()` so there is nothing for a client to assert. Either is
small: the lookup is `WHERE tenant_id = $1 AND user_id = $2 AND deleted_at IS
NULL`, on an index that already exists, returning at most one row by
construction. **Containment is part of the requirement**: the resolution must be
bounded to the caller's own tenant and must not widen the branch scope they
already hold.

Until then, the interim form is **a supervisor navigating to a technician** —
`GET /technicians/available` for the branch, then that technician's queue. Note
what that does _not_ mean: a technician **selecting themselves** from the
availability list is the self-assertion case the prohibition covers, so the
interim form serves the _supervisor_ persona fully and the _technician_ persona
only through a supervisor. It is not a workaround for "My jobs"; there is none.

### `INS-10` — a work order has no customer

**CRITICAL.** Blocks Owner requirement 2. Confirms P1-27 finding `INT-036`.

**No customer column exists in any of the 44 tables.**
`WorkOrderDetail.workOrder` is `{id, companyId, branchId, receptionVisitId,
vehicleId, kind, state, partsForwardState, displayNumber, openedAt,
recordVersion}`.

The chain that exists is
`wo.work_orders → rec.reception_visits → rec.reception_party_roles →
crm.business_partners` — three joins, none exposed from the work-order side, and
none available as a filter on the board.

A client-side chain through `GET /receptions/{id}` and
`GET /appointments/{id}` is possible and **is not recommended**: two or three
extra round trips per work order (so it cannot feed a board column), it needs
`rec.reception.read` **and** `apt.appointment.read` on top of
`wo.work_order.read`, and it does not exist for walk-ins
(`appointment_id` XOR `walk_in_id`).

**Fix:** a customer projection on the work-order read. Small, Backend.

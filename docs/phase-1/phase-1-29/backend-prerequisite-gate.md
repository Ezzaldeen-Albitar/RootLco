# P1-29 — Backend Prerequisite Gate

**This document is a gate, not an implementation.** Nothing here authorises code.
It enumerates every Backend prerequisite the preparation slice discovered,
sized against the tree, so that the sequencing rule in
[execution-decision.md](execution-decision.md) §4 can be applied:

> **A Backend prerequisite precedes every frontend feature that consumes it.**

Eight prerequisites, `BE-1` … `BE-8`. Three of them close the phase's three
Critical findings. None of them is optional in the sense of "the phase can
close without it" — each is either closed, or the frontend capability that
depends on it is not delivered, and
[execution-decision.md](execution-decision.md) §3 governs what that means for
closure.

---

## 1. How to read an entry

Each prerequisite carries the same ten fields:

| field                  | meaning                                                                      |
| ---------------------- | ---------------------------------------------------------------------------- |
| **finding**            | the `INS-` id in [blocker-register.md](blocker-register.md)                  |
| **problem**            | what is wrong, in one sentence                                               |
| **severity**           | CRITICAL / HIGH / MEDIUM, on the register's scale                            |
| **evidence**           | the file, line or measurement that establishes it — never an inference       |
| **missing capability** | the exact thing that does not exist, distinguishing _schema_ from _contract_ |
| **affects**            | the P1-29 screens and actions that wait on it                                |
| **ownership**          | which phase or initiative should own the work                                |
| **depends on**         | what must land before it can                                                 |
| **minimal surface**    | the smallest change that closes it                                           |
| **acceptance proof**   | what would demonstrate closure — a measurement, not an opinion               |

**The `schema` / `contract` distinction is load-bearing throughout.** This
repository has repeatedly conflated "the database supports it" with "an
operation exposes it", and five of the eight prerequisites below are cases where
the database is complete and the contract is absent. Sizing them as schema work
would overstate every one of them.

## 5. BE-3 — customer projection on the work-order read

| field                  | value                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                         |
| ---------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **finding**            | `INS-10` (P1-27 `INT-036`)                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                    |
| **problem**            | A work order does not expose its customer, so the service advisor's core question — _whose car is this_ — has no answer on the work-order surface.                                                                                                                                                                                                                                                                                                                                                                                            |
| **severity**           | **CRITICAL**                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                  |
| **evidence**           | **No customer column exists in any of the 44 `wo`/`dia`/`tech`/`qms` tables.** `WorkOrderDetail.workOrder` is `{id, companyId, branchId, receptionVisitId, vehicleId, kind, state, partsForwardState, displayNumber, openedAt, recordVersion}`. The relationship exists only as a three-hop join: `wo.work_orders → rec.reception_visits → rec.reception_party_roles → crm.business_partners`.                                                                                                                                                |
| **missing capability** | **Contract only.** The data is reachable; no read exposes it from the work-order side, and `GET /work-orders` accepts no `customerId` filter.                                                                                                                                                                                                                                                                                                                                                                                                 |
| **affects**            | The board (a customer column, and search by customer — `INS-02`), the work-order detail header, the technician screen's context, and any printed job card.                                                                                                                                                                                                                                                                                                                                                                                    |
| **ownership**          | P1-29 Backend prerequisite slice (A0), reading across the `rec`/`crm` boundary through a sanctioned port rather than a raw join.                                                                                                                                                                                                                                                                                                                                                                                                              |
| **depends on**         | nothing                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                       |
| **minimal surface**    | A customer projection on `wo.work-order-detail`. **Do not chain it client-side**: that is two or three extra round trips per work order (so it cannot feed a board column), it requires `rec.reception.read` **and** `apt.appointment.read` on top of `wo.work_order.read`, and it does not exist for walk-ins (`appointment_id` XOR `walk_in_id`, `ck_reception_visits_one_origin`).                                                                                                                                                         |
|                        | Two constraints on the shape. First, **no permanent one-to-one ownership assumption**: `rec.reception_party_roles.relationship_role` distinguishes `service_requester`, `vehicle_owner` and others, and the party who brought the car is not necessarily the party who owns it. The projection must name the role it is reporting. Second, **vehicle history semantics must stay correct** — the customer on a work order is the customer _of that visit_, not the vehicle's current owner, and a later ownership change must not rewrite it. |
| **acceptance proof**   | The board and the detail show the customer for both an appointment-originated and a walk-in-originated work order, with no additional permission beyond `wo.work_order.read`, and a subsequent change of vehicle owner does not alter a closed work order's recorded customer.                                                                                                                                                                                                                                                                |

## 7. BE-5 — permission declaration ↔ catalogue parity gate

| field                                            | value                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                |
| ------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **finding**                                      | `INS-11`                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                             |
| **problem**                                      | An operation can declare a permission code that is not in the catalogue, and nothing catches it — while no RLS policy in this domain consults a permission code either, so there is no second line of defence.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                       |
| **severity**                                     | HIGH (security)                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                      |
| **evidence**                                     | `defineOperation` rejects an empty `permissions` array and nothing else; the registry's own test registers the fictitious code `a.b.c` and passes. The shipping catalogue is a **seed** — `supabase/seeds/04_iam_permission_catalog.sql:15` is the only `INSERT INTO iam.permissions` in the tree and no migration writes the table — carrying **112 tuples, 112 unique codes, 17 domain prefixes**, pinned by `.github/ci-baselines/schema-baseline.json:14` (`permissionCount: 112`).                                                                                                                                                                                                                                                              |
| **missing capability**                           | A CI gate. Nothing else about the system needs to change.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                            |
| **affects**                                      | Every P1-29 operation, and `BE-4` most of all, since it is the one prerequisite that adds codes.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                     |
| **ownership**                                    | P1-29 Backend prerequisite slice (A0), or repository tooling.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                        |
| **depends on**                                   | nothing. **It should be built first**, so it polices `BE-4`'s new codes as they are written.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                         |
| **minimal surface**                              | One script comparing the `permissions` arrays of every `defineOperation` against the seeded catalogue, failing on any declared code absent from it.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                  |
|                                                  | **It must parse, not grep.** Permission codes and **audit action** codes share the same three-segment dotted shape — `wo.work_order.transition` and `wo.work_order.state_changed` are indistinguishable to a regex — and a naive scan over source text produces a list dominated by audit actions. That is the same class of defect that has produced a false gate result in this repository seven times, and it is why the P1-28 gates were rebuilt on the TypeScript AST. The gate must read the `permissions` array of a parsed `defineOperation` call and nothing else.                                                                                                                                                                          |
| **the second direction, and why it is advisory** | The reverse check — a seeded code that no operation declares — currently finds **ten**: `iam.login.view_all`, `inv.item.manage`, `org.branch.manage`, `org.company.manage`, `org.department.manage`, `org.subscription.manage`, `rpt.report.configure`, `sal.reversal.approve`, `wo.work_order.create`, `wty.policy.manage`. Five of the `org` ones are already inventoried by PRE-P1-29 at `docs/phase-1/pre-p1-29-multi-tenant-admin-rbac-workflow/architecture-decisions.md:281`, and `wo.work_order.create` is P1-27 finding `WF-12`, already adjudicated by P1-19's pre-merge audit. **This direction should report, not fail** — an unconsumed code is a governance question, not a build break, and failing on it would block unrelated work. |
| **acceptance proof**                             | The gate fails on a deliberately misspelt code in a scratch declaration and passes on the tree as it stands — a red-proof, as this repository requires of every new guard.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                           |

## 11. The contract mirror inventory (`INS-01`)

`docs/api/openapi.v1.json` declares **zero** request bodies and **zero** typed
success schemas across 305 operations, and `apps/web` may not import `apps/api`
source (`apps/web/scripts/check-api-boundary.mjs:77`). So the payload contract
must be **mirrored** by hand. This section sizes that work, which no other
document in the set did.

### 11.1 What P1-28's mirror actually is, and what holds it true

Two layers, and **only one of them is gated**.

| layer                  | content                                                                                                                                                                                                                                                                             | what checks it            |
| ---------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------- |
| **1 — operation rows** | a frozen array of literals with exactly seven fields: `operationId`, `method`, `template` (path without the `/api/v1` prefix), `idempotent`, `versionGuarded`, `permission`, `auditClass` — e.g. `apps/web/src/features/appointments/appointments-contract.ts:74-92` and `:122-190` | **the gate**, plus a test |
| **2 — payload DTOs**   | `AppointmentDetail`, `ReceptionDetail`, … hand-transcribed from `apps/api` service source and cited in prose                                                                                                                                                                        | **nothing**               |

**Authority A of `scripts/ci/check-p1-28-adapter-reachability.mjs` is
one-directional id-set containment, computed by a regex over source text.** It
reads each mirror file as text, extracts ids with
`/^\s*operationId:\s*'([^']+)'/gm` (`:254-262`), and emits
`CONTRACT_MIRROR_MISSING` for any published `apt.*`/`rec.*` operation whose id
is absent (`:264-271`). It never opens a DTO and never checks a field.

The row **fields** are held by a test rather than the gate —
`apps/web/tests/appointments-contract.test.ts:87-121` checks
`method`/`template`/`idempotent`/`auditClass` against `PUBLISHED_OPERATIONS`,
and `x-required-permissions` plus the `IdempotencyKey`/`IfMatch` `$ref`
presence against `openapi.v1.json`, with completeness asserted in both
directions (`:123-134`).

**Nothing anywhere compares a payload DTO to `apps/api`.** A P1-29 mirror
inherits exactly that asymmetry, and
[test-and-acceptance-plan.md](test-and-acceptance-plan.md) §3 states the ceiling
rather than promising coverage it cannot deliver.

### 11.2 The size of the P1-29 mirror

Scope is the **58 published operations** (`wo.` 26, `dia.` 13, `qms.` 13,
`tech.` 6, from `docs/phase-1/phase-1-24/evidence/operation-register.json`). All
58 are already in the generated manifest
`apps/web/src/lib/api/idempotent-operations.ts`, and **zero have a mirror row
anywhere in `apps/web/src` today.**

|                                                            |                                                                                                                                                                                                         count |
| ---------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------: |
| operation rows to write                                    |                                                                                                                                                                                                        **58** |
| distinct **request** shapes                                |                                                                 **32** — 30 top-level bodies plus 2 nested-only elements. 34 of the 35 write operations carry a body; `tech.labor-session-stop` carries none. |
| distinct **response** shapes                               |                                                                                                                    **46** — 40 named exported types plus **6 anonymous inline envelopes** the API never named |
| top-level request bodies with a faithful exported API type | **4** — `RaiseRequestInput`, `ApprovalEvidenceInput`, `CreateReworkInput`, and `AssignInput` only behind a `Date` ↔ ISO adapter. **The other 26 exist only as an inline zod `const Body` in the route file.** |

The **named response types** to mirror:
`WorkOrderSummary`, `JobView`, `ReachableState`, `WorkOrderDetail`,
`TransitionResult`, `ClosureEligibility`, `ClosureBlocker`,
`OpenInventoryCommitments`, `WorkOrderHistoryEntry`, `WorkOrderHistoryView`,
`JobHistoryView`, `LineRow`, `AssignmentView`, `QueueEntry`,
`AdditionalWorkRequestView`, `AdditionalWorkDetailView`, `CustomerApprovalView`,
`ApprovalEvidenceView`, `DiagnosticReportView`, `DiagnosticReportDetail`,
`ItemResultRow`, `MeasurementRow`, `DtcRow`, `FindingRow`, `RecommendationRow`,
`EvidenceView`, `ReviewView`, `OutstandingItem`, `ReportHistoryEntry`,
`ReportHistoryView`, `QcRecordView`, `QcRecordDetail`, `QcCheckResultRow`,
`QcCheckRow`, `ReworkLinkView`, `ReworkCostRow`, `ReopenAttemptView`,
`LaborSessionView`, `EligibilityVerdict`, `EligibilityFinding`.

The **six anonymous envelopes** — responses with no named type on either side —
belong to `wo.job-reassignment`, `wo.additional-work-approval` (POST),
`qms.rework-create`, `qms.reopen-attempt`, `tech.technician-available` and
`tech.technician-queue`. Naming them frontend-side creates a type with no
counterpart in `apps/api`, which is the exact drift shape a mirror exists to
prevent — and nothing would catch it. **Prefer a Backend change exporting six
interfaces** over inventing six frontend names.

### 11.3 Three envelopes that must be imported, not re-declared

Already present in `apps/web`:

| envelope                       | location                                    |
| ------------------------------ | ------------------------------------------- |
| `CursorPage<T>`                | `apps/web/src/lib/api/read-operation.ts:69` |
| `ItemsOnly<T>`                 | `apps/web/src/lib/api/read-operation.ts:76` |
| `ProblemDetails` / `Violation` | `apps/web/src/lib/api/client.ts:90` / `:54` |

Re-declaring any of them would create a second definition of a settled shape.

### 11.4 Two open questions the implementing slice must answer first

1. **Does P1-29 extend the P1-28 gate, or add a sibling?** `MIRROR_FILES`
   (`check-p1-28-adapter-reachability.mjs:121-124`) and the `/^(apt|rec)\./`
   register filter (`:240`) are **hard-coded**, and the file's whole
   `PENDING_FRONTEND_ADAPTER` apparatus is bound to phase-1-28 artefacts.
   Generalising it changes a gate that **P1-28's seal depends on**; a sibling
   `check-p1-29-adapter-reachability.mjs` does not. The sibling is the safer
   default.
2. **One mirror file or four?** P1-28 used one per feature directory, but
   `QueueEntry` is declared in the work-order module and served by
   `tech.technician-queue`, `OpenInventoryCommitments` comes from
   `modules/inventory`, and `qms.reopen-attempt` declares the
   `wo.work_order.transition` permission — so a strict module-per-file split
   forces cross-feature imports, which the receptions contract docblock says a
   feature may never do (`INS-14`). Choose the layout **before** transcription.

## 12. What this gate does not do

- It does not authorise any of the work it describes.
- It does not schedule it. [execution-decision.md](execution-decision.md) §4
  fixes the order; which prerequisites are funded, and when, is the Owner's.
- It does not claim the eight are exhaustive of all Backend work P1-29 might
  want — only that they are what the preparation slice **found and verified**.
  [blocker-register.md](blocker-register.md) carries the full 49 findings; these
  eight are the subset that block a designed capability.
- **It does not promise CI coverage of payload drift.** Section 11.1 states
  plainly that no gate in this repository compares a payload to the Backend. The
  only thing that tests a mirror against the API is a real response.

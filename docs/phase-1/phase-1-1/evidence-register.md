## Purpose

This register maps every material claim made in the Phase 1-1 documentation set to the evidence that supports it. No claim in this register is asserted without a corresponding observation. Where a claim cannot be evidenced, that absence is recorded honestly rather than papered over.

## Evidence types and where evidence lives

Two distinct classes of evidence appear in this register, and the distinction matters for auditability:

1. **Transcript-recorded command output.** Commands were executed on 2026-07-16 and their real output (including exit codes) was recorded in the working-session transcript. This evidence is reproducible by re-running the stated command but is not itself a committed artefact. Rows citing "Session transcript" are of this class.
2. **Committed files.** Configuration, scripts, and source files committed on the working branch `chore/p1-01-development-readiness`. These are inspectable directly in the repository. Rows citing a repository path are of this class.

Many rows cite both: the committed file defines the behaviour and the transcript records the measured proof that the behaviour holds.

Evidence type values used below: **command output** (a command was run and its output recorded), **running container** (the observation was made against a live container, not merely an image), **file** (a committed repository file), **measured metric** (a number that was measured, not estimated).

## Honesty notes

- Every command output, exit code, HTTP status, byte count, and timing in this register was actually observed on 2026-07-16. Nothing has been extrapolated or estimated, with one flagged exception: host RAM is stated as "approximately 16.5 GB" and hot reload as "approximately 6 seconds", both being real measurements reported at the precision they were taken.
- Transcript-recorded evidence (rows citing "Session transcript") is not a committed artefact. If durable proof is required for an entry criterion, the stated command should be re-run and its output captured into the repository or the canonical documentation set.
- Container-based evidence (rows marked "running container") was gathered from live, running containers — image existence alone was never treated as proof of behaviour.
- Docker is not claimed to improve performance automatically; Windows bind mounts are slower, and the named volumes exist precisely to keep container development acceptable (E-018, E-022, E-024–E-026).
- Technical tests were executed by Eng. Ezzaldeen Al-Bitar; independent QA ownership is not yet assigned and is recorded as a risk/conditional-gate item in `docs/phase-1/phase-1-1/qa-readiness.md`. A named security reviewer, exception authority, and incident contact are likewise not yet evidenced (P1-01-SEC-003; P1-EC-016 blocking candidate) — Eng. Ezzaldeen Al-Bitar is the security implementation owner, which is not the same as an independent reviewer.
- Only the Local environment is implemented; Development, Staging, and Production remain "Planned — not provisioned" (see `docs/phase-1/phase-1-1/environment-matrix.md`).

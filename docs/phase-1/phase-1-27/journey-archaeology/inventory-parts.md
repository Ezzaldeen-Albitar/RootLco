# P1-27 journey archaeology — Inventory parts (issue, consumption and return)

**Classification:** Confidential — Commercial Product and Pilot Planning ·
**Read at:** `develop` `a56eeea0a10d56cd17827ec443dd5ecff40f8c0d`

## Verdict

The inventory contract can support the **stock half** of the workshop parts
journey today and cannot support the **traceability half**. Fourteen inventory
operations exist and every one of them is registered by a route module, backed by
a service and a repository, and present in `docs/api/openapi.v1.json`. A part is
issued by `POST /stock-issues`, whose body carries `workOrderId` (required),
`itemId`, `locationId`, `quantity` and optionally `reservationId` and
`requiredPartRef`. It carries **no vehicle id and no technician id**, and no read
in this domain returns either — the actor recorded on `inv.part_issues.created_by`
and `inv.stock_movements.actor_id` is the authenticated caller taken from the
request context, and neither column is exposed by any endpoint. An unused part is
reversed by `POST /stock-returns`, addressed by `partIssueId` and nothing else, so
"return another work order's issue" is unrepresentable rather than merely refused.
Movement provenance is a database trigger, `inv.guard_stock_movement_provenance`,
and it is the trust root: no ledger row can exist unless a business row of the
matching kind, item, location and **exact** quantity already exists, which is why
the API has no "set stock level" endpoint and why an issue is always exactly one
`out` movement of exactly the issued quantity.

What §14 asks for and the contract does not carry: there is **no read that lists
the parts issued against one work order as issues**. The closest thing is
`GET /stock-movements?companyId&branchId&workOrderId`, which returns _movements_
correlated through `inv.part_issues` and `inv.part_returns` by two `EXISTS`
sub-queries — usable, but it returns no work-order id per row, no actor, no cost,
and, critically, a `part_return` row's `reference.id` is the **return** id, not
the issue it reverses, so a client cannot attribute a return to an issue and
therefore cannot compute the remaining returnable quantity of any issue (see the
`readPartIssue` note under operation 7). There is
also **no read at all** for stock locations, reservations, damaged stock,
customer-supplied parts, external-purchase parts or opening batches, and no
single-item read — so a parts screen has no way to populate the `locationId` it is
required to send. Money in this domain is `numeric(18,4)` plus an ISO-4217 code
and is write-only: `unitCost` can be written on an external purchase and is never
echoed back (`costRecorded: boolean`), and `inv.item_cost_details.standard_cost` is
touched by no route whatsoever. A "what did these parts cost this work order"
figure is not obtainable from this API.

**How the `workOrderId` filter actually works** (`InventoryRepository.listMovements`,
`apps/api/src/modules/inventory/data/inventory-repository.ts:1330`): there is no
`work_order_id` column on `inv.stock_movements`, so the filter is two `EXISTS`
clauses — `reference_kind = 'part_issue'` joined to `inv.part_issues.work_order_id`,
or `reference_kind = 'part_return'` joined through `inv.part_returns.part_issue_id`
to `inv.part_issues.work_order_id`. Consequences a screen must respect:

- `damage`, `adjustment` and `opening` movements are **excluded** by this filter,
  by construction. A work-order parts view built on it shows issues and returns only.
- For a `part_issue` row, `reference.id` **is** the `partIssueId` that
  `POST /stock-returns` wants. That link is real and usable.
- For a `part_return` row, `reference.id` is the **return** id. Nothing in the API
  maps a return back to its issue, so per-issue "already returned" and "remaining
  returnable" cannot be computed by a client. `InventoryRepository.readPartIssue`
  (`inventory-repository.ts:882`) does compute `returnedQty`, and it is a `public`
  method, but it is **not exported from the module surface** (`index.ts` re-exports
  nine repository row types and `PartIssueRow` is not among them) and the only route
  that reaches it is `POST /stock-returns`, which calls it as a precondition check.
  Its `returnedQty` therefore reaches a client only folded into `ReturnView`
  (`totalReturned` / `issuedQuantity`) **after** a return has actually been
  performed. There is no read path to it.

## Movement provenance — what the trust root actually constrains

`inv.guard_stock_movement_provenance` (`supabase/migrations/20260723095000_inv_operations.sql:592`,
`BEFORE INSERT ON inv.stock_movements`) is described by this module as the trust
root. Read literally, it constrains five things and nothing else:

1. **A movement cannot exist without a business row.** For each
   `reference_kind` it looks up the source row by `(tenant_id, reference_id,
item_id, location_id)` and raises `foreign_key_violation` when not found. Two
   kinds resolve those last two columns indirectly and the exact SQL matters: a
   `part_return` is joined to its parent `inv.part_issues` row and matched on the
   **issue's** `item_id`/`location_id`, and a `damage` row is matched on
   `item_id` plus `from_location_id` **OR** `quarantine_location_id`, which is how
   one damage record legitimately anchors both of its legs. So a
   ledger row can never be minted directly — every `out` traces to an
   `inv.part_issues` row, every `in` to a `part_return`, `opening_line`, approved
   `adjustment`, or the quarantine leg of a `damaged_stock` row.
2. **The quantity must match the source EXACTLY** (`NEW.quantity <> v_qty` raises
   `check_violation`). A part issue therefore moves exactly the issued quantity —
   partial-issue movements are unrepresentable.
3. **The type and direction must match the kind.** `opening`/`in`,
   `issue`/`out`, `return`/`in`, `damage`/either, `adjustment`/the approved
   direction. This is transcribed into `MOVEMENT_REFERENCE_MATRIX` in
   `apps/api/src/modules/inventory/domain/inventory.ts` and asserted before the
   call so a bad triple gets a readable refusal.
4. **Approval gates.** An `opening_line` movement is refused unless its batch is
   `approved`; an `adjustment` movement is refused unless the adjustment is
   `approved`. This is why the only path from nothing to stock runs through a
   maker-checker approval.
5. **Single use.** `uq_stock_movements_source` is `UNIQUE (reference_kind,
reference_id, direction)` — one movement per source per direction, which is
   why damage is the one kind that legitimately produces two rows.

Alongside it, `inv.guard_stock_balance_coherence` (`…094000_inv_ledger.sql:133`)
rejects any `inv.stock_balances` write where `on_hand_qty <> Σ signed_qty` or
`reserved_qty <> Σ active reservations`. Together these mean **there is no "set
stock level" endpoint and none can be added** without a migration: stock without a
movement behind it cannot be stored. For the frontend the consequence is concrete —
corrections are new movements, never edits, and any screen offering "adjust this
figure" has no operation to call (see the ABSENT table below).

The `Quantity` value object (`apps/api/src/modules/inventory/domain/inventory.ts`)
holds scaled `BigInt` thousandths, has **no `toNumber()`**, and refuses scientific
notation, a leading `+`, `NaN` and `Infinity`. `QUANTITY_MIN = '0.001'`,
`QUANTITY_MAX = '999999999.999'`.

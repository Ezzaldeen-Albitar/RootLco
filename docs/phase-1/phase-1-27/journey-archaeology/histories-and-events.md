# P1-27 journey archaeology — the three histories, and the event substrate

**Classification:** Confidential — Commercial Product and Pilot Planning ·
**Read at:** `develop` `a56eeea0a10d56cd17827ec443dd5ecff40f8c0d`

## Verdict

Exactly **one** of the three histories the journey needs is a unified stream, and
it is the Customer one: `crm.timeline_events` is a real emitting ledger, written
by six `AFTER INSERT` triggers in the same transaction as the change they
describe, and `GET /api/v1/customers/{customerId}/timeline` publishes it
keyset-paginated. Its `event_type` CHECK admits eight values, of which **two can
never be produced by this platform today** — `communication_logged`, because no
route or repository writes `crm.communication_log` anywhere in `apps/api`, and
`commercial_changed`, because the only writer of `crm.partner_status_history`
hard-codes `status_kind = 'lifecycle'`. The Vehicle history is **sectioned, not
unified**: `veh.vehicle_attribute_history` is a field-level change ledger over
eleven master columns of `veh.vehicles` and nothing else, and the `veh` schema
has no timeline table — a vehicle stream can only be assembled from five
separately-ordered published sections (attribute changes, plates, ownerships,
odometer readings, relationships), each with its own cursor contract key. The
Work Order history is also **sectioned**: `wo.work-order-history` returns the
work order's own status ledger plus a synthesised `origin` block, and jobs,
diagnostics, labour, parts, additional work, QC and rework each have a separate
read hanging off a different identifier. There is **no cross-entity unified
stream anywhere**: the only cross-domain chronological read on the whole 243-
operation surface is `iam.audit-event-list`, which is gated on `iam.audit.view`,
requires a mandatory `from`/`to` window of at most 92 days, and **audits every
read of itself** — so it is an audit tool, not a customer-facing timeline, and
using it as one would write a security-class audit record every time an operator
opened a screen. `shared.event_outbox` is written by **55 `publishEvent` call
sites across 33 module services** and has **no HTTP read of any kind**; the only
reader in the repository is the worker
(`apps/api/src/server/worker/outbox-worker.ts`), which connects as `app_worker`.
Of the **28 history/event tables in the schema, 10 are reachable over HTTP and 18
are not**, including `veh.vehicle_status_history` — the typed status ledger
written for every vehicle status change, which no operation reads.

---

## Operations that exist

Twelve operations. Every one below was verified by opening its route module, its
application service, its repository, and its entry in `docs/api/openapi.v1.json`.
Every permission code was read from the route's `defineOperation` registration
and confirmed present in `supabase/seeds/04_iam_permission_catalog.sql` at the
line cited.

A note that applies to all twelve: **the OpenAPI document is thin**. Every entry
declares `parameters: [ { $ref: CorrelationId } ]` only — no path parameter, no
`cursor`, no `limit` — and a `200` response schema of bare `{"type": "object"}`.
The `x-required-permissions`, `x-scope`, `x-audit-class`, `x-rate-limit-policy`
and `x-cache-category` extensions are accurate and are the only load-bearing part
of the published document. This is the open finding `P1-27-INT-004`
(`docs/phase-1/phase-1-27/findings.md:144`). **Do not derive a request or
response shape from `openapi.v1.json` for any of these operations.**

### `veh.vehicle_attribute_history` — confirmed: master fields only

`supabase/migrations/20260720095000_veh_vehicle_attribute_history.sql`.

Columns: `id`, `tenant_id`, `vehicle_id`, `field_code`, `old_value`, `new_value`,
`correlation_id`, `actor_id`, `occurred_at`, `seq`. Only CHECK is
`ck_vehicle_attribute_history_field_not_blank`.

Rows are written **only** by `veh.emit_vehicle_attribute_history()`, an
`AFTER UPDATE` trigger on `veh.vehicles` (`tg_vehicles_attribute_history`), one
row per changed tracked column, in the same transaction. A no-op update writes
nothing. The trigger tests exactly eleven columns with `IS DISTINCT FROM`:

`vin_normalized` · `make_id` · `model_id` · `trim_id` · `model_year` ·
`body_type_id` · `powertrain_type_id` · `powertrain_category` · `color` ·
`lifecycle_status` · `workshop_status`

`field_code` can therefore only ever be one of those eleven strings. It contains
**no visit, no repair, no job, no part, no invoice, no photograph, and no person
other than the actor who made the edit**. No restricted identifier can appear:
restricted identifiers live in `veh.vehicle_identifiers` and are not master
columns.

`42501`. `tg_vehicle_attribute_history_stamp` (BEFORE INSERT,
`shared.stamp_status_history`) server-stamps `actor_id` and `occurred_at` — and
**raises `check_violation` if the session has no actor**, so a history row cannot
be written without attribution.

### Is there a work-order history operation, and what does it contain?

Yes — `wo.work-order-history`, above. Exactly:

- **`origin`** — `openedAt` and `openedBy` read from `wo.work_orders` columns,
  and `initialState` read from the oldest ledger row's `from_state`. This block
  exists because `wo.emit_work_order_status_history` is `AFTER UPDATE` only, so
  the insert that opens an order emits no ledger row. A backfilled genesis row was
  rejected as worse than an omitted one: `shared.stamp_status_history` forces
  `occurred_at := now()`, so the fabricated row would claim the order opened at
  the moment of the backfill.
- **`transitions`** — one keyset page of `wo.work_order_status_history`:
  `{ id, fromState, toState, reason, occurredAt, actorId }` per row.

Table columns (`supabase/migrations/20260722096000_wo_status_history.sql:27`):
`id`, `tenant_id`, `company_id`, `branch_id`, `work_order_id`, `from_state`,
`to_state`, `reason`, `correlation_id`, `actor_id`, `occurred_at`, `seq`.
Constraints: `ck_work_order_status_history_state_change`
(`from_state IS DISTINCT FROM to_state` — a no-op cannot be recorded),
`ck_work_order_status_history_to_format` and `..._from_format`
(`^[a-z][a-z0-9_]{1,62}$`), `ck_work_order_status_history_reason_not_blank`.
**There is no closed enum of states in this table** — the state vocabulary lives
in the `wo.work_order_states` catalogue, which a tenant may extend, so a screen
must render the state code and its catalogue name rather than a hard-coded list.

What it does **not** contain: jobs, labour, parts, additional work, diagnostics,
QC, rework, quotations, invoices, deliveries or warranties. Each of those has its
own operation keyed on its own identifier.

## Unified or sectioned — the honest conclusion for each of the three histories

| history        | verdict                                                                                                                                                                                                                                              | the sections                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                     |
| -------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Customer**   | **UNIFIED stream available** — `crm.customer-timeline`, keyset-paginated, newest first — **plus** a second, differently-shaped, unpaginated `crm.customer-history` projection over four tables. Two overlapping reads of the same underlying events. | The unified stream's own sections (by `event_type`): lifecycle change · consent change · block · unblock · alert raised · merge. Two further declared types (`commercial_changed`, `communication_logged`) are unreachable. The parallel `crm.customer-history` projects `status` · `consent` · `block` · `merge` — **it omits alerts, which the timeline carries**, and the timeline omits the merge _summary_, which the history composes.                                                                                                                                                                                                                     |
| **Vehicle**    | **SECTIONED only.** There is no `veh` timeline table and no emitting ledger; `veh.vehicle-history` is a field-level change log over eleven master columns.                                                                                           | Five published, vehicle-id-addressable sections: (1) master attribute changes — `veh.vehicle-history`, ordered `veh.vehicle_attribute_history:occurred_desc`; (2) plates — `veh.vehicle-plate-history`, ordered `veh.plate_history:created_at_desc`; (3) ownerships — `veh.vehicle-ownership-history`, ordered `veh.ownership_history:created_at_desc`; (4) odometer — `veh.vehicle-odometer-history`, ordered `veh.odometer_readings:observed_desc`; (5) relationships — `veh.vehicle-relationship-list`. A sixth ledger, `veh.vehicle_status_history` (typed, with `status_kind`, a coherence guard and `seq`), is written by trigger and **read by nothing**. |
| **Work Order** | **SECTIONED only.** `wo.work-order-history` is the order's own status ledger plus a synthesised origin; everything else is a separate read on a separate identifier.                                                                                 | Sections addressable from a work-order id: status transitions (`wo.work-order-history`) · jobs (`wo.work-order-detail`) · additional work (`wo.additional-work-list`) · required parts (`wo.required-part-list`) · service lines (`wo.service-line-list`) · QC (`qms.qc-record-list`) · rework (`qms.rework-list`) · stock movements (`inv.stock-movement-list` filtered by `workOrderId`). Sections addressable only from a **job** id, obtained from `wo.work-order-detail`: job status ledger (`wo.job-history`) · diagnostics (`dia.diagnostic-list`, then `dia.diagnostic-history` per report) · labour (`tech.labor-session-list`).                        |

**Merging any of these client-side would be dishonest, and the reason is
mechanical, not stylistic.** Every section carries a _different_ ordering
contract key, and `decodeCursor` refuses a cursor minted under another key. The
five vehicle sections sort on three different columns — `occurred_at`
(attribute history), `created_at` (plates, ownerships and relationships, each
under its own contract key) and `observed_at` (odometer) — and the wider
platform adds `effective_at` (`crm.consent_history`) and `detected_at` (the
duplicate queues). A merged list would have no single
cursor, so its page boundaries would disagree with every constituent section's
own boundaries, and rows would appear or vanish depending on which section
happened to run out first. §21's prohibition on duplicating mutable history into
three tables is satisfied by the sectioned model; it is **not** satisfied by
assembling a fake unified stream in the browser.

**If a unified Vehicle or Work Order stream is ever wanted, it must be built the
way `crm.timeline_events` was built** — as a real emitting ledger with its own
table, its own `AFTER INSERT` triggers, its own `event_type` CHECK and its own
single ordering key — not assembled from five reads.

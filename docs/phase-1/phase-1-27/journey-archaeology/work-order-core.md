# P1-27 journey archaeology — Work Order core

**Classification:** Confidential — Commercial Product and Pilot Planning ·
**Read at:** `develop` `a56eeea0a10d56cd17827ec443dd5ecff40f8c0d`

## Verdict

The Work Order surface is large, complete inside its own boundary, and structurally
unable to answer the Owner's §6 as written. **There is no `POST /api/v1/work-orders`
and no other operation that inserts an ordinary work order.** `apps/api/src/app/api/v1/work-orders/route.ts`
exports `GET` only; the only exported `POST` functions under the whole `work-orders`
tree are on child paths (`transition`, `closure`, `jobs`, `service-lines`,
`required-parts`, `additional-work`, `quality-controls`, `rework`,
`reopen-attempts`). The single ordinary creation path is
`POST /api/v1/receptions/{receptionId}/convert-to-work-order`, whose request body is
`z.object({}).strict().nullable()` — it accepts **no customer id, no vehicle id, no
reception-visit id in the body and no relationship id**. Company, branch, vehicle and
origin are all inherited from the locked reception visit. The second and last insert
path is `POST /work-orders/{workOrderId}/rework`, which copies the visit and vehicle
from a **closed** original and is therefore not a creation affordance for a new job.
So "open a repair order directly against the selected Customer and Vehicle" cannot be
a single request against today's contract; the Frontend can only drive
`create reception → party roles → condition evidence → authorization → approve →
convert`. That chain **is** completable in one uninterrupted session, and an earlier
draft of this file said otherwise. `rec.reception-create` returns the visit's
`recordVersion` on its 201; the four middle steps are not `versionGuarded` and write
only child tables — `setStatus` is the sole `UPDATE rec.reception_visits` in the
module, so the version the client holds is still current when it reaches `approve`;
`rec.reception-approve` consumes it as `If-Match` and returns the post-approval
version as its own ETag (its docblock: that is "what the conversion that follows must
present"); and `convert` consumes that. The gap is **resumption**, not the happy path:
no published read supplies a visit's `record_version`, so a client that reloads, hands
over to a second operator, or arrives at a visit it did not itself create can neither
approve nor convert it (`P1-27-INT-010` / `P1-27-INT-011`). Approval may apply two
edges (`opened → inspecting → authorized`), so the returned version is not always
`expectedVersion + 1` and must be read from the response rather than computed.

**The work order is not linked to a customer at all — not directly, and not through
the vehicle.** `wo.work_orders` (migration `20260722095000_wo_work_orders.sql`) has
columns `reception_visit_id` and `vehicle_id` and nothing else that names a party; a
repository-wide grep for `customer_id` across `supabase/migrations` returns zero
files. `WorkOrderRow` and `WorkOrderSummary` carry `receptionVisitId` and `vehicleId`
and no partner field; a grep for `customerId|partnerId|business_partner` across
`apps/api/src/modules/work-order` returns **no matches**. The customer is reachable
only as `work order → reception_visit_id → rec.reception_party_roles.partner_id →
crm.business_partners`, and `rec.reception_party_roles` has **no GET operation** —
`/receptions/{receptionId}/party-roles` is POST-only. Therefore **no screen can today
display the customer of a work order**, and gaps 3, 5, 6, 8 and 9 of the Owner's list
are contract gaps in the Backend, not layout gaps in the Frontend.

The board is also unfilterable by the things the journey navigates by. `GET /work-orders`
requires `companyId` and `branchId` and accepts only `state`, `kind`, `openedFrom`,
`openedTo`, `cursor`, `limit` — there is **no `vehicleId` filter, no customer filter
and no `displayNumber` search**, and the schema is `.strict()`, so sending one is a 422. "This vehicle's work orders" and "this customer's work orders" cannot be
answered.

What the domain _does_ support today is the whole of the in-workshop lifecycle once
the order exists: a tenant-configurable state graph read from catalogue tables (never
mirrored in TypeScript), jobs with their own graph and assignments, service lines and
required-part demand, additional-work requests with an immutable customer decision and
its evidence, a six-blocker closure gate reported in full before it is enforced, a
recorded-and-always-refused reopen ledger, rework against a closed original, and a
read-only invoice preview. Every write is scoped, audited and version-guarded where it
touches shared state.

## Operations that exist

Thirty-four operations were opened for this file: the route module, the service, the
repository and the `docs/api/openapi.v1.json` entry for each. A standing note on the
OpenAPI document: it is generated from the operation registry and its `200` bodies are
declared as bare `{"type": "object"}` — it carries the operation id, path, method,
`x-required-permissions`, `x-scope`, `x-audit-class`, `x-rate-limit-policy` and
`x-cache-category` and **no field names**. Every field name below is read from the Zod
schema in the route module and the TypeScript projection in the service.

A standing note on pagination: `Page<T>` is `{ items, nextCursor, hasMore }`
(`apps/api/src/server/db/pagination.ts` lines 45–51). There is no `total`.
`DEFAULT_PAGE_SIZE = 50`, `MAX_PAGE_SIZE = 100`, and a `limit` above 100 is **clamped,
not refused**. `schemas.cursor` is `z.string().min(1).max(512)`; `schemas.limit` is
`z.coerce.number().int().min(1).max(100)`.

A standing note on money and quantities: `quantity` on both line tables is
`numeric(12,3)` and crosses the boundary as a **decimal string**; every invoice-preview
amount is `numeric(18,4)` and crosses as a **decimal string** with one ISO-4217
`currency` code for the whole document. `record_version` is `integer` and is a JSON
number.

### The status model, exactly

`wo.work_orders.state` carries only a **format** CHECK — `ck_work_orders_state_format`
`CHECK (state ~ '^[a-z][a-z0-9_]{1,62}$')`. There is no enumerated CHECK on the value.
The vocabulary lives entirely in the tenant-extensible catalogue table
`wo.work_order_states`, and the seeded platform rows are
`supabase/seeds/06_wo_job_state_graph.sql`:

| code                | name              | is_terminal | is_closed | is_cancellation | reason_required | allows_jobs | allows_labor | allows_additional_work | requires_qc | is_reopenable |
| ------------------- | ----------------- | ----------- | --------- | --------------- | --------------- | ----------- | ------------ | ---------------------- | ----------- | ------------- |
| `draft`             | Draft             | false       | false     | false           | false           | false       | false        | false                  | false       | false         |
| `open`              | Open              | false       | false     | false           | false           | true        | true         | true                   | false       | false         |
| `in_progress`       | In Progress       | false       | false     | false           | false           | true        | true         | true                   | false       | false         |
| `awaiting_parts`    | Awaiting Parts    | false       | false     | false           | **true**        | true        | false        | true                   | false       | false         |
| `awaiting_customer` | Awaiting Customer | false       | false     | false           | **true**        | false       | false        | true                   | false       | false         |
| `qc_pending`        | QC Pending        | false       | false     | false           | false           | false       | false        | false                  | **true**    | false         |
| `ready_to_close`    | Ready to Close    | false       | false     | false           | false           | false       | false        | false                  | **true**    | false         |
| `closed`            | Closed            | **true**    | **true**  | false           | false           | false       | false        | false                  | false       | false         |
| `cancelled`         | Cancelled         | **true**    | **true**  | **true**        | **true**        | false       | false        | false                  | false       | false         |

`cancelled` carries `is_closed = true` **and** `is_cancellation = true`. That is why
the rework service refuses a cancelled original explicitly: the database alone would
accept it.

Seeded platform edges (`wo.work_order_transitions`), `requires_reason` in brackets:

`draft→open` [no] · `open→in_progress` [no] · `in_progress→awaiting_parts` [**yes**] ·
`awaiting_parts→in_progress` [no] · `in_progress→awaiting_customer` [**yes**] ·
`awaiting_customer→in_progress` [no] · `in_progress→qc_pending` [no] ·
`qc_pending→in_progress` [**yes**] · `qc_pending→ready_to_close` [no] ·
`ready_to_close→closed` [no] · and `→cancelled` [**yes**] from each of `draft`,
`open`, `in_progress`, `awaiting_parts`, `awaiting_customer`.

A work order therefore **opens in `draft`** (the column default) and is not
job-accepting until `open`. There is no edge from `closed` or `cancelled` to anything;
`wo.guard_work_order_transition` freezes a terminal state regardless of any configured
edge (BR-WO-002).

The seeded job graph, from the same file: states `planned`, `assigned`,
`in_progress`, `paused`, `completed` (terminal), `cancelled` (terminal), with
`assignment_required` true for `assigned`/`in_progress`/`paused` and `labor_allowed`
true for `assigned`/`in_progress` only. Edges: `planned→assigned` · `assigned→in_progress`
· `in_progress→paused` [yes] · `paused→in_progress` · `paused→assigned` [yes] ·
`in_progress→completed` · and `→cancelled` [yes] from `planned`, `assigned`,
`in_progress`, `paused`.

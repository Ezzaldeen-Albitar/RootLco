# P1-27 journey archaeology — Vehicle — plate, identity and profile

**Classification:** Confidential — Commercial Product and Pilot Planning ·
**Read at:** `develop` `a56eeea0a10d56cd17827ec443dd5ecff40f8c0d`

## Verdict

The contract can support a full plate **history** screen and a full vehicle
**profile** screen, and it can support **neither** of the two things the journey
actually asks for. There is exactly one operation anywhere in the backend that
returns a plate value — `veh.vehicle-plate-history`, `GET
/vehicles/{vehicleId}/plates` — and it is a paginated sub-resource of one
vehicle. **Neither `veh.vehicle-search` nor `veh.vehicle-read` returns a plate at
all**: I opened both repositories and neither statement joins, selects from, or
subqueries `veh.plate_history` for a projection (search touches the table only
inside an `EXISTS` filter, and never selects a column from it). So a plate shown
"prominently on six surfaces" today costs one extra `expensive-read` request per
vehicle per surface, and on any list surface it is N extra requests for N rows.
The rate limit turns that from slow into impossible, and not in the way one
would guess: `expensive-read` is `limit: 30`, `windowMs: 60_000`, keyed
`['operation', 'tenant', 'user']`
(`apps/api/src/server/http/rate-limit.ts` lines 127–136), and `handleOperation`
passes `operation: operation.id` (`route-handler.ts` line 307). So
`veh.vehicle-plate-history` has its **own** bucket, _separate_ from the search's
— but that bucket is **30 requests per minute per operator**, and one default
50-row search page needs 50 of them. The 31st row on the first page already
answers `429` `ERR-RTE-001`. A plate column on a search result table cannot be
built from this operation at any page size above 30. On effective
dates the Owner's §8 is exactly right and the position is worse than "do not
trust `active`": `active` is **not a column**. It does not exist in
`veh.plate_history`. It is invented in TypeScript as `valid_to === null`, so it
means "this interval was never closed", and a plate whose `valid_from` is in the
future reports `active: true` while a different plate is physically on the car.
The backend computes no notion of "current" and exposes no point-in-time
resolver: `veh.plate_at(uuid, date)` exists in the frozen schema, is granted to
`app_runtime`, is called by **no** repository, and even if it were called it
returns the plate row's `id`, not the plate. "Current plate" is therefore a
**client** computation from `validFrom`, `validTo` and today's local date, over
a page of history that is **ordered by `created_at`, not by `valid_from`** — so
a back-dated plate sorts to the top of "history" and, if the vehicle has more
plates than one page, the in-force plate can be on page two. Separately, one
consequence of how a future-dated assignment closes the outgoing interval is a
live search defect, described in full below: for the whole window between the
assignment and the changeover, searching the plate that is on the car returns
nothing, and searching the plate that is not yet issued returns the vehicle. On
identity: VIN is carried as `vin_raw` (never published) plus the generated
`vin_normalized` (published as `vin` by both search and read), it is unmasked
everywhere, and **chassis and engine numbers are ABSENT from the entire API** —
`veh.vehicle_identifiers` is read by no route, no service and no repository in
`apps/api`. Two further facts a profile screen must be built around: the plate
list and the vehicle read **disagree about which vehicles exist** — the read
filters `deleted_at IS NULL` and the plate list joins `veh.vehicles` not at all,
so a soft-deleted vehicle is a `404` in the header and still lists its plates in
the tab; and the OpenAPI document is a **subset** of the real response set for
this module — I enumerated the responses of all 28 `*vehicle*` operations in
`docs/api/openapi.v1.json` and **not one declares `400`, `404` or `428`**,
though the implementation produces all three, and **every one declares `200`**
even though `veh.vehicle-create` and `veh.vehicle-plate-assign` return `201`. A
client generated from the spec has no branch for a missing vehicle and would
read a successful plate assignment as a failure.

## How "current plate" would have to be computed, field by field

The backend computes nothing. A client holding one page of
`veh.vehicle-plate-history` must decide from exactly these three published
fields plus its own clock:

| Input       | Source                                          | Rule                                                                                                                          |
| ----------- | ----------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------- |
| `validFrom` | `valid_from::text`, `"YYYY-MM-DD"`              | in force requires `validFrom <= today`                                                                                        |
| `validTo`   | `valid_to::text` or `null`                      | in force requires `validTo === null \|\| validTo > today`                                                                     |
| `active`    | invented client-side field, `valid_to === null` | means "never closed" — **not** "in force"                                                                                     |
| today       | the operator's **local** date                   | must be built from local parts; `toISOString().slice(0,10)` gives the UTC day and answers for the wrong day east of Greenwich |

Comparison must be **lexicographic on the ISO strings**. Parsing either date
with `new Date()` re-introduces the timezone shift the `::text` cast exists to
avoid.

The four honest states are `in-force`, `scheduled` (open interval, `validFrom`
in the future), `ended` (`validTo` has passed), `unknown` (a date that is not an
ISO day). This is already implemented on the Frontend as `isInForceOn`,
`localToday` and `intervalState` in
`apps/web/src/features/vehicles/history-contract.ts` — the journey should reuse
those rather than re-derive them, and must not introduce a fifth label such as
"current".

Two structural limits the client computation cannot overcome on its own:

1. The list is ordered by `created_at DESC`, **not** `valid_from DESC`. A
   back-dated plate row sorts to the top of "history".
2. Because it is paginated at 50 by default, a vehicle with more than one page
   of plates can have its in-force plate on page two. "The current plate" is
   therefore not derivable from the first page alone without following
   `nextCursor` to the end.

## Consequences of a future-dated assignment (read from the SQL, not inferred)

`assignPlate` closes the outgoing interval with
`SET valid_to = COALESCE($3::date, current_date)` where `$3` is the **new**
plate's `effectiveDate`, and then inserts the new row with
`valid_from = COALESCE($5::date, current_date)`. So for an assignment dated one
month ahead:

- the outgoing row immediately has `valid_to = <future date>` — it is no longer
  `NULL`, so its `active` flag flips to `false` **today**, a month before the
  plate leaves the car;
- the incoming row has `valid_from = <future date>`, `valid_to = NULL` — so its
  `active` flag is `true` **today**, a month before the plate is on the car;
- `veh.vehicle-search`'s plate filter is `EXISTS (… ph.valid_to IS NULL AND
ph.plate_normalized = veh.normalize_plate($n))`. For that whole month,
  **searching the plate physically on the vehicle returns nothing, and searching
  the not-yet-issued plate returns the vehicle.**

This is a property of the operations as they stand at
`a56eeea0a10d56cd17827ec443dd5ecff40f8c0d`. It is stated here as an input to the
Frontend decision, not as a defect ticket.

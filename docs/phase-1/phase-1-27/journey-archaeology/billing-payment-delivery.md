# P1-27 journey archaeology — Accounting, payment and delivery

**Classification:** Confidential — Commercial Product and Pilot Planning ·
**Read at:** `develop` `a56eeea0a10d56cd17827ec443dd5ecff40f8c0d`

## Verdict

Twenty operations exist across `billing`, `payments`, `delivery` and the warranty
subresource that hangs off a completed handover, and every one of them was registered by a
route module, implemented by a service, backed by a repository and published in
`docs/api/openapi.v1.json`. Together they support the whole of one work order's money and
handover path **provided the client already holds the identifiers**: preview what a work
order would bill, create the single draft invoice, issue it (one number, once), read its
header and its open receivable, credit it under dual control, void it before issue, list the
payment methods a receipt may cite, record a receipt, allocate that receipt to an issued
invoice, read the receipt with its allocation history, open a delivery record, verify the one
authorised receiver, record checklist outcomes, bind signature document references, read the
eight-blocker eligibility decision, complete the handover under `If-Match` with exactly one
overridable blocker, and generate and read a warranty.

What it cannot support is **navigation**. There is no list operation over any business
document in this domain — the single list that exists, `sal.payment-method-list`, is closed
reference data with no cursor and no `total`.
There is no `GET /invoices`, no `GET /payments`, no `GET /deliveries`, no
`GET /work-orders/{id}/invoice`, no `GET /work-orders/{id}/deliveries`, no
`GET /customers/{id}/invoices`, and no `GET /credit-notes/{id}`. Every identifier in this
domain is obtainable **only from the 201 response of the command that created it**. A screen
that opens on a work order and asks "does this job have an invoice, and is it paid?" cannot
be built from this contract — `sal.invoice-preview` answers what the invoice _would_ contain,
not whether one exists, and the only server-side reader that resolves a work order to its live
invoice (`BillingReadService.openReceivableForWorkOrder`) is an internal cross-module port
that the code explicitly forbids exposing as a route. The same is true of the delivery: once
the create response is lost, the delivery id is unrecoverable and so is the `record_version`
that `POST .../completion` demands in `If-Match`.

Four other structural facts decide what may be built. **There is no `partially_paid` and no
`paid` invoice status** — the invoice row admits exactly four values and payment state is
derived, not stored. **There is no refund, no partial reversal, and no receipt-reversal
route**, although the tables and the `sal.reversal.approve` permission exist. **There is no
online payment gateway** — three method kinds only, and the three platform-seeded methods are
visible to every tenant and citable by no receipt, so a tenant with no provisioned method row
cannot record a payment at all. And **every money figure crosses the wire as a decimal string
with an ISO-4217 code**, never as a JSON number.

foreign key anywhere in `sal` that refuses a handover against an unpaid issued invoice.

#### Each `facts[]` entry

`{ blocker: BlockerCode, established: boolean, source: string }`. `established: false` means
the fact could not be read and the blocker is **assumed** present — operationally different
from a known-bad fact, and a UI must distinguish them.

#### `overridable[]`

`OVERRIDABLE_BLOCKERS`, a one-element list:
`[{ code: 'financial_balance_outstanding', permission: 'sal.delivery.complete' }]`. Nothing
else is overridable, and the reason is honesty rather than strictness: two of the others are
enforced inside the primitive, so an "override" would be accepted and then fail at the
database.

#### The `collectable` flag

`collectable` lives on `WorkOrderReceivableView` in
`apps/api/src/modules/billing/application/billing-read-service.ts` (lines 161–203). It is
**not on the eligibility wire response** — it is consumed inside `readFinancialFact` and
surfaces to a client only through the `facts[]` entry's `source` prose. The receivable port
returns four distinguishable shapes, and only the first is an actual debt:

| Case                                                       | `amount`                      | `hasOutstanding`                      | `balanceVisible` | `collectable` | Blocker outcome                                                                      |
| ---------------------------------------------------------- | ----------------------------- | ------------------------------------- | ---------------- | ------------- | ------------------------------------------------------------------------------------ |
| Live issued/credited invoice with a real balance           | the exact decimal string      | `amount > 0` by `Decimal.greaterThan` | `true`           | `true`        | blocker present iff `amount > 0`, `established: true`                                |
| Live invoice not yet issued (`draft`, `void_before_issue`) | `null` (**never `'0.0000'`**) | `true`                                | `true`           | **`false`**   | blocker present, `established: true`, source names the status                        |
| Amounts hidden because the caller lacks `sal.finance.view` | `null`                        | `true`                                | `false`          | `true`        | blocker present, `established: **false**`                                            |
| No live invoice for the work order (port returns `null`)   | —                             | —                                     | —                | —             | blocker present, `established: **false**` — "nothing was invoiced is not settlement" |

The second row is the defect the P1-22 review found and fixed: before `collectable` existed,
**creating a draft invoice REMOVED the financial blocker**, making a work order with a draft
strictly more deliverable than one with no invoice at all. The fourth row is a deliberate,
documented disagreement with the billing port's own doc comment, which says a consumer should
treat `null` as "no financial blocker".

**An odometer trap.** The route regex accepts up to **two** decimal places, but
`veh.odometer_readings.value` is `numeric(12,1)` and `parseOdometerValue` validates against

**below** the current effective kilometres, so a mistyped low odometer is a 409 from the
database, not a validation error.

## Invoice states — exact values and CHECK constraints

**`ck_invoices_status`** (`supabase/migrations/20260724091000_sal_invoices.sql` line 65) —
exactly four values:

```
'draft', 'issued', 'credited', 'void_before_issue'
```

The legal edges, transcribed from `sal.guard_invoice_freeze` into `INVOICE_TRANSITIONS`:
`draft → draft`, `draft → issued`, `draft → void_before_issue`, `issued → credited`.
`credited` and `void_before_issue` are terminal. There is no un-void, no un-issue and no
re-open.

**`ck_invoices_number_iff_issued`** (line 67) is a biconditional:
`(invoice_number IS NULL AND issued_at IS NULL) = (status IN ('draft','void_before_issue'))`.
So an invoice number exists **if and only if** the invoice is `issued` or `credited`.

**`ck_invoice_status_history_to_status`** (line 518) is deliberately **wider — six values**:

```
'draft', 'issued', 'partially_paid', 'paid', 'credited', 'void_before_issue'
```

`partially_paid` and `paid` are recordable in the history table and are **never storable on the
invoice row by any database code**, because payment state is derived (M-fin-1) from
`sal.invoice_open_receivable`. Reading the history vocabulary as if it were the invoice's own
would invent two statuses the invoice cannot hold. **No API operation writes either value**,
and no read returns them on `InvoiceView.status`.

Other closed vocabularies in billing:

| Constraint                            | Values                                                                                                                                     |
| ------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------ |
| `ck_invoice_lines_line_type`          | `'service'`, `'part'`, `'fee'`                                                                                                             |
| `ck_credit_notes_approval_state`      | `'pending'`, `'approved'`, `'rejected'`                                                                                                    |
| `ck_receipt_reversals_approval_state` | `'pending'`, `'approved'`, `'rejected'`                                                                                                    |
| `ck_financial_events_event_type`      | `'invoice_issued'`, `'receipt_recorded'`, `'payment_allocated'`, `'credit_note_issued'`, `'receipt_reversed'`, `'warranty_split_recorded'` |
| `ck_financial_events_source_type`     | `'invoice'`, `'receipt'`, `'payment_allocation'`, `'credit_note'`, `'receipt_reversal'`                                                    |
| `ck_invoice_numbering_configs_mode`   | `'gapless'`, `'gapped'` — read-only metadata with **zero behavioural effect** anywhere in the DDL, and no route exposes it                 |

## Payment states — what is real and what would be invented

**`ck_receipts_status`** (`supabase/migrations/20260724092000_sal_payments.sql` line 112) —
exactly four values, and these are the only payment states that exist:

```
'recorded', 'partially_allocated', 'allocated', 'reversed'
```

`recorded → partially_allocated → allocated` is driven by `sal.allocate_receipt`, which
re-sums after each allocation and sets the status itself. `'reversed'` is terminal and is
reachable only when an approved `sal.receipt_reversals` row exists — **and this API exposes no
reversal route** (`P1-22-L-05`), so no request can ever produce it.

Against the four candidate labels named in the assignment:

| Candidate label    | Verdict                                                                                                                                                                                                    | Evidence                                                                                                                                                                        |
| ------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| "awaiting invoice" | **INVENTED.** No such state anywhere                                                                                                                                                                       | Not in `ck_receipts_status`, not in `ck_invoices_status`, not in `ck_invoice_status_history_to_status`                                                                          |
| "awaiting payment" | **INVENTED as a state.** Derivable as a presentation label only: an invoice whose `status = 'issued'` and whose `sal.invoice_open_receivable` equals its gross                                             | `OutstandingView` gives `status` + `outstanding` + `isSettled`; there is no stored field that says "awaiting payment"                                                           |
| "partially paid"   | **REAL as history vocabulary only** (`partially_paid` in `ck_invoice_status_history_to_status`); **INVENTED as an invoice status**. Derivable per-invoice from `outstanding > 0` and `outstanding < gross` | `INVOICE_HISTORY_STATES` vs `INVOICE_STATUSES` in `apps/api/src/modules/billing/domain/billing.ts` lines 38–63                                                                  |
| "paid"             | **REAL as history vocabulary only** (`paid`); **INVENTED as an invoice status**. Derivable from `OutstandingView.isSettled === true` **on an issued invoice**                                              | Same. `isSettled` is `true` for a `draft` too, because `sal.invoice_open_receivable` short-circuits to `0` — so a UI must gate on `status === 'issued'` before rendering "paid" |

The receipt-side equivalents that ARE real: `ReceiptDetailView.status` plus
`ReceiptDetailView.unallocated` (`sal.receipt_unallocated`, derived on every call). Note that
`unallocated` reads `0` both for a fully allocated receipt and for a reversed one.

## Delivery eligibility and completion — direct answers

- **The eligibility operation** is `sal.delivery-eligibility-read`,
  `GET /api/v1/deliveries/{deliveryId}/eligibility`, permissions `sal.delivery.view` +
  `sal.finance.view`. It returns `deliveryId`, `workOrderId`, `status`, `eligible`,
  `blockers[]`, `overridden[]` (always empty), `facts[]`, `checklistGaps[]` (bounded at 20),
  `overridable[]` and `recordVersion`, and emits the version as an `ETag`.
- **The eight blockers** are enumerated exactly in the table under §17 above, and are the
  frozen contents of `BLOCKER_CODES`.
- **The `collectable` flag** and its four receivable shapes are in the table under §17.
- **The operation that completes a delivery** is `sal.delivery-complete`,
  `POST /api/v1/deliveries/{deliveryId}/completion`. It requires all three of
  `sal.delivery.complete`, `sal.delivery.view`, `sal.finance.view`; an `Idempotency-Key`; a
  `finalOdometerValue` decimal string; and an `If-Match` carrying the delivery's current
  `record_version`. It **is** version-guarded, and the client obtains the version from the
  `ETag`/`recordVersion` of the eligibility read (or, only while nothing has advanced the
  record, from the `201` of `POST /deliveries`).

| `sal.financial_events`     | `amount`              | `numeric(18,4)` | `ck_financial_events_amount` — `>= 0` (no route reaches this table)                                        |

Two money validators, not one: **`>= 0`** on invoice, line and financial-event amounts (a
zero-total issued invoice is legal — a fully warranty-covered job), and **`> 0`** on every
payment instrument. **Negative amounts are legal nowhere**; there is no signed amount column
in `sal`, so a credit is always a separate positive-amount row, never a negative line.

Currency: `currency_code text NOT NULL` with `FOREIGN KEY … REFERENCES shared.currencies (code)`
on `sal.invoices`, `sal.invoice_lines`, `sal.receipts`, `sal.payment_allocations`,
`sal.credit_notes` and `sal.receipt_reversals`. **No `currency_code` column in `sal` or `wty`
carries a `DEFAULT`**, and the platform ships no jurisdiction default. Seeded currencies
(`supabase/seeds/01_reference_data.sql`): `JOD` minor unit **3**, `USD` **2**, `EUR` **2** —
and `assertMinorUnitScale` refuses an inbound amount more precise than its currency
(`ERR-VAL-001`, rule `minor_unit_scale`) even though the column would accept four decimals.

**Non-money numerics in this domain** (do not validate these against money's scale):

| Column                                  | Type            | Notes                                                                                                  |
| --------------------------------------- | --------------- | ------------------------------------------------------------------------------------------------------ |
| `sal.invoice_lines.quantity`            | `numeric(12,3)` | `ck_invoice_lines_quantity` — `> 0`. Wire string, **no currency**                                      |
| `quo.quotation_items.captured_tax_rate` | `numeric(9,6)`  | surfaced as `InvoicePreviewLine.taxRate`, a fraction not a percentage. Always `0` today (`P1-22-L-08`) |
| `veh.odometer_readings.value`           | `numeric(12,1)` | `ck_odometer_readings_value_nonneg` — `>= 0`; `ck_odometer_readings_unit` — `unit IN ('km','mi')`      |

**`bigint` columns** — `seq` on `sal.invoice_status_history`, `sal.payment_allocations`,
`sal.delivery_status_history` and `sal.financial_events`, all
`bigint GENERATED ALWAYS AS IDENTITY`. Exactly one reaches the wire:
`ReceiptAllocationView.sequence`, **rendered as a STRING** because a `bigint` does not fit a
JavaScript number.

# P1-27 journey archaeology — service catalogue, labour, pricing and quotation

**Classification:** Confidential — Commercial Product and Pilot Planning ·
**Read at:** `develop` `a56eeea0a10d56cd17827ec443dd5ecff40f8c0d`

## Verdict

Today this domain can price and quote work that is already on a work order, and it
can record a customer's line-by-line decision on that quotation with evidence. There
are seventeen operations, all registered under `svc.` and `quo.`, all built in Phase
1-20, and every amount they return is an exact decimal **string** with an ISO 4217
currency code beside it. What it cannot do is get a tenant into that state or get a
user back out of it. There is **no operation that lists quotations** — none at all, for
a work order, a customer, a branch or a date — so a quotation can only ever be reached
by an id the caller already holds; `GET /api/v1/quotations/{quotationId}` is the only
read in this domain. **One route outside it partially closes the work-order join**:
`sal.invoice-preview` (`GET /api/v1/work-orders/{workOrderId}/invoice-preview`, P1-22,
module `billing`) queries `quo.quotations` by `work_order_id` and returns
`quotationId` and `quotationRevisionId` — but only for the single revision whose
derived outcome is `accepted`, under `sal.invoice.manage` **AND** `sal.finance.view`,
answering `ERR-RES-001` when none is accepted and `ERR-CON-001` when more than one is.
It is not a list and it cannot reach a draft, issued-but-undecided or rejected
quotation. There is **no operation that reads a single service** (`GET /services/{serviceId}`
is ABSENT; only `PATCH` exists on that path), **no operation that reads a service
version or its standard labour minutes**, and **no operation that reads or writes a
service category** — so the `categoryId` on every catalogue row is an opaque uuid with
no name behind it. Five tables that price resolution depends on absolutely —
`svc.service_versions` (draft create), `svc.service_categories`,
`svc.price_list_assignments`, `svc.discount_rules` and `svc.pricing_approval_policies` —
have **no API write path whatsoever**; without a `price_list_assignments` row
`svc.resolve_price` returns nothing and every quotation line fails with "no price is
configured", and no operation in this repository can create one. Three of these
absences are already recorded by the owning phase as `P1-20-G-02`, `P1-20-G-03` and
`P1-20-A-05`. Partial approval is **not** supported: decisions are per item, but
`rollUpDecisions` turns any single rejected line into a `rejected` quotation and a
terminal `rejected` revision, so "approve three of five lines and proceed" is an
invention, not a contract. There is an "additional work request" concept, but it lives
in `wo.`, is owned by Phase 1-19, and its link to a quotation revision
(`quotationRevisionRef`) is optional, single-shot and frozen at decision time.

## Operations that exist

Files opened for every operation below: the route module under
`apps/api/src/app/api/v1/**/route.ts`, the application service under
`apps/api/src/modules/*/application/*.ts`, the repository under
`apps/api/src/modules/*/data/*.ts`, and the entry in `docs/api/openapi.v1.json`.

> **Read this before trusting `openapi.v1.json` for field names.** The document
> contains **zero** `requestBody` objects (`grep -c requestBody docs/api/openapi.v1.json`
> → 0) and every success response is declared `{"type": "object"}`. It carries
> `operationId`, `summary`, `tags`, `x-required-permissions`, `x-scope`,
> `x-audit-class`, `x-rate-limit-policy`, `x-cache-category`, the response status
> codes, a `security` block (`bearerAuth`) and a `parameters` array that holds only a
> `$ref` to the shared `CorrelationId` header — **path and query parameters are not
> declared either**. **The only authority for a field name is the `.strict()` Zod
> schema in the route module.** Every field name in this document is transcribed
> verbatim from those schemas.

### Cross-cutting facts that apply to every operation here

| Fact                   | Detail                                                                                                                                                                                                                                                                                              |
| ---------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Pagination shape       | `{ items, nextCursor, hasMore }` — `apps/api/src/server/db/pagination.ts:45`. **There is no `total`.** `DEFAULT_PAGE_SIZE = 50`, `MAX_PAGE_SIZE = 100`; a `limit` above 100 is clamped, not refused (`resolveLimit`, line 54).                                                                      |
| Query `limit`/`cursor` | `schemas.limit` is `z.coerce.number().int().min(1).max(100)`; `schemas.cursor` is `z.string().min(1).max(512)` (`apps/api/src/server/http/validation.ts:217,220`). A malformed cursor is `ERR-PAG-001` (HTTP 400), not a 500.                                                                       |
| Money                  | `numeric(18,4)` everywhere, returned as a decimal **string**, with a separate ISO 4217 `currency` field. `pg` returns OID 1700 as text and the repositories additionally cast `::text`. Quantity is `numeric(12,3)`; tax rate is `numeric(9,6)` and is a **fraction in `[0,1]`**, not a percentage. |
| `.strict()`            | Every request schema in this domain is `.strict()`. One unknown key is `ERR-VAL-001` → **HTTP 422** for the whole request.                                                                                                                                                                          |
| Error → HTTP           | `ERR-VAL-001` 422 · `ERR-PAG-001` 400 · `ERR-IAM-001` 403 · `ERR-IAM-002` 401 · `ERR-RES-001` 404 · `ERR-CON-001` 409 · `ERR-CON-002` 428 · `ERR-TRN-001` 409 · `ERR-SYS-001` 500 (`apps/api/src/server/errors/catalog.ts`).                                                                        |
| Idempotency            | `idempotent: true` on the operation means an `Idempotency-Key` request header is **mandatory**; omitting it is refused. A replay answers **200 even where the first attempt answered 201** (`P1-20-A-10`).                                                                                          |
| Concurrency            | `versionGuarded: true` means `If-Match` carrying the aggregate's `record_version` is **mandatory**; absent → `ERR-CON-002` (428), stale → `ERR-CON-001` (409).                                                                                                                                      |

## Answers to the seven questions, with evidence

### What is a service catalogue item, and how is one attached to a work order?

A catalogue item is a row in **`svc.services`**: `id`, `tenant_id`,
`service_category_id`, `service_code text` (immutable —
`tg_services_immutable('tenant_id','service_code','created_at','created_by')`),
`name text`, `description text NULL`, `lifecycle_status text` (`ck_services_lifecycle`
= `active` \| `archived`), `archived_at timestamptz`
(`ck_services_archived_at CHECK ((lifecycle_status = 'archived') = (archived_at IS NOT NULL))`),
`record_version integer`. It has **no `company_id` and no `branch_id`** — it is
tenant-wide reference data — and **no price column**.

A service becomes sellable only when three facts hold together, tested in one SQL
statement by `ServiceCatalogRepository.isSellableAt`:

1. `svc.services.lifecycle_status = 'active'`;
2. a `svc.service_versions` row with `status = 'published'` whose half-open range
   `effective_from <= asOf AND (effective_to IS NULL OR effective_to > asOf)` covers
   the date;
3. a `svc.branch_service_availability` row for `(tenant, company, branch, service)`
   with `is_available AND status = 'active'`. **An absent row is a denial, not a
   default.**

It reaches a work order by **two different mechanisms, and they are not linked**:

| Mechanism                                      | Column                                                                                                                                                                           | Operation                                                                      | Carries a price?                                                                                   |
| ---------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------- |
| Operational line — "this work is on the order" | `wo.work_order_service_lines.service_ref` → `svc.services (tenant_id, id)` via `fk_work_order_service_lines_service` (added by migration `20260723097000_wo_forward_fks.sql:29`) | `wo.service-line-record` (`serviceRef` in the body)                            | **No.** `description text`, `quantity numeric(12,3)`, `unit text DEFAULT 'each'` and nothing else. |
| Commercial line — "this is what it costs"      | `quo.quotation_items.service_id` → `svc.services (tenant_id, id)` via `fk_quotation_items_service`                                                                               | `quo.quotation-create` / `quo.quotation-revision-create` (`lines[].serviceId`) | **Yes**, resolved server-side.                                                                     |

The bridge between them is `quo.quotation_items.source_service_line_ref`. It is
accepted on write (`lines[].sourceServiceLineRef`), stored, and **never validated and
never returned**: the column has **no foreign key** (the only FKs on
`quo.quotation_items` are `_tenant`, `_revision`, `_service`, `_item` and `_currency`),
nothing in `QuotationService.priceLines` checks it (`quotation-service.ts:931` passes
`line.sourceServiceLineRef ?? null` straight through), and `toLine`
(`quotation-service.ts:158`) **omits it from `MoneyLine`**. So a screen cannot ask
"which work-order line did this quotation line come from" through the API.

### How is labour recorded — quantity, time, price? Exact columns and types.

Labour is **three unrelated things**, in three schemas, and none of them multiplies
minutes by a rate.

1. **Standard (estimated) labour time** — `svc.standard_labor_times`:
   `id uuid`, `tenant_id uuid`, `service_version_id uuid NOT NULL`,
   `labor_code text NULL` (`ck_standard_labor_times_code_format` — lower snake),
   **`standard_minutes numeric(10,2) NOT NULL`** with
   `ck_standard_labor_times_minutes CHECK (standard_minutes > 0)`,
   `skill_ref uuid NULL`, `status text` (`active` \| `inactive`),
   `record_version integer`. The unit is **minutes**, not hours
   (`LABOR_TIME_UNIT = 'minutes'`), and the value crosses as a decimal **string**
   (`LaborTimeView.standardMinutes`, `unit: 'minutes'`). It hangs off the **version**,
   so a revised standard is a new version. **There is no branch override** —
   `P1-20-A-02`. **No route reads it**: `ServiceCatalogService.publishedVersion` is the
   only reader and it has zero call sites.
2. **Planned labour on the order** — `wo.work_order_service_lines`:
   `description text NOT NULL`, `quantity numeric(12,3) NOT NULL DEFAULT 1`
   (`ck_work_order_service_lines_quantity CHECK (quantity > 0)`),
   `unit text NOT NULL DEFAULT 'each'`. Free-text unit; no minutes, no rate, no money.
3. **Actual labour worked** — `tech.labor_sessions`:
   `technician_profile_id uuid NOT NULL`, `job_id uuid NOT NULL`,
   `started_at timestamptz NOT NULL DEFAULT now()`, `ended_at timestamptz NULL`,
   `source text NOT NULL DEFAULT 'manual'`
   (`ck_labor_sessions_source CHECK (source IN ('manual','timer','correction'))`),
   `correction_of_id uuid NULL`, with
   `ck_labor_sessions_window CHECK (ended_at IS NULL OR ended_at > started_at)` and
   `ex_labor_sessions_overlap EXCLUDE USING gist (tenant_id WITH =, technician_profile_id WITH =, tstzrange(started_at, COALESCE(ended_at,'infinity')) WITH &&)`.
   **There is no duration column** — elapsed time is `ended_at − started_at` and the
   API returns only the two ISO timestamps (`LaborSessionView = { id, technicianProfileId, jobId, startedAt, endedAt, source, correctionOfId, recordVersion }`).
   No timestamp is accepted from a caller.

**Price of labour: there is none as a distinct concept.** `grep -rn "labor_rate|labour_rate|hourly_rate|labor_price" supabase/migrations` returns **no matches**. Labour is
priced exactly like anything else — a `svc.price_rules` row against the service's
`service_id` — and a quotation line's money is `captured_unit_price × captured_quantity`,
where `captured_quantity` is whatever the caller sent, **not** minutes worked and **not**
`standard_minutes`. Nothing in the codebase joins `tech.labor_sessions` to a price.

### What is the quotation lifecycle? Exact status values and CHECK constraint.

Two state machines, and they are different:

| Level     | Column                           | CHECK constraint                    | Members                                                           |
| --------- | -------------------------------- | ----------------------------------- | ----------------------------------------------------------------- |
| Quotation | `quo.quotations.status`          | **`ck_quotations_status`**          | `draft`, `active`, `accepted`, `rejected`, `expired`, `cancelled` |
| Revision  | `quo.quotation_revisions.status` | **`ck_quotation_revisions_status`** | `draft`, `issued`, `superseded`, `rejected`, `expired`            |

The revision graph is fixed by `quo.guard_quotation_revision_freeze`: `draft` may
become anything; `issued` may become **only** `superseded`, `rejected` or `expired`;
those three are **terminal** (`TERMINAL_REVISION_STATES`). A non-draft revision's four
captured totals and its `issued_at` are frozen. Independently,
`quo.guard_quotation_item` refuses any item whose parent revision is not `draft` — that
is what makes an issued revision an immutable snapshot. **The trigger is
`BEFORE INSERT OR UPDATE` only** (`20260723096000_quo_quotations.sql:246`), not DELETE:
the function body has a `TG_OP = 'DELETE'` branch but nothing registers it, because
`app_runtime` holds only `GRANT SELECT, INSERT, UPDATE ON quo.quotation_items` (`:261`),
so a runtime delete is refused by the absent grant rather than by the guard. An
admin/owner connection can still delete an issued revision's items.

Reachable transitions through the shipped API:

- `draft → active` — `quo.issue_revision`, inside `quo.quotation-issue`.
- `active → accepted` — the roll-up when every item is `approved`.
- `active → rejected` — the roll-up when **any** item is `rejected`; the revision is
  also moved to `rejected` (terminal).
- `active → expired` — `QuotationService.expireLapsed`, which **has no route and no
  scheduler** (`P1-20-A-05`; `grep -rn expireLapsed apps/api/src` matches only its own
  definition).
- `cancelled` — **no operation writes it. Reachable only by direct database access.**

An **accepted** revision deliberately stays `issued`: there is no `accepted` revision
state to move to, and the acceptance is derived from the item rows, never stored.

### How is customer approval recorded? Approver, channel, time, approved scope, rejected scope.

There are **two separate approval records**, and confusing them is the trap.

**A. Commercial approval — `quo.approval_decisions`** (one row per quotation item):

| Fact                   | Column / behaviour                                                                                                                                                                                                                                                                               | Carried?                                                                                       |
| ---------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------- |
| **Approver**           | `decided_by uuid NOT NULL`, set by the database to `iam.current_user_id()` inside `quo.record_item_decision` — **the staff user who recorded the decision, not the customer**. Returned as `DecisionView.recordedBy`.                                                                            | **Partially.** The schema has no customer-principal column (`P1-20-A-03`).                     |
| Claimed customer party | `decidingPartyRef` in the request body; **not persisted anywhere**. It is validated to equal `quo.quotations.payer_partner_ref` and then discarded — it appears only in the `quo.quotation_revision.decided` audit detail on the revision-wide route, and nowhere at all on the per-item route.  | **No — write-only, and only on one of the two routes.**                                        |
| **Channel**            | `decision_channel text NOT NULL`, `ck_approval_decisions_channel` = `in_person`, `phone`, `portal`, `email`, `system`.                                                                                                                                                                           | Yes.                                                                                           |
| **Time**               | `decided_at timestamptz NOT NULL DEFAULT now()` — server-stamped.                                                                                                                                                                                                                                | Yes.                                                                                           |
| **Approved scope**     | The set of `quotation_item_id`s whose row has `decision = 'approved'`. There is no free-text scope field.                                                                                                                                                                                        | Derived only.                                                                                  |
| **Rejected scope**     | Same, with `decision = 'rejected'`.                                                                                                                                                                                                                                                              | Derived only.                                                                                  |

Append-only: `GRANT SELECT, INSERT` and nothing else. | Yes, on write. **`quo.quotation-detail` does not return it and no read operation exposes it.** |

`quo.approval_decisions` is append-only (`GRANT SELECT, INSERT ON quo.approval_decisions TO app_runtime`)
and `uq_approval_decisions_item` on
`(tenant_id, company_id, branch_id, quotation_revision_id, quotation_item_id)` makes
the **first** decision on a line permanent. A change of mind requires a new revision.

**B. Operational approval — `wo.customer_approvals`** (one row per additional-work
request; P1-19): `deciding_party_role_id uuid NOT NULL` FK to

same reception visit as the work order, `decision text`
(`ck_customer_approvals_decision` = `approved` \| `rejected`), `channel text`
(`ck_customer_approvals_channel` = `in_person`, `phone`, `email`, `sms`, `portal`,
`other`), **`presented_scope text NOT NULL`** (`ck_customer_approvals_presented_scope_not_blank`,
max 4000 at the boundary) — a verbatim record of what the customer was shown —
`quotation_revision_ref uuid NULL`, `decided_at timestamptz DEFAULT now()`.
The whole row is content-immutable (`tg_customer_approvals_immutable`).

**`quotation_revision_ref` DOES carry a foreign key.** The Phase 1-9 table comment
still says "an optional forward quotation-revision reference (no FK; P1-10)" and that
comment is **stale**: `20260723097000_wo_forward_fks.sql:40-44` adds
`fk_customer_approvals_quotation_revision FOREIGN KEY (tenant_id, company_id, branch_id, quotation_revision_ref)
REFERENCES quo.quotation_revisions (tenant_id, company_id, branch_id, id) ON DELETE RESTRICT`,
alongside `ix_customer_approvals_quotation_revision_ref`. It is MATCH SIMPLE, so a
`NULL` ref stays unenforced — which is why the column can still be omitted — but a
**non-null** ref must name a real revision in the SAME company and branch, and the
database enforces that even before the application's own standing check runs.

So: **`presentedScope` free text exists only on the operational approval, never on the
quotation.** The quotation's "approved scope" is nothing but the set of approved line
ids, and the frontend must reconstruct it.

### Is partial approval supported by the contract, or would it be an invention?

**Storage supports it; the lifecycle does not, and building a "partial approval" screen
would be an invention.**

`quo.approval_decisions` is genuinely per item, so `approved` on lines 1–3 and
`rejected` on lines 4–5 is a storable state. But `rollUpDecisions`
(`apps/api/src/modules/quotation/domain/quotation.ts:160`) is the single authority for
the quotation-level outcome and its rule is:

```
if (itemCount === 0)      return null;
if (rejectedCount > 0)    return 'rejected';   // ANY rejected line
if (approvedCount === itemCount) return 'accepted';
return null;                                   // still awaiting decisions
```

One rejected line therefore moves the **whole quotation** to `rejected` **and** moves
the revision to `rejected`, which `quo.guard_quotation_revision_freeze` treats as
terminal. After that no further decision can be recorded against that revision
(`assertDecidable` refuses a revision whose status is not `issued`), so the approved
lines cannot be progressed. The documented commentary is explicit: "A customer who
refuses one line has not accepted the quotation as presented."

The supported workflow for "the customer wants some of it" is: create a **new draft
revision** containing only the wanted lines, issue it, and decide that. There is no
`partiallyAccepted` status in `ck_quotations_status` and no per-line "proceed" flag
anywhere.

### Is there an "additional work request" concept?

Yes — `wo.additional_work_requests`, Phase 1-19, not this domain. Read in full:

| Column                   | Type / constraint                                                                                                                                                                                                                     |
| ------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `work_order_id`          | uuid NOT NULL, composite FK to `wo.work_orders`                                                                                                                                                                                       |
| `originating_job_id`     | uuid NULL, composite FK to `wo.jobs`                                                                                                                                                                                                  |
| `originating_finding_id` | uuid NULL — **no foreign key at all**; the only guard is an application read through the `diagnostics` module                                                                                                                         |
| `summary`                | text NOT NULL, `ck_additional_work_requests_summary_not_blank`, max 500 at the boundary                                                                                                                                               |
| `state`                  | text NOT NULL DEFAULT `'pending'`, **`ck_additional_work_requests_state CHECK (state IN ('pending','approved','rejected','withdrawn'))`**                                                                                             |
| `fulfillment_state`      | text NOT NULL DEFAULT `'unfulfilled'`, **`ck_additional_work_requests_fulfillment CHECK (fulfillment_state IN ('unfulfilled','fulfilled','waived'))`**; the API accepts only `fulfilled` and `waived` (`SETTABLE_FULFILLMENT_STATES`) |
| `is_required`            | boolean NOT NULL DEFAULT true, immutable after insert                                                                                                                                                                                 |

`wo.guard_additional_work_state` refuses `state = 'approved'` unless an `approved` row
already exists in `wo.customer_approvals` for the request — which is why
`wo.additional-work-approval` writes the approval and moves the state in **one**
transaction. A required request that is `pending`, or `approved` with
`fulfillment_state = 'unfulfilled'`, blocks work-order closure (blocker B3).

The customer-facing description lives in the separate **`wo.additional_work_request_details`**
(1:1, `classification` CHECK-fixed to `'restricted'`), whose SELECT, INSERT **and**
UPDATE policies all additionally require `iam.has_permission('iam.sensitive.view')`.
For a caller without that permission the row does not exist, for reading or writing.

The link to this domain is `wo.customer_approvals.quotation_revision_ref` (**nullable,
and composite-FK'd to `quo.quotation_revisions (tenant_id, company_id, branch_id, id)`
by `fk_customer_approvals_quotation_revision`, `20260723097000_wo_forward_fks.sql:40`
— MATCH SIMPLE, so only a non-null ref is enforced**). When supplied it is validated
through `CommercialApprovalReader.standingOf`
under a lock, and refused unless the revision is visible, in the **same company and
branch**, on the **same work order**, is the **current** revision, is **`issued`**, is
**not expired**, and its derived outcome is **`accepted`**. The caller must also hold
`quo.quotation.read` in that scope. Because `tg_customer_approvals_immutable` freezes
the column, **there is no later moment at which the link can be established** — it is
supply-at-decision-time or never.

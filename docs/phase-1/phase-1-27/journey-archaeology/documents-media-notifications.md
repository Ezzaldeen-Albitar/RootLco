# P1-27 journey archaeology — Documents, media evidence and notifications

**Classification:** Confidential — Commercial Product and Pilot Planning ·
**Read at:** `develop` `a56eeea0a10d56cd17827ec443dd5ecff40f8c0d`

## Verdict

A create/upload path for a document **does exist** — the prior record that "the
vehicle documents endpoint is READ-ONLY" is true of the vehicle tree and false of
the API as a whole. `POST /api/v1/attachments/upload-authorizations` creates the
`shared.documents` metadata row and returns a signed upload URL, and
`POST /api/v1/attachments/versions` registers the uploaded object as a version.
But four separate facts, each read out of the code rather than inferred, mean the
journey **cannot** carry a photograph, a signed handover sheet or a scanned
registration document today. First, the upload path requires a
`shared.document_categories` row and **no category is seeded anywhere in the
repository**, while `app_runtime` holds SELECT only on that table and no route
creates one — so every call to the upload operation answers `ERR-RES-001`
"Document category not found or disabled" for every possible `categoryCode`.
Second, the object store is a **port with no production adapter**:
`STORAGE_PROVIDER` defaults to `unconfigured`, whose `signUpload`/`signDownload`
both throw `ERR-SYS-001`, and the only other adapter (`local_fake`) signs against
the RFC 2606 host `object-storage.invalid`, which by construction never resolves.
Third, a version is born `pending` and **acceptance is unreachable from any
application role** — `shared.guard_document_version_transition` demands a `clean`
row in `shared.file_scan_results`, which no application role may write — and
`DOWNLOADABLE_STATES` is `['accepted']`, so **every** download authorization
answers `ERR-DOC-001`. Documents can therefore be bound as evidence and never
retrieved. Fourth, `GET /vehicles/{vehicleId}/documents` resolves the entity token
`veh.vehicle` (singular) while the only write that can create a link accepts
`veh.vehicles` (plural) — so the one document list the vehicle journey has
returns an empty array permanently, and always will, whatever anybody uploads.

Notifications are the mirror image: the write half exists and is sound, and the
half the journey needs is missing. `POST /api/v1/notifications` enqueues one
`shared.outbound_messages` row in `pending` and contacts no provider; three read
operations expose the caller's own inbox and (under a separate, audited
permission) delivery attempts. But **no template read operation exists at all** —
there is no `GET /message-templates`, no `GET /message-templates/{id}/versions`,
no `GET /template-versions/{id}` — and `templateVersionId` is a required,
`.strict()`-validated field, so a Frontend has no published way to discover a
value it is obliged to send. Raising a notification against an **employee for an
assignment** is not possible either: `recipientRef` must be a UUID, and it lands
in the recipient's in-app inbox **only when `iam.user_accounts` resolves it in
this tenant** (`NotificationRepository.isTenantUser`,
`data/notification-repository.ts:124-133`) — any other UUID is accepted, stored
as a salted digest with `recipient_user_id IS NULL`, and is therefore invisible
to every read operation. An assignment names a `tech.technician_profiles.id`, and
**no HTTP surface publishes the `user_id` column that joins them**. Nothing
in any domain module calls `queueMessage` — the sole caller of the notification
service is the HTTP route itself, so no assignment, closure, approval or arrival
raises a notification automatically. There is no unread state, no mark-as-read
operation, and no `read_at` column.

`P1-OD-025` blocks the _policy_ questions — accepted file types, size limits,
retention periods, storage placement. It does not block, and must not be blamed
for, the four engineering facts above.

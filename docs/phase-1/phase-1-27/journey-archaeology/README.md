## 1. The relationship model, as the contracts really express it

§3 of the Owner's instruction gives the tree
**Customer → relationship → Vehicle → Reception Visit → Work Order → eighteen
children**. Every edge of that tree is below, with the operation that publishes
it or the statement that none does.

## 4. The honest headline

Of the twenty-three waves the Owner's §24 lays out, **none is buildable today
against contracts that already exist. Ten can be built in a reduced form that is
honest about what it cannot show. Thirteen are blocked on Backend work that has
not been started.** One hundred integration findings are opened by this
archaeology, twenty-six of them Critical, on top of the three already recorded.

The reason is not that the backend is thin. It is large and, inside each module,
complete: 243 published operations, every one authorised, scoped, audited and
version-guarded where it touches shared state, and every one of them was opened
for this survey. The reason is that **the platform was built as thirteen
well-formed modules and the joins between them were never published.** A work
order knows its vehicle and cannot name its customer. A customer can be linked to
a vehicle and the link cannot be read back. A reception visit can be created,
inspected, signed, authorised and converted, and cannot be found again five
minutes later — twelve operations, every one a `POST`, and not one `GET`. Parts,
quotations, invoices, payments and deliveries all accept a `workOrderId` on the
way in and publish nothing keyed on it coming back. Every identifier in the
commercial half of the journey exists only in the `201` of the command that
created it.

Three findings deserve the Product Owner's attention above the rest, because each
one stops the journey rather than degrading it. **A vehicle can be received
exactly once, ever** (`INT-013`) — the second visit of every returning customer is
a permanent 409, and no screen can work around it. **No screen can display the
customer of a work order** (`INT-036`) — the column does not exist and the hop
through the reception visit is unreadable. **No photograph can be uploaded or
retrieved** (`INT-093`, `INT-094`, `INT-095`) — three independent blocks, any one
of which is sufficient, which is why the Owner's gap 2 is not a Frontend
omission.

What follows from this is a sequencing statement rather than a Frontend backlog.
The ten PARTIAL waves are real work that can start now and will produce screens
the Owner can test. The thirteen BLOCKED waves cannot start, and building
anything against a guessed contract for them would repeat the four failures this
phase has already shipped.

## 5. What must NOT be built

Each item below would require inventing a contract. This phase has shipped four
failures of exactly that shape — an invented permission `veh.vehicle.create`
(the real code is `veh.vehicle.manage`), an invented `ADDRESS_TYPES` list wrong
in both directions, nine guessed fixture field names all refused by `.strict()`
schemas, and a test fixture whose `matchBasis` shape the backend never produces.

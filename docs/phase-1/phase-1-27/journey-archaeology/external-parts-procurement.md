## Verdict

The external-parts and procurement capability is **almost entirely ABSENT**. The
whole API carries exactly **one** operation in this domain —
`inv.external-purchase-part-create`, `POST /api/v1/external-purchase-parts` — and
it is a write-only, single-shot **reference record** against a work order. Of the
six operational acts Step 18 needs — request, approve, order, receive, attach an
invoice reference, see the cost — it serves **one and a half**: it records a
request for an external part (description, quantity, supplier, optional
restricted unit cost) and it binds that record to a work order by a mandatory
foreign key. It cannot
**approve** (no approver column, no approval route, no permission code), cannot
**order** (there is no purchase order, no purchase requisition, no supplier
master and no `prc` schema anywhere in the database), cannot **receive** (the
status vocabulary is closed at `recorded`/`linked`/`cancelled`, there is no
`received` member, and no `PATCH`/`PUT` route exists so the status set at
creation is the status for ever), and cannot **attach an invoice reference**
(no invoice-number, order-number or receipt column exists; `evidence_ref` carries
no foreign key; and the document-link allow-list `LINKABLE_ENTITY_TYPES` contains
**no `inv.` entity at all**, so a supplier invoice cannot even be linked to the
part). The cost **is** structurally linked to the work order — but it is written
to a separate restricted table that **no operation reads**, it is never echoed in
the response (`costRecorded` is a boolean, not an amount), and the invoice
preview bills from quotation-revision lines only, so that cost never reaches a
bill. Worst for a frontend: **there is no read of any kind** — no list, no
detail. A screen can create an external-part record and can then never show it
back, not even to the person who just created it. Any screen for this journey
beyond a single fire-and-forget create form is blocked on Backend work that does
not exist.

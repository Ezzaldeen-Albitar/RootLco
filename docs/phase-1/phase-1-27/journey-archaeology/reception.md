# P1-27 journey archaeology — Appointment and Reception

**Classification:** Confidential — Commercial Product and Pilot Planning ·
**Read at:** `develop` `a56eeea0a10d56cd17827ec443dd5ecff40f8c0d`

## Verdict

The Appointment and Reception domain is a **write-only surface**. There are
exactly **twelve operations** — four `apt.*` and eight `rec.*` — and **every one
of them is a `POST`**. There is **no `GET` anywhere** under
`apps/api/src/app/api/v1/appointments/**` or
`apps/api/src/app/api/v1/receptions/**`, and no other module reads
`rec.reception_visits` or `apt.appointments`. The prior survey's claim of "8
operations and 0 reads" is **confirmed for the `rec.` namespace and understated
overall**: it is 8 reception writes plus 4 appointment writes, and 0 reads in
both namespaces. A screen can therefore _perform_ the whole journey — book,
check in, name the parties, capture condition evidence, capture a signature or a
refusal, record an authorisation decision, approve, and convert — but it can
**never show what it just did**. The only data a caller ever receives back is
the small object returned by the write that produced it; refresh the page and it
is gone. Consequently: there is **no operation that lists a customer's or a
vehicle's reception visits**, no reception detail read, no branch reception
board, no appointment calendar, no evidence list, no status history and no
custody chain. A "reception history" panel cannot be built at all, and a
"reception detail" screen can only be built by the client hoarding every write
response in its own state for the duration of a single session.

Two structural facts are good news for the journey. First, a **customer-reported
concern is structurally separate from a technical finding**: a `complaint` is a
row in `rec.complaints` (+ a `restricted` narrative in `rec.complaint_details`)
and a finding is a row in `rec.condition_items` hanging off an inspection in
`rec.visual_inspections`; the module states explicitly that it never promotes
one into the other. Second, **vehicle condition, damage marks and warning
lights all exist** — as five of the eight members of one discriminated-union
command on `POST /receptions/{receptionId}/condition-evidence`.

Four facts will break a screen if they are not designed around.
`rec.reception-convert-to-work-order` **does exist** and is fully implemented,
but two of the six reception statuses — `closed_without_work` and `refused` —
are **unreachable through the API**: no route moves a visit into either, so a
reception that should not proceed can only be abandoned in `opened`. Worse, and
this is the finding with the widest blast radius in this document, **a vehicle
can be received exactly once, ever**: `uq_reception_visits_open_vehicle` is a
partial unique index on `(tenant_id, vehicle_id)` whose predicate includes
`converted` alongside `opened`, `inspecting` and `authorized`
(`supabase/migrations/20260721097000_rec_reception_visits.sql:115-118`), and
`converted` is terminal in the frozen transition graph, so nothing — not the API,
not `sal.complete_delivery`, not any statement in `supabase/` — can ever move a
converted visit out of that predicate. The returning customer's second visit is a
permanent `ERR-RES-002` (409). See the journey note under `rec.reception-create`.
Separately, recording a
`complaint` or a `contents` line additionally requires the caller to hold
`iam.sensitive.view` **on top of** the operation's declared permission, enforced
by row policy at the database, not by the operation registry. And every one of
the twelve operations is `idempotent: true`, so **`Idempotency-Key` is
mandatory on all twelve** — omit it and the request is a 400 before anything
else runs.

## Operations that exist

Common to every operation below unless a row says otherwise:
`Idempotency-Key` is **required** (8–200 characters after trimming; absent or
malformed → `ERR-INT-002`, 400 — `apps/api/src/server/http/idempotency.ts:41-66`).
`If-Match` accepts a bare integer or the quoted ETag form `"7"`, optionally
`W/`-prefixed (`apps/api/src/server/db/concurrency.ts:28-44`). Every request
schema is `z.…strict()`, so **one unknown key is a 422 for the whole request**.
`ERR-IAM-001` (403), `ERR-INT-001` (409, key re-used with a different
fingerprint), `ERR-INT-002` (400) and `ERR-INT-003` (400, secret-looking field
name in the body) are reachable on all twelve and are not repeated per
operation.

**Journey notes.** A visit has exactly one origin (`ck_reception_visits_one_origin`),
so a walk-in is a first-class `rec.walk_in_references` row, never a fabricated
appointment. Behind the scenes `rec.accept_check_in()` writes the visit, the
mandatory `service_requester` party role, the initial `accepted` custody event
and the first status-history row in one statement, so the journey does **not**
need a separate "assign the requester" call after check-in. `odometerReadingId`
is a reference to a row created by `POST /vehicles/{vehicleId}/odometer-readings`
(`veh.vehicle-odometer-record`, permission `veh.vehicle.odometer.record`), whose
response is `{ readingId, captureMethod, anomalyFlag }` — that is where the id
comes from.

**A vehicle can be received exactly once, ever.**
`uq_reception_visits_open_vehicle` is `(tenant_id, vehicle_id)` WHERE
`reception_status IN ('opened','inspecting','authorized','converted') AND
deleted_at IS NULL`
(`supabase/migrations/20260721097000_rec_reception_visits.sql:115-118`). The
migration's own comment says only `closed_without_work` and `refused` release the
vehicle — and those are precisely the two states no route can reach. `converted`
therefore holds the slot permanently: the frozen graph gives `converted` no
outgoing edge (`…097000:188-199`; `domain/reception.ts:32`); the only statement in
the whole repository that updates a visit's status is
`ReceptionRepository.setStatus` (`reception-repository.ts:195`), called from
exactly two places, neither of which can leave a terminal state; there is **no
`UPDATE rec.reception_visits` anywhere in `supabase/`**, so no trigger or
database function moves one either; and `sal.complete_delivery` — which ends
custody — writes a `released` row into `rec.custody_history` and a
`sal.delivery_status_history` row and never touches the visit
(`supabase/migrations/20260724094000_sal_delivery.sql:464-467`). Nothing soft-
deletes a visit either: the repository offers no delete and no route does. So the
second `POST /receptions` for a vehicle that has ever been converted is
`ERR-RES-002` (409) for the life of the tenant. The existing test proves the
constraint only for a still-`opened` visit
(`tests/backend/p1-18-reception-create.test.ts:739`); the `converted` case is
untested and unhandled. Any screen that offers "receive this vehicle" must expect
that 409 on every returning vehicle, and the workshop journey cannot be run twice
for one vehicle until a Backend remediation either narrows the index predicate or
opens a route to `closed_without_work`.

**A customer-reported concern and a technical finding are structurally
separate.** A `complaint` (`rec.complaints` + `rec.complaint_details`) is what
the customer said; a `condition_item` (`rec.condition_items`) is what staff
observed, and it cannot exist without an `inspection` parent on the same visit.
`domain/reception-evidence.ts:9-16` states in terms that the module models no
cause, no fault, no liability, no cost and no diagnosis, and never promotes one
into the other. There is no API path from a complaint to a finding, or from
either to a job.

**Numeric fields on the request are JSON numbers, not strings.** `evSocPercent`,
`coordX`, `coordY`, `declaredValue` and `quantity` are all `z.number()` on the
wire even though the underlying columns are `numeric(5, 2)`, `numeric(6, 5)`,
`numeric(14, 2)` and `integer`. The "numeric arrives as a string" rule applies to
read responses, and this domain **has no reads at all**, so it never bites here —
but it will the moment a read contract is added.

## What I searched and did not find

Every path below is relative to the repository root. Every claim of absence in
this document rests on one of these searches.

**Module discovery.** `apps/api/src/modules/` contains no directory named
`appointment`. Appointments and receptions are **one module**, `reception`
(`apps/api/src/modules/reception/`), which owns both the `apt.` and `rec.`
operation prefixes; `apps/api/src/modules/reception/index.ts:5-20` states why.
The module has exactly twelve files: four `application/*`, four `data/*`, three
`domain/*` and `index.ts`. All twelve were opened.

**Route enumeration.** `apps/api/src/app/api/v1/receptions/**/route.ts` →
8 files; `apps/api/src/app/api/v1/appointments/**/route.ts` → 4 files. All
twelve were opened in full. Grep `id: '(rec|apt)\.` over `apps/api/src`
returns exactly those twelve `defineOperation` registrations and no others.
**Every one declares `method: 'POST'`.** There is no `export async function GET`
in either tree.

**No read of the reception tables anywhere else.** Grep
`rec\.reception_visits|apt\.appointments` over `apps/api/src` returns: the
reception module's own repositories; `shared-services/domain/sequence-registry.ts`
(`targetTable` metadata); `shared-services/domain/attachment-policy.ts`
(`LINKABLE_ENTITY_TYPES`); and a comment plus a table-name literal in
`delivery/application/delivery-service.ts`. Grep `FROM rec\.|JOIN rec\.` over
`apps/api/src` returns six matches, **all inside
`apps/api/src/modules/reception/data/`**: the visit lock
(`reception-repository.ts:158`), the two halves of the standing-decision
`UNION ALL` (`:351` `rec.authorizations`, `:356` `rec.refusals`), the
active-party-roles read (`:384`), the inspection-exists check
(`reception-evidence-repository.ts:57`) and the damage-map-exists check (`:73`).
That is five reads, one of which is a two-arm union. No other module SELECTs
from `rec`.

**Customer and vehicle history.** Case-insensitive grep for

**The one-visit-per-vehicle blocker — how it was proven, so it is not re-argued.**
Four searches, all negative, are what turn "the index looks restrictive" into
"the second visit is impossible": grep `UPDATE rec\.reception_visits` over
`supabase/` → **no matches at all**, so no migration, trigger or database

returns exactly one statement, `reception-repository.ts:195`; grep `setStatus`

**not** release the vehicle; and `ReceptionRepository` exposes no delete and no
route under `/receptions/**` is anything but `POST`, so a visit is never

# P1-27 journey archaeology — CRM customer and the customer↔vehicle relationship

**Classification:** Confidential — Commercial Product and Pilot Planning ·
**Read at:** `develop` `a56eeea0a10d56cd17827ec443dd5ecff40f8c0d`

## Verdict

The CRM customer record itself is fully served: 28 operations exist under
`/api/v1/customers/**` and `/api/v1/customer-duplicates/**`, covering search, a
single-customer read with `recordVersion`/`ETag`, individual and company
creation, all eight profile components in both directions (list and write),
lifecycle status, timeline, governance history, duplicate scan/queue/review and
merge. Every one of them was opened, and every permission code they name exists
in `supabase/seeds/04_iam_permission_catalog.sql`. One qualification: three of
the eight component lists — alerts, tags and restrictions — return **only rows in
force today**, with no parameter that widens them, so this contract cannot answer
"was this customer ever restricted?" (see the filter table in Group C).

The customer↔vehicle relationship is the opposite. **The contract publishes the
vehicle→parties direction only.** `POST /api/v1/customers/{customerId}/vehicles`
is a write and nothing else — the route module at
`apps/api/src/app/api/v1/customers/[customerId]/vehicles/route.ts` exports `POST`
and no `GET`. The only read of `veh.vehicle_relationships` anywhere in the
platform is `veh.vehicle-relationship-list`, `GET /api/v1/vehicles/{vehicleId}/relationships`,
which is keyed by **vehicle** and requires a `vehicleId` the screen does not
have. There is therefore **no operation, at any path, under any permission, that
answers "which vehicles does this customer have?"**. A customer profile screen
cannot list the customer's vehicles today, and cannot get there by fanning out
either: it has no list of candidate vehicle ids to fan out over.

Three further hard limits follow from the schema rather than from the routes.
**A relationship cannot be corrected.** `tg_vehicle_relationships_immutable`
(`supabase/migrations/20260720100000_veh_relationships_and_evidence.sql:141-145`)
freezes `tenant_id`, `vehicle_id`, `partner_id`, `relationship_role`,
`valid_from`, `authorization_scope`, `granted_by`, `created_at` and `created_by`.
The only mutable **business** column left is `valid_to` — `record_version`,
`updated_at` and `updated_by` are also unfrozen, but they are stamped by
`shared.touch_row_metadata()` and carry no business fact. The only `UPDATE`
statement against the table in the whole API is
`VehicleRelationsRepository.closeRelationship` — reachable solely through
`retireAuthorizedParty`, which first requires
`relationship_role = 'authorized_person'`. So **a relationship in any of the
other six roles — including `owner` and `driver`, which is what
`crm.vehicle-link` writes — can never be ended, corrected or reversed by any
published operation.** A mistyped role is permanent. Finally, no read that
carries a relationship carries anything descriptive about the other side: the
relationship list returns `partnerId` and no customer name; the ownership
history returns `partnerId` and no customer name; neither returns make, model,
year or plate. A screen showing relationships in human words needs a second read
per row.

The P1-27 web client currently calls **none** of the relationship operations.
`crm.vehicle-link` appears only as a table row in
`apps/web/src/lib/api/idempotent-operations.ts:331-333`; no feature module
invokes it.

### Group C — customer profile components

All eight lists share the same shape: path `{ customerId }` (uuid), query
`.strict()` with exactly `cursor` and `limit`, permission `crm.customer.read`,
`auditClass: 'none'`, `rateLimitPolicy: 'expensive-read'`, scope `tenant`,
response `{ items, nextCursor, hasMore }` with **no `total`**, errors
`ERR-RES-001` / `ERR-IAM-001` / `ERR-VAL-001` / `ERR-PAG-001`, no event, no
idempotency, no concurrency, owning phase **Phase 1-16 remediation
(`P1-27-INT-001`)**, tests `tests/backend/p1-16-customer-read.test.ts`
lines 33–40. Each list resolves the parent first, so an other-tenant customer is
a 404, never an empty 200. The per-operation differences are below.

**Not one of the eight lists is a full history, and three of them silently drop
rows that still exist.** The `WHERE` clause of each, read from
`apps/api/src/modules/crm/data/customer-read-repository.ts`:

| list                   | rows the read excludes                                                                                                   | line       |
| ---------------------- | ------------------------------------------------------------------------------------------------------------------------ | ---------- |
| `crm.contact-list`     | `deleted_at IS NOT NULL`                                                                                                 | `:383`     |
| `crm.address-list`     | `deleted_at IS NOT NULL`                                                                                                 | `:438`     |
| `crm.preference-list`  | none — every row                                                                                                         | `:498`     |
| `crm.consent-list`     | none — the full append-only history                                                                                      | `:558`     |
| `crm.note-list`        | `deleted_at IS NOT NULL`, **plus** `restricted`/`secret` notes hidden by `sel_notes_tenant` without `iam.sensitive.view` | `:635`     |
| `crm.alert-list`       | **`active IS NOT TRUE`, and any alert whose `effective_to < current_date`**                                              | `:714-715` |
| `crm.tag-list`         | **assignments whose `valid_to < current_date`, and assignments to a soft-deleted segment** (`s.deleted_at IS NULL`)      | `:764-765` |
| `crm.restriction-list` | **restrictions whose `effective_to < current_date`**                                                                     | `:826`     |

The three emphasised rows matter to the journey: a screen asking "has this
customer ever been restricted?" or "what alerts have been raised on this
customer?" gets **only what is in force today**, and there is no query parameter
that widens it — the query schema is `.strict()` with exactly `cursor` and
`limit`. A lapsed restriction and a restriction that was never imposed are
indistinguishable through this contract. `crm.customer-history` (B7) is the only
read that carries retired governance facts, and it carries status, consent,
block and merge — **not** alerts, tags or restrictions.

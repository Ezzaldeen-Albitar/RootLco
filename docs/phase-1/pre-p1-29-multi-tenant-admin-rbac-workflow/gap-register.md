# PRE-P1-29 — gap register

**Classification:** Confidential — Commercial Product and Pilot Planning

---

## 1. What this document is

This is the single canonical statement of what the platform already has, what it has
but never connected, what it has wrong, and what it does not have at all, for the
multi-tenant administration, RBAC and organization-structure work that must land
**before** Phase 1-29 begins.

Every row carries a file path, and a line number wherever one exists. Nothing here is
an estimate. Where a fact could not be settled, the row says so and names what would
settle it.

Measured against protected `develop` `b969894c`. Every product citation — every path under
`apps/` and `supabase/` — reads the same there as in the checkout the rows were taken from.

One paragraph that stood here has been removed rather than corrected, because it was wrong and
the way it was wrong is worth recording. It said the four PRE-P1-29 ownership profiles lived on
the measuring branch "and nowhere else", on the strength of a search reporting that `develop`
contained no `pre-p1-29` string in either governing file. `develop` contains eight of them in
`.github/ci-baselines/phase-ownership-profiles.json` (lines 108 to 125) and four in
`scripts/ci/check-phase-ownership.mjs`, and the profile line numbers cited in section 3 —
`:304`, `:372`, `:398`, `:429` — are exactly right on `develop` today. The profiles merged in
pull request #255 before that branch was even cut.

The search returned nothing because on this platform a Git revision-and-path argument of the form
`origin/develop:.github/…` is rewritten by the shell into `origin\develop;.github\…`, which Git
rejects — and a failed command piped into a counter reports zero. **A zero from a command that can
fail silently is not evidence of absence.** Read the blob through an argument vector rather than a
shell string, and the absence disappears.

**P1-29 is not started and must not be started.** Rows classified _Deferred to P1-29_
below are recorded here only so that nobody later mistakes them for something this
initiative dropped.

## 3. The four waves

The ownership gate already knows these four lanes; they are not invented here.
The branch-prefix-to-profile mapping is at
`.github/ci-baselines/phase-ownership-profiles.json:107-126`. The profiles themselves
are in `scripts/ci/check-phase-ownership.mjs` — `pre-p1-29-initiative` at `:372-397`,
`pre-p1-29-backend` at `:398-428`, `pre-p1-29-web` at `:429-450`, and
`repository-tooling` at `:304-327`. The file buckets those profiles name are the
`CLASSIFIERS` table at `:37-127`, and a bucket absent from a profile's `allowed` list
is forbidden by default (`:129-130`).

| Wave                       | Branch shape                                                                            | May change                                                                                                                                            | May not change                                                                                                  |
| -------------------------- | --------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------- |
| **Backend lane**           | `feature/pre-p1-29-backend-…`                                                           | API source, migrations, database seeds, the generated operations manifest, the handwritten contract mirrors, docs, tooling, tests, root configuration | Handwritten Web, API workspace configuration, database harness                                                  |
| **Web lane**               | `feature/pre-p1-29-web-…`                                                               | Web, the contract mirrors, docs, tooling, tests, root configuration                                                                                   | API source, API workspace configuration, migrations, seeds, the generated operations manifest, database harness |
| **Initiative integration** | `feature/pre-p1-29-multi-tenant-administration-rbac-workflow` (full name, not a prefix) | Both lanes' output plus docs, tooling, tests and root configuration                                                                                   | API workspace configuration, database harness                                                                   |
| **Governance**             | `chore/pre-p1-29-…` (profile `repository-tooling`)                                      | Tooling, tests, docs, root configuration — the ownership profiles themselves, the gates that read them, and the tests proving those gates can fail    | Any product source: Web, both contract buckets, API source and configuration, migrations, seeds, the database   |

The full branch name is used for the integration lane deliberately: a shorter prefix
would swallow both lane branches and hand each of them the other half of the product
(`.github/ci-baselines/phase-ownership-profiles.json:125`).

## 5. Where the sequencing is forced

Four dependencies are not preferences. They constrain the order of the waves.

1. **GAP-01 before GAP-07.** A chooser has nothing to choose between until an identity
   can hold more than one membership. The unique index at
   `supabase/migrations/20260718090000_iam_user_accounts_and_profiles.sql:109-110` is
   the first thing that has to change, and it is a migration — Backend lane only. The
   Web lane is forbidden from carrying a migration by its own profile
   (`scripts/ci/check-phase-ownership.mjs:442-444`).

2. **GAP-18 before GAP-07.** A company chooser that can only show identifiers is not a
   product. Names have to come back from a directory read before a selector is worth
   building, and the session response is the wrong place to widen — it already
   deliberately publishes only server-resolved facts.

3. **GAP-08 before GAP-19, GAP-20 and GAP-22.** Publishing company, branch and
   department management while a tenant-scoped operation is evaluated tenant-wide would
   put write authority over the organization structure behind the weakest check on the
   platform. The scope fix is a prerequisite for the structure surface, not a companion
   to it.

4. **GAP-16 governs GAP-19, GAP-20, GAP-22 and GAP-24.** The permission codes for all
   four already exist and are already pinned in the schema baseline. New operations
   should require the codes that were seeded for them. That keeps the catalogue count
   at 112 and avoids the failure mode this repository has already hit once, where a
   route declared a code the catalogue did not carry and every denial-based test still
   passed — because a permission that does not exist cannot be held by anybody
   (`.github/ci-baselines/schema-baseline.json:15`).

## 6. What this register cannot settle

Four things are genuinely undetermined, and are listed so that no wave assumes an
answer.

- **The Owner authorizations this register cites are not in the repository.** Five
  rows carry an Owner decision as part of their classification — `GAP-01`, `GAP-05`,
  `GAP-07`, `GAP-26` and `GAP-28` — and none of it is written down anywhere under
  `docs/`. There is no PRE-P1-29 requirements document; `docs/product/` holds only
  `owner-workflow-requirements.md`, whose P1-29 table (`:220-239`) covers work-order
  execution and says nothing about tenancy, memberships or a control-plane principal;
  and no file under `docs/` carries a 2026-08-22 Owner instruction. Everything those
  rows say about the **code** is verified against the code and stands on its own. The
  authorization to change the code does not, and would be settled by the decision
  being recorded in the repository before the Backend lane opens.

- **Whether tenant subscription management belongs in the pilot at all (GAP-24).** The
  table and the permission both exist and neither has ever been used. This is a
  commercial decision about what the product sells, not a technical gap. It would be
  settled by an Owner instruction to either build the surface or retire the code.

- **The disposition of the eight non-organization inert permission codes (GAP-15).**
  `iam.login.view_all`, `inv.cost.view`, `inv.item.manage`,
  `rec.reception.receiving_employee.assign_any`, `rpt.report.configure`,
  `sal.reversal.approve`, `wo.work_order.create` and `wty.policy.manage` each belong to
  a phase that is not PRE-P1-29. Whether they are wired here, wired by their owning
  phase, or retired, cannot be decided from the code. It would be settled by a per-code
  disposition from the phase that seeded each one.

- **Whether the control-plane principal authenticates through the same provider as
  tenant users (GAP-26).** Nothing in the codebase constrains this either way, because
  nothing in the codebase knows the concept exists. The choice has consequences for
  GAP-01: if the Superadmin authenticates through the same provider, it participates in
  the same platform-unique identity key that GAP-01 is changing. It would be settled by
  an Owner or architecture decision recorded before the Backend lane opens.

Two further points are worth stating plainly rather than leaving to inference. First,
`GAP-06` is the only **row** in this register whose evidence differs between `develop`
and an unmerged branch; every other row's citations read the same on both. Outside the
rows, §3 and §5.1 cite the two ownership-gate files that carry the PRE-P1-29 profiles,
and those exist only on this governance branch — see §1. Second, this register makes no
claim about test coverage, CI state or evidence seals for any row — it is a statement of
what the product does and does not do.

## 0. Read this before anything else

### 0.1 This is a PROGRAM PLAN. It authorises nothing.

**It schedules nothing. It funds nothing. It implements nothing. It does not
begin P1-28.**

The Product Owner asked for a formal controlled Frontend implementation program
after every existing Backend contract had been mapped. The mapping is finished
and lives in `docs/product/README.md`, which carries **176 integration
findings** gathered from ten documents. This document is the program that sits
on top of that mapping: it partitions the remaining Frontend work into work
packages, states for each what contract it would consume, what must close before
it may start, and what it must prove before it may be presented for acceptance.

Four things follow from that, and none of them is negotiable.

| this document does                                                            | this document does **not**                                                                                                                                                                                                       |
| ----------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Partition the work into packages with stated entry and exit criteria          | Start any package, allocate any package to a person, or put any package in a calendar                                                                                                                                            |
| Name the contracts a package would consume, read out of the repository        | Claim any of those screens exists. **Not one of them does**, outside the P1-27 surface named in `WFP-01` and `WFP-02`                                                                                                            |
| Record the dependency order the contracts themselves impose                   | Express a preference about order where the contracts impose none                                                                                                                                                                 |
| Name the owning Frontend phase where a repository record establishes one      | Invent a phase number. Where no record names one, the entry reads **not established** and says what would establish it                                                                                                           |

Promoting a `WF-`/`RMC-`/`INS-`/`DTA-`/`PROC-`/`PPD-`/`VHM-`/`VDP-`/`VCAT-`/`MVE-` finding into the live `P1-27-INT-###` register is the register owner's act, and this document does not do it |

### 1.1 What the operating product can actually do today

**Nothing in the workshop journey.** The router holds no page for an
appointment, a reception visit, a work order, a job, an inspection, a
quotation, a part, an invoice, a payment, a delivery or a warranty.
**Twenty-seven of the twenty-nine journey steps have no screen of any kind.**
The two that do — step 2, customer identification or creation, and step 3,
vehicle identification or creation — are served by the search, read and creation
screens P1-27 built, and by nothing else.

The sidebar already names twelve of the missing areas as `planned`, which is the
honest rendering — an entry that pointed at a route which does not exist would
tell an operator the screen is real. **Four of those `planned` entries name a
permission code that is not seeded**, and under `navigation.ts`'s own
"unknown means denied" rule they are therefore invisible to every actor alive:

| sidebar entry  | permission it names    | seeded? | note                                                                      |
| -------------- | ---------------------- | ------- | ------------------------------------------------------------------------- |
| `appointments` | `apt.appointment.read` | **no**  | No `apt.*.read` code exists at all                                        |
| `billing`      | `sal.invoice.read`     | **no**  | The invoice read is gated on the write code `sal.invoice.manage`          |
| `delivery`     | `sal.delivery.read`    | **no**  | The real code is **`sal.delivery.view`**                                  |
| `documents`    | `shared.document.read` | **no**  | Recorded as `RMC-07`; both document reads are gated on the **write** code |

All four are `status: 'planned'`, so each renders as a signpost rather than a
link and **no screen built so far is affected**. `navigation.ts` declares
**20 `available` entries and 12 `planned` ones**; eighteen of the twenty name a
permission code — `overview` and `gallery` carry `permission: null` — and every
one of those eighteen is seeded. `shared.document.read` is recorded in the planning
register as `RMC-07` — a document-local finding, **not** an entry in the
`P1-27-INT-###` register. All four are additionally recorded as
`P1-27-R-07` in `docs/phase-1/phase-1-27/risk-register.md`, which is a **risk**
entry and likewise not a register finding. They are the same defect shape as
`P1-26-F-011` and `P1-26-F-029`, which were the same defect twice inside one
phase. **No test and no gate compares `navigation.ts` against the seed
catalogue**, and seeding the four codes is Backend work. Reconciling all four is
an entry criterion of the packages that own them, and it is named as such below
rather than left as a footnote.

## 2. How to read a work package

### 2.1 The fields

| field                              | what it records                                                                                                                                                                                                                                                                                          |
| ---------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Package**                        | A stable **local** identifier, `WFP-##`. It is document-local, exactly like the `WF-`/`RMC-` series, and is **not** a task id, a phase id or a register entry.                                                                                                                                           |
| **Journey steps covered**          | Which of the twenty-nine steps in `end-to-end-workshop-workflow.md` §5 the package serves.                                                                                                                                                                                                               |
| **Backend contracts consumed**     | Real operation ids, methods, paths and permission codes, read out of the route modules and cross-checked against `docs/api/openapi.v1.json` and the permission seed.                                                                                                                                     |
| **Contract status**                | `EXIST` · `PARTIAL` · `ABSENT`. `PARTIAL` and `ABSENT` are `end-to-end-workshop-workflow.md` §1.2's own words; that section's third term is **`PRESENT`**, and `EXIST` is this document's word for it — the same meaning, not a fourth status. A status is about the **contract**, never about a screen. |
| **Findings that must close first** | The document-local identifiers from `docs/product/README.md` §3. Closing one is the controlled sequence in §4, not a screen change.                                                                                                                                                                      |
| **Entry criteria**                 | What must be **true and checkable** before the package may start. Never "when we are ready".                                                                                                                                                                                                             |
| **Exit criteria**                  | What must be true before the package may be **presented** for Owner acceptance. Presenting is not passing.                                                                                                                                                                                               |
| **Owning Frontend phase**          | The phase, where a repository record names one. Otherwise **not established**, plus what would establish it.                                                                                                                                                                                             |
| **Depends on**                     | Other packages. Derived from the contracts, not from preference — see §6.                                                                                                                                                                                                                                |

### 2.2 Six entry criteria that apply to every package without exception

The per-package tables list only what is **additional** to these. Nothing below
repeats them, and nothing below waives them.

| #   | universal entry criterion                                                                                                                                                                                                                                                                                                                                                                                                                                                     |
| --- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| U1  | **Contract archaeology is complete and written down** before the first screen file is created: every operation id, method, path, permission code, request schema, response projection, audit class and page contract read out of the owning route module — not out of `openapi.v1.json`, which publishes no request body for any of its 152 mutations (`P1-27-INT-004`).                                                                                                      |
| U2  | **Every permission code the package will render against is confirmed present** in `supabase/seeds/04_iam_permission_catalog.sql`, and every code the package's writes will hit at the **database** is confirmed too. | U3  | **The acceptance environment can reach the package.** The Owner-acceptance role is provisioned **from the catalogue**, not from a list somebody believed, and a signed-in Owner can open every screen the package delivers. P1-27 shipped with an acceptance account holding fourteen Administration codes and not one CRM or Vehicle code.                                                                                                                                   |
| U4  | **No Backend, database or migration change is in the branch.** `scripts/ci/check-phase-ownership.mjs` and `scripts/ci/check-api-backend-only.mjs` both pass — see §4.3 for what each actually proves.                                                                                                                                                                                                                                                                         |
| U5  | **Every open Owner decision the package touches is named in the package’s own plan**, with the capability it blocks stated as pending. `P1-OD-017` is open. `P1-OD-025` is open for every surface EXCEPT reception evidence, where it is resolved — a package that touches it must say which half it is standing on, because “the decision is open” and “the decision does not cover this surface” are different sentences and only one of them is a reason to ship a notice. |
| U6  | **The screens the package will build are `planned` in `apps/web/src/config/navigation.ts` and their permission codes resolve.** A `planned` entry naming an unseeded code is invisible to everyone and must be reconciled before the screen is built, not after.                                                                                                                                                                                                              |

## 4. The contract-gap procedure

**No finding in §3 may be closed by editing a screen.** Every one of them is a
missing or wrong Backend contract, and a Frontend package that worked around one
would be building on a fact the platform does not hold. The sequence below is not
advice; it is the order the repository's own change control enforces, and it is
the sequence the Product Owner specified.

### 4.1 The eight steps, in order

| #   | step                                           | what it means, and what it refuses                                                                                                                                                                                                                                                                                                                                                                        |
| --- | ---------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1   | **Assign an integration finding**              | The Owner accepts the finding and it is promoted into the phase register with a real `P1-27-INT-###` number — the highest allocated today is **`P1-27-INT-009`**. A `WF-`, `RMC-`, `INS-`, `DTA-`, `PROC-`, `PPD-`, `VHM-`, `VDP-`, `VCAT-` or `MVE-` identifier is **document-local and is not a register entry**. Until this step, nothing is scheduled.                                                |
| 2   | **Identify the owning Backend phase**          | Named from `docs/product/README.md` §3 and checked against the phase records rather than assumed. Where the entry says _not allocated_, _not established_ or _the domain does not exist_, this step is a **Product Owner scope decision** and an engineer cannot perform it.                                                                                                                              |
| 3   | **Open a separate protected remediation**      | Its own branch, its own scope, based on the exact protected `origin/develop`. **A Backend contract is never repaired inside a Frontend phase's branch.**                                                                                                                                                                                                                                                  |
| 4   | **Add the OpenAPI contract**                   | The operation is registered — id, method, path, scope, audit class and action, rate-limit policy, and the `idempotent` and `versionGuarded` declarations. A published contract is what a later phase may rely on; an unpublished route is not.                                                                                                                                                            |
| 5   | **Add security and authorisation**             | The permission code, seeded in `supabase/seeds/04_iam_permission_catalog.sql` and **refused by the catalogue check if invented**. Row-level security on any new table, enabled **and forced**. Scope resolved by the server from the caller's grants and never accepted from the client. Where the database requires a permission the operation does not declare, publish the full requirement — `WF-27`. |
| 6   | **Add tests**                                  | Authorisation **both ways** — a denial-only suite proves nothing. Tenant isolation. The keyset page contract `{ items, nextCursor, hasMore }` with no `total`. Money as a decimal string with its ISO 4217 code. `numeric` and `bigint` as strings in **both** directions. **Cursor stability where two rows share a timestamp** — the defect behind `P1-27-INT-006` and `P1-27-INT-008`.                 |
| 7   | **Merge through protected change control**     | A merge commit onto `develop` through the protected gates, with zero bypass actors. **Promotion to `main` is a separate, later act** and is not part of closing a finding.                                                                                                                                                                                                                                |
| 8   | **Reintegrate into the owning Frontend phase** | Only now does the screen become buildable. The Frontend phase takes the closed contract into its **own** task register and its **own** gate, and the finding is recorded as closed against the contract that actually shipped — never against the intention.                                                                                                                                              |

### 4.2 Two rules about the sequence itself

**A finding blocked on an Owner decision stops at step 1.** `P1-OD-017` and
`P1-OD-025` are open, and every finding they bind waits for the decision rather
than for an engineer. `WFP-16` is the clearest case: it stops at step 1 in its
entirety.

**Steps 4, 5 and 6 are not optional and not reorderable.** A route published
without its permission code is an unauthenticated surface; a permission code
seeded without a route is configuration that cannot be tested; and a contract
merged without tests is a claim rather than a fact.

### 4.3 Backend work never happens inside a Frontend branch — and two gates enforce it

Both scripts were verified present in this checkout before being cited here.

| gate                                    | what it actually proves                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                               |
| --------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `scripts/ci/check-phase-ownership.mjs`  | A phase declares which parts of the repository it may touch, and the gate proves the branch honoured that declaration. It classifies **every** changed file into one of nine buckets — `web`, `apiSource`, `apiConfig`, `migrations`, `supabase`, `docs`, `tooling`, `tests`, `rootConfig` — and **an unclassified file is a failure, not a shrug**. Its docblock names the expensive failure mode exactly: "a Backend or Database change riding inside a Frontend phase, where nobody reviews it as Backend and no Backend gate is triggered by it." |
| `scripts/ci/check-api-backend-only.mjs` | `apps/api` serves HTTP and nothing else. The gate fails the build if Frontend material appears in the API workspace — a page, a stylesheet, a client component, a browser global, a React hook, an import of the web workspace, or a tracked build artefact. It counts every expectation, so **a scan matching zero files fails rather than passing quietly**, and it strips comments and string literals first, because the API legitimately contains `input.window.from` and audit codes like `shared.document.upload_authorized`.                  |

**One honest limitation, stated rather than glossed.**
`check-phase-ownership.mjs` carries exactly three profiles today —
`p1-26-frontend`, `api-boundary` and `backend-login-contract` — and
`p1-26-frontend` is the default. The Frontend profile is therefore named after
P1-26 while its rule set is generic: a Frontend phase may change `web`, `docs`,
`tooling`, `tests` and `rootConfig`, and must change no `apiSource`,
`apiConfig`, `migrations` or `supabase`. **There is no `p1-27-frontend` profile
and no `p1-28-frontend` profile.** A package that wants a gate named after
itself must add the profile and the test that plants a violation against it, in
the same change.

**And that obligation is a review rule, not a test result — stated plainly
because this document is not entitled to credit a test with more than it
asserts.** `tests/ci/phase-ownership.test.ts` plants a violation against each of
the three profiles that exist, and its `profile declarations` block asserts only
that **every** declared profile states why it exists and keeps its allowed and
forbidden bucket sets disjoint. It does **not** pin the list of profile names. A
fourth profile would therefore fail nothing merely by existing, so nothing in the
suite as it stands compels the planted-violation test to be written alongside it.

### 4.4 What the P1-27 record proves about this sequence

The sequence is not theoretical. P1-27 ran it six times before and during the
phase, and the phase's own ownership boundary — `canonical-plan.md` §9 — is what
forced each one onto a Backend branch:

| finding         | what was missing                                              | PR   | owning phase  |
| --------------- | ------------------------------------------------------------- | ---- | ------------- |
| `P1-27-INT-001` | No customer detail read and no GET on eight CRM sub-resources | #192 | P1-16         |
| `P1-27-INT-002` | No vehicle detail read                                        | #193 | P1-17         |
| `P1-27-INT-005` | No read for either duplicate-candidate queue                  | #194 | P1-16 / P1-17 |
| `P1-27-INT-006` | A keyset cursor minted from a JS `Date` silently lost rows    | #195 | P1-16 / P1-17 |
| `P1-27-INT-007` | Five catalogue relations had no read operation of any kind    | #197 | P1-17         |
| `P1-27-INT-008` | Six of the seven paginated vehicle reads lost rows silently   | #197 | P1-17         |

`P1-27-INT-007` and `P1-27-INT-008` were found **during** the phase and fixed on
a P1-17 branch rather than inside the Frontend one, because
`check-phase-ownership` would have failed the merge. That is the mechanism
working, and it is the reason the mechanism is cited here rather than described.

## 5. What every package must carry, learned from P1-27's own rejection

**This section is the reason the program exists.** Each obligation below names
the P1-27 failure that produced it. None of them is a general principle borrowed
from elsewhere.

At the moment the Product Owner found eleven defects by hand, **767 web unit
tests, 146 anonymous browser tests, 180 authenticated browser tests, 1636
database and RLS tests, hosted CI and CodeQL were all green.** Six of the eleven
were frontend behaviour and **not one was visible to any of those tiers.** That
is not an argument for more tests of the same kind.

### 5.1 A mutation for every acceptance-visible behaviour, not a passing assertion

**The P1-27 failure.** Seven Tailwind colour names were used across fourteen
components and registered in the theme in none of them — `brand-primary`,
`on-brand`, `status-danger`, `status-success`, `status-warning`, `link`,
`paper`. Tailwind emits no CSS for a class it does not recognise and reports
nothing about it, so **51 utilities across 14 components had no rule behind
them**: every primary button on the CRM and Vehicle screens rendered with no
fill, every error message was not red, every success message was not green, and
the printed document had no page colour. Nothing caught it — not the type
checker, not ESLint, not Stylelint, not the design-token gate (these are names,
not raw values), not 767 unit tests, not either browser tier.

Three more of the same shape, all from this phase's own record:

- The Wave 5 DOM suite mocked `profile-api` wholesale. Mutating
  `includesRestricted: result.data.includesRestricted === true` to a hard-coded
  `true` left **all twenty tests passing**. A layer that survives its own
  mutation is a layer nothing is testing, however green the run looks.
- `formatMatchScore`'s first six tests looked like precision tests and were
  agreement tests: replacing the whole function with
  `Math.round(parseFloat(s) * 100)` passed every one. The replacement values were
  then chosen by **running the two implementations against each other and keeping
  only the inputs where they disagree**.
- A fail-closed guard read `table.status === 'ok'`. `TableStatus` has no `'ok'`
  member, so the form rendered **nowhere at all** and the denial test passed for
  entirely the wrong reason. Only the inverse assertion could tell the two apart.

**The obligation.** Every behaviour the Owner can see is pinned by an entry in
`scripts/ci/hostile-mutations.mjs` with a named verifying test, and the matrix is
run. A `className` assertion passes whether or not the class means anything, and
a screen that renders is not a screen that works.

### 5.2 An installed-browser review, not only the bundled one

**The P1-27 failure.** Playwright ships its own chromium. **The defect the Owner
reported cannot exist there**: bundled chromium in a container draws overlay
scrollbars and Windows 11 draws classic ones, so a review in the bundled browser
would have reported the scrollbar as fine while the Owner was looking at a grey
stripe. Twenty minutes in the Owner's installed Chrome then found three more
defects that everything else had passed:

1. **A closed navigation group was 6px tall, not zero** — one permanent sliver
   per closed group, on the exact surface the Owner had just reported for a
   permanent artefact. A box's own padding is never clipped by its own
   `overflow: hidden`, and `min-height: 0` does not change that. The CSS
   reasoning said it should already be zero. **The measurement disagreed and the
   measurement was right.**
2. **The stylesheet documented a rule the browser discards.** 6px was written
   down; 10px is painted. Chrome from 121 onward implements the standard
   `scrollbar-width` and ignores an element's `::-webkit-scrollbar` rules when it
   is set.
3. **The authenticated browser tier could not sign in at all** —
   `getByLabel('Password')` matched two elements once the reveal control gained
   the name "Show password". The anonymous tier had the same defect and it was
   fixed before merge; this one survived because the anonymous tier is what CI
   runs and the authenticated tier is opt-in and local. **Neither tier is a
   superset of the other.**

**The obligation.** Every package runs a review in the installed browser, at the
viewports the Owner named, and **every check measures something and prints the
measurement**. The drawer is measured at a geometry where a drawer exists —
Tailwind's `lg` breakpoint is 1024px and the sidebar is `lg:flex`, so at exactly
1024×768 the thing under test is the desktop sidebar and a "tablet drawer" check
there would measure nothing and report a pass.

### 5.3 Contract archaeology before any screen is written

**The P1-27 failure — four separate times.**

- The Backend read surface the phase was scoped to consume **did not exist**.
  Nothing in 226 operations returned a customer; `vehicles/{vehicleId}` exported
  PATCH only; neither duplicate queue had a read; five catalogue relations were
  readable by nothing, so a creation form could not offer a make and a vehicle
  could only ever be created with all five catalogue references null.
- The permission `veh.vehicle.create` was invented by symmetry with
  `crm.customer.create`. It does not exist. The catalogue check refused the
  whole bootstrap rather than granting thirty of thirty-one.
- **Six invented enum vocabularies** reached a first draft — `crm.purpose.service`,
  `crm.consentKind.profiling`, `crm.alertType.payment`,
  `crm.restrictionType.credit_hold` among them. **No CHECK constraint admits any
  of them.** A key for a value the database cannot hold is dead weight; a key
  _missing_ for one it can hold renders the raw key on screen.
- **Two invented server vocabularies rendered raw keys to the operator.**
  `translate()` is `messages[key] ?? key`, so a value with no label renders
  `crm.addressType.service` on screen and **nothing fails** — not typecheck, not
  lint, not a test, not the build.

**The obligation.** Before the first screen file exists, every operation id,
method, path, permission code, request schema, response projection, audit class,
page contract and enum vocabulary is read out of the owning route module and the
migration that owns the column, and written down. `openapi.v1.json` **cannot** be
used as the client contract for a write: it publishes `requestBody` for **zero**
of its 152 mutations and its whole `components.schemas` section holds three
entries (`P1-27-INT-004`).

### 5.4 Plain-language wording, checked by `validate:plain-language`

**The P1-27 failure.** Owner defect 9: user-facing wording across the
application still assumed technical knowledge. Two of the eleven defects — 7 and
9 — were wording, and one of them was on the duplicate-review screens, whose
entire purpose is a careful decision about two real records.

**The obligation.** `scripts/ci/check-plain-language.mjs` runs **24 rules over
every value in both message catalogues** — JSON, UUID, enum, payload, null,
boolean, object, schema, endpoint, API, design token, status code, token,
cursor, idempotency, serialise, SQL, regex, **tenant**, permission code,
operation id, snake_case identifier, camelCase identifier and raw translation
key — with **no exemptions**, and it carries a two-way self-test.
`tests/ci/plain-language-gate.test.ts` proves the gate can still fail. Every
package passes it, and the word "tenant" is a rule rather than a preference
because it is not a word used in a workshop.

### 5.5 No colour and no class name that is not registered

**The P1-27 failure.** §5.1 above — the 51 utilities that emitted no CSS. It was
**not reported by the Owner**; the remediation found it. It is recorded
separately from defect 9 because it is a different failure with a different
cause, and merging it into the wording finding would lose the lesson.

**The obligation.** `apps/web/scripts/check-tailwind-theme.mjs`
(`validate:web-theme`) fails the build on a colour utility whose name resolves to
no entry in `tailwind.config.ts`, and `tests/ci/tailwind-theme-gate.test.ts`
proves the gate can still fail. The same package obligation extends to the
existing design authorities: no second data-table system, notification system,
i18n system, form system, dialog system, API client, brand authority or
scroll-ownership model. `validate:web-tokens` refuses a raw value;
`validate:notification-authority` refuses a second notification authority.

### 5.6 Honest reporting of what a tier did NOT examine

**The P1-27 failure — three of them.**

- `P1-27-SEC-001` made `query()` throw on `tenantId`, `companyId` and
  `branchId`. Against the running application it threw five times on a P1-26
  screen that had worked since that phase closed. The source sweep that
  justified the rule swept `features/crm` and `features/vehicles`, proved no
  scope key appears there, and **that proof was correct**. The conclusion drawn
  from it — "the client never sends scope" — was a **generalisation over trees
  the sweep never opened**.
- **176 authenticated tests passed while the server was throwing.** The failure
  rendered a state the assertions tolerate. It was found by reading server log
  lines interleaved with a green summary. **A green suite is not the same as a
  quiet one.**
- The findings register originally said the remaining cursor sites were "in
  operations P1-27 does not call". Six of them turned out to be the reads behind
  every remaining vehicle wave. The claim was true when written, made before the
  vehicle surface had been read, and nothing re-checked it when the waves that
  call those operations came into view.

**The obligation.** Every package's evidence record states, by name, what each
tier did **not** examine. Two conventions from the installed-Chrome review are
adopted verbatim:

- **A check that measured nothing is recorded as _not applicable_, never as
  _passed_.** Three of five sidebar heights are recorded that way, because at
  those heights the navigation does not overflow, there is no scrollbar to
  measure, and a 0px gutter proves nothing.
- **A console is classified, not counted.** "No console errors" is a weaker claim
  than it sounds: a CSP violation, a CORS refusal and a hydration mismatch do not
  all surface as `console.error`, so each is matched for by name.

And one more, from the same record: the clean room must be placed where the
build can actually run. P1-27's first clean room passed `npm ci`, typecheck,
lint and both suites, then failed `build:web` on a Windows `MAX_PATH` limit
caused by the scratchpad prefix — **an artifact of where the clean room was put,
not a fact about the tree.** Reporting that as a build failure would have been as
wrong as reporting the green tests as a clean-room pass.

## 6. Sequencing

**Derived from the `Depends on` column, and that column is derived from the
contracts.** Where the contracts impose no order, none is asserted here.

### 6.1 The one hard chain, and why each link is hard

| link                | why it cannot be reordered                                                                                                                                                  |
| ------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `WFP-05` → `WFP-08` | **There is no `POST /work-orders`.** A work order can be created only by converting an authorised reception, and a visit reaches `authorized` only from `inspecting`        |
| `WFP-08` → `WFP-11` | A quotation's lines come from the work order's service lines and required parts; `quo.quotation-create` requires **`wo.work_order.read`** as well as `quo.quotation.manage` |
| `WFP-08` → `WFP-12` | A stock issue is posted against a work order; `wo.required_parts` records the demand a part issue claims to satisfy                                                         |
| `WFP-08` → `WFP-13` | A quality-control record is opened at `POST /work-orders/{workOrderId}/quality-controls`; there is no work-order-free QC                                                    |
| `WFP-11` → `WFP-14` | The invoice preview derives from the work order's lines and its approved additional work                                                                                    |
| `WFP-14` → `WFP-15` | `financial_balance_outstanding` is one of the eight delivery blockers                                                                                                       |
| `WFP-13` → `WFP-15` | `quality_control_not_passed` is another, and two of the eight are enforced inside the database primitive                                                                    |
| `WFP-12` → `WFP-15` | `part_obligation_outstanding` is a third                                                                                                                                    |

Written out: **`WFP-05` → `WFP-08` → { `WFP-11`, `WFP-12`, `WFP-13` } →
`WFP-14` → `WFP-15`.** `WFP-11`, `WFP-12` and `WFP-13` are mutually independent
and may run at the same time as each other.

### 6.2 What can run in parallel, and why

| package  | independent of the chain because                                                                                                                                |
| -------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `WFP-03` | The catalogue is reference data. Nothing in it depends on a visit, a work order or an invoice                                                                   |
| `WFP-07` | A department is an organisational record. Its Backend gap is schema work that nothing else waits on — but everything about step 13 waits on **it**              |
| `WFP-10` | A price list can be built and published before any vehicle has ever arrived. `svc.price-resolve` needs no work order                                            |
| `WFP-16` | It is blocked on an Owner decision, not on a package. When `P1-OD-025` is answered it can proceed regardless of where the chain has reached                     |
| `WFP-17` | The notification and template surfaces are independent of the journey. `WFP-08` and `WFP-09` become its **consumers** at step 15, which is a different relation |

`WFP-01` and `WFP-02` are already built and are the front of the chain; they are
inside an open phase and their only remaining exit criterion is the Owner's
explicit Pass.

### 6.3 What cannot run in parallel, stated plainly

- **`WFP-04` and `WFP-05` cannot start until `WF-06` closes.** Together they are
  twelve operations and zero reads. This is not a sequencing preference; there is
  nothing to render.
- **`WFP-06`'s template half cannot start until `WF-11` closes.** Without
  template management **no workshop can create an inspection sheet at all**, so a
  road-test or lift-inspection screen would be a screen over nothing.
- **`WFP-07` cannot start at all.** `WF-09` needs a migration adding a department
  reference to an operational record. No partial version exists.
- **`WFP-09`'s roster half cannot start until `WF-14` closes.** Eight of the nine
  `tech` tables are written by nothing, so a new tenant's roster is empty and
  every eligibility check returns nothing.
- **`WFP-18` is last by construction.** Each of its sections needs the owning
  domain's read to exist first, and `VHM-03` alone — an optional `vehicleId` on
  `wo.work-order-list` — makes seven of the twenty-eight sections reachable.

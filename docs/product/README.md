## 0. This whole set is planning and traceability only

**Nothing in any of the ten documents indexed below is implemented by Phase
1-27.** Not one of them describes a capability a workshop can use. They are a
map: they take what the Product Owner asked for, lay it against the contracts
that actually exist in this repository, and record — by number — every place
where the contract a step needs does not exist.

Three statements are kept apart throughout the set, and a reader who runs them
together will draw a false conclusion from every page:

| statement                          | what it means                                                                                                                                                       |
| ---------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **A Backend contract exists**      | A published API operation was read out of a route file on branch `remediation/p1-27-owner-acceptance-ux`. It can be called. It does **not** mean a screen calls it. |
| **A Frontend screen exists**       | True only for what Phase 1-27 itself delivered: customer and vehicle search, read and creation screens, and the two duplicate-**review** screens. Nowhere else.     |
| **A step or section is described** | The business intention has been mapped onto a contract. **Mapping is not building.**                                                                                |

This set also does not authorise work. The obligations it records become real
only when a later phase takes them into its own task register and gate, by the
sequence in §5.

### 0.1 Rules every document in the set obeys

| rule                                                                                                                        | why                                                                                                                                                           |
| --------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| No contract is guessed. Operation ids, permission codes, tables, columns and status values were read out of the repository. | A previous documentation wave invented `veh.vehicle.create`; the permission catalogue check refused it. The real code is **`veh.vehicle.manage`**.            |
| No count, total, service level, vendor price or throughput figure is invented.                                              | Where a number is unknown the text says **not established** and names what would establish it.                                                                |
| Money is a **decimal string plus an ISO 4217 currency code**. Never JavaScript floating point.                              | `numeric(18,4)` holds values IEEE-754 cannot represent. The loss would be silent and would not repeat reliably enough to be found by testing.                 |
| `numeric` and `bigint` arrive as **strings** and stay strings.                                                              | Converting one to a number to format it is how precision is lost silently.                                                                                    |
| Every list is keyset/cursor paginated: `{ items, nextCursor, hasMore }`. **There is no `total`.**                           | The platform fetches one extra row to detect `hasMore` rather than running a second counting query. No screen may show "page 3 of 47".                        |
| **`P1-OD-017`** (duplicate and merge rules) and **`P1-OD-025`** (media upload policy) are OPEN Owner decisions.             | They are named wherever they bind and are never written around. Where either binds, the capability is described as pending and the decision is named.         |
| Purchasing or contracting a paid data provider is a **commercial decision reserved to the Product Owner**.                  | Every document recommends an **evaluation** where an external source would help. None recommends, prices or authorises a purchase, and no vendor is endorsed. |

## 2. How to read the consolidated register

The register in §3 gathers **every** finding from all ten documents into one
table. Each identifier is **document-local**: the `WF-`, `RMC-`, `INS-`, `DTA-`,
`PROC-`, `PPD-`, `VHM-`, `VDP-`, `VCAT-` and `MVE-` series are introduced by
their own documents and are **not** entries in the live `P1-27-INT-###` register
at `docs/phase-1/phase-1-27/findings.md`, whose highest allocated identifier is
`P1-27-INT-009`. Promoting any of them into that register is a governance act
belonging to the register's owner, and this document does not perform it.

Three cautions about the columns.

| column                    | how to read it                                                                                                                                                                           |
| ------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Owning Backend phase**  | The phase that would own the change. Where no phase owns the domain, the entry says so — **not allocated**, **not established** or **the domain does not exist** — rather than guessing. |
| **Owning Frontend phase** | The phase that owes the screen. **Not established** means no record in this repository names one. **None** means the finding genuinely has no screen obligation. Neither is an omission. |
| **Required action**       | Compressed. The owning document holds the full statement, and the register never contradicts it — where the two ever disagree, the owning document is correct.                           |

**The register is not a plan and not a schedule.** No finding here is scheduled,
funded or accepted. Whether any of them is in Phase 1 scope is a Product Owner
scope decision against the canonical Phase 1 plan.

## 5. The controlled sequence for closing a finding

**No finding in §3 may be closed by editing a screen.** Every one of them is a
missing or wrong Backend contract, and a Frontend phase that worked around one
would be building on a fact the platform does not hold. The sequence below is not
advice; it is the order the repository's own change control enforces.

| #   | step                                           | what it means, and what it refuses                                                                                                                                                                                                                                                                                                                                                                             |
| --- | ---------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1   | **Assign**                                     | The Owner accepts the finding and it is promoted into the phase register at `docs/phase-1/phase-1-27/findings.md` (or the successor register) with a real `P1-27-INT-###` number. A `WF-`, `RMC-`, `INS-`, `DTA-`, `PROC-`, `PPD-`, `VHM-`, `VDP-`, `VCAT-` or `MVE-` identifier is document-local and is **not** a register entry. Until this step, nothing is scheduled.                                     |
| 2   | **Identify the owning Backend phase**          | Named from the register in §3, and checked against the phase records rather than assumed. Where the entry says _not allocated_, _not established_ or _the domain does not exist_, this step is a Product Owner scope decision and cannot be performed by an engineer.                                                                                                                                          |
| 3   | **Open a separate protected remediation**      | Its own branch, its own scope. A Backend contract is never repaired inside a Frontend phase's branch: the P1-27 canonical plan forbids `apps/api/src/**` and `supabase/**` changes in a Frontend phase, and the changed-file ownership gate enforces it.                                                                                                                                                       |
| 4   | **Add the OpenAPI contract**                   | The operation is registered — id, method, path, scope, audit class and action, rate-limit policy, and the `idempotent` and `versionGuarded` declarations. A published contract is what a later phase may rely on; an unpublished route is not.                                                                                                                                                                 |
| 5   | **Add security and authorisation**             | The permission code, seeded in `supabase/seeds/04_iam_permission_catalog.sql` and refused by the catalogue check if invented. Row-level security on any new table, enabled **and forced**. Scope resolved by the server from the caller's grants and never accepted from the client. Where the database requires a permission the operation does not declare, the full requirement is published — see `WF-27`. |
| 6   | **Add tests**                                  | Authorisation both ways — a denial-only suite proves nothing. Tenant isolation. The keyset page contract `{ items, nextCursor, hasMore }` with no `total`. Money as a decimal string with its ISO 4217 code. `numeric` and `bigint` as strings in both directions. Cursor stability where two rows share a timestamp.                                                                                          |
| 7   | **Merge through protected change control**     | A merge commit onto `develop` through the protected gates, with zero bypass actors. Promotion to `main` is a separate, later act and is not part of closing a finding.                                                                                                                                                                                                                                         |
| 8   | **Reintegrate into the owning Frontend phase** | Only now does the screen become buildable. The Frontend phase takes the closed contract into its own task register and its own gate, and the finding is recorded as closed against the contract that actually shipped — never against the intention.                                                                                                                                                           |

### 5.1 Two rules about the sequence itself

**A finding blocked on an Owner decision stops at step 1.** `P1-OD-017` and
`P1-OD-025` are open, and every finding they bind waits for the decision rather
than for an engineer. Building the "safe half" of a decision is how a decision
gets pre-empted.

**Steps 4, 5 and 6 are not optional and not reorderable.** A route published
without its permission code is an unauthenticated surface; a permission code
seeded without a route is configuration that cannot be tested; and a contract
merged without tests is a claim rather than a fact.

# Owner directive 2026-09-16 — change-control register

Every prerequisite found while measuring the directive against the repository at `2c573a24`, plus
the findings added when the merged work was re-measured at `5b2c7840` on 2026-09-18. A finding here
is a statement about the code as measured, not a plan; the disposition column says what was decided
about it, and the status column says whether that decision has landed.

**Rows CC-OD-16 to CC-OD-21 were measured at `5b2c7840`, after the six directive pull requests
merged.** They are what the merged work left open, or left absent by decision, and they are
recorded here rather than left to be noticed later.

**Rows CC-OD-24 to CC-OD-31 were raised by the measurement campaign of 2026-09-19 to 2026-09-21**,
which worked the product by hand on the local acceptance stack against three heads of `develop` in
turn and ended at `f30ce918`. Each of those rows names the head it was measured at, and none of them
claims a re-measurement it did not take. **Six of the eight are decisions rather than defects**:
whether the provisioning form should assign the plan it names (CC-OD-24), whether a provisioned
organisation may record a cost (CC-OD-25) or approve a credit note (CC-OD-26), where a vehicle
catalogue comes from (CC-OD-28), whether platform authority should be revocable (CC-OD-29 — decided 2026-09-22, see its row), and
whether a password change should end a session already in use elsewhere (CC-OD-31). They are written
as decisions, with what each costs stated, and no slice has been asked to guess at any of them. The
same campaign closed the wording half of CC-OD-31 and the reachability half of CC-OD-16.

**CC-OD-32 was not raised by that campaign.** It was read at `fe09f1a9` while recording the close of
CC-OD-27, and it states what the fix for that row deliberately did not cover. A row that closes may
leave a narrower row behind it; this register writes that down rather than closing the wider row
quietly.

**CC-OD-23, and the register's numbering.** This row is introduced here, on the harness branch,
because the change it describes is a Supabase-configuration change and every phase profile
forbids that bucket by name. A differently worded `CC-OD-22` and `CC-OD-23` pair was written on
the unmerged branch `feature/owner-directive-acceptance-evidence`, which measured the same
recovery fault on a hand-corrected stack and correctly declined to carry the repair. Those two
rows and this one describe the same investigation and must be reconciled into one register when
both branches land; whichever merges second owns that reconciliation.

**The register therefore has a hole at `CC-OD-22` on this branch, and it is left deliberately.**
Renumbering this row to `CC-OD-22` would collide with a different finding of that id on the other
branch and make the conflict silent instead of loud. The identifier is held for the other branch's
row, this row keeps `CC-OD-23`, and the merge that brings the two together is expected to conflict
here and is meant to.

`CC-OD-23` is closed by this branch for the mail cause it names, and only for that. The
sign-in fault that had to be cleared before the journey could be completed is `P1-26-F-045`, which
already exists in `docs/phase-1/phase-1-26/findings.md` with its own routing, and no part of it is
re-declared as a new finding here.

## Rules

- A row closes only with a dated note naming the merged pull request that closed it. The note is
  added to this file in the same change that flips the status.
- No row is closed by a plan. A plan to fix a finding leaves the row open; the merge closes it.
- `fixed in this branch (hosted result pending)` means the code change is committed on the named
  branch and the hosted result for that branch has not been read yet. It is not a closed row.

**What a `measured` marker claims, and what it does not.** It claims that the capability was
exercised on the local environment on that date and that the product's own answer was read back —
including where that answer was a refusal, in which case the row says so. It is **not** a claim that
any check, certification, audit or approval passed, and it is not a claim about any environment
other than the local one, because no other environment exists. Where the campaign measured a
capability and found a gap, the row states the gap and names the change-control row that carries it.

## The four states

- **implemented** — a user can reach the capability through a route in the web application, the
  route calls a backend operation that exists, and the evidence column names where that was
  demonstrated. Where an operation exists and works but has no screen, the row says
  `implemented (API only)` and is not a completed workflow.
- **partial** — some of the capability exists and a stated part of it does not. The gap is written
  in the row, not left to be inferred.
- **missing** — no route, no operation, or neither.
- **externally blocked** — the capability cannot be completed inside this repository, and the
  reason names what is outside it.

A row needs all three of a UI route, a backend operation and evidence before it reads
**implemented**. A plan is not evidence. An API without its screen is not a completed workflow. A
screenshot of a screen that performed no transaction is not evidence that the transaction works.

**A row with no marker is not a demonstrated row either.** It means one of three things, and the row
itself says which: the capability is `missing` or `externally blocked`, so there is nothing to
demonstrate; the row records a document rather than a running capability; or the capability predates
these six pull requests and is unchanged by them, in which case whatever evidence exists for it
belongs to the earlier phase that delivered it and was not re-taken here. No hosted run, acceptance
run, certification or approval is claimed anywhere in this file.

## Owner directive of 2026-10-01: accounting invariants, approved product policy and per-organisation configuration

The 2026-10-01 directive asks for configurable commercial policy to be kept apart from accounting invariants, and for no financial policy to be invented. This section keeps three things apart: what the code enforces as an invariant, what ADR-023 approves as product policy, and what each organisation configures. It cites ADR-023 by line and does not restate its rules. Implementation state of each decision is ADR-023's mapping table (`:270-288`); verification state is the delivery matrix above.

**The count, kept apart from the 97 capability rows:** the decision table in part 3 holds 16 rows (D5 and D15 share one).

### 1. Accounting invariants the code already enforces

These are code facts, not ADR-023 policy, and keeping them needs no questionnaire answer. No module reads a company or branch settings row (`docs/platform/architecture-assessment-2026-10-01.md` section 5), so no current setting reaches them; FC-19 proposes making that structural.

- **Issued documents are frozen.** `sal.guard_invoice_freeze` admits `issued -> credited` only (current definition `20260917093000_sal_counter_sales.sql:88-123`; trigger `20260724091000_sal_invoices.sql:133`; `billing/index.ts:54-56`). Stock from an issued counter sale returns only through a sales return (`20260917093000_sal_counter_sales.sql:34-39`).
- **Document amounts are snapshots.** Quotation lines carry a captured rate and amount checked by a trigger (`20260930100000_sal_minor_unit_rounding.sql:102-130`). Invoice lines are copied from the approved revision (`invoice-service.ts:825-840`).
- **Money is computed by the database in numeric**, and no client supplies an amount except a credit note's, which is bounded (`billing/index.ts:37-49`).
- **Financial events are append-only.** SELECT and INSERT grants only (`20260724093000_sal_financial_events.sql:123-124`). Amount and currency are bound to the source row (`:61-110`). One event per source and event type (`:53`).
- **The stock ledger is append-only.** SELECT and INSERT grants only (`20260723094000_inv_ledger.sql:97-98`). One movement per source and direction (`:80`).
- **Balances are derived, not stored.** The open receivable comes from `sal.invoice_open_receivable` (`20260724093000_sal_financial_events.sql:129-150`). Stock balances are coherence-guarded to movements and reservations (`20260723094000_inv_ledger.sql:129`).
- **Recovery is roll-forward only** for financial records (`20260724093000_sal_financial_events.sql:9-10`; `docs/phase-1/phase-1-11/phase-1-11-roll-forward-only-recovery-note.md`).
- **Audit is append-only**, written only through `iam.audit_append` (`apps/api/src/server/audit/audit.ts:88-92`).
- **Document numbers have no fallback.** An unprovisioned sequence is a configuration error (`billing/index.ts:50-53`).

### 2. Configurable commercial policy today

Each organisation sets these. None is an accounting invariant.

- Price lists, versions, rules, assignments, discount rules and pricing approval policies (`20260723092000_svc_pricing.sql:80-355`).
- Item selling prices by branch, company or everywhere (`20260917092000_inv_item_sale_prices.sql:54`; `capability-status.md:155`).
- Approval limits per type, currency, role or person within a company, including D13's credit-note limits (ADR-023 `:196-201`, `:392-393`).
- Who holds each permission code: the organisation's role grants.
- Tax classes and rates, designed as company configuration (`20260717105000_org_settings_tax_features.sql:193-194,244-245`). There is no write path yet (PPD-03): FC-20 is a design for the structure, held with the values until the questionnaire is answered.
